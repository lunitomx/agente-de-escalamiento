Zero architectural debate — the ADR from S14.1 was working as intended.

## What To Improve

1. **Design doc expected-value table should be formula-derived, not hand-written.** The design doc had a $100 discrepancy in the COGS example row — the table showed one expected CF impact while the formula text implied a different value. Future design docs for calculation dashboards should auto-derive the expected values from the formula itself, not enter them manually.
2. **Injection guard pattern should be in the standard dashboard template.** The `window.CASH_DATA.key = window.CASH_DATA.key || {...}` guard was caught by QR, but it should be a required line item in the implementation checklist (or baked into the scaffold template) so it's never missed on initial implementation.
3. **AR/QR should explicitly check `||` guards on all `window.*` data injection points.** This is a common defensive pattern specific to these dashboards. Adding it as a named check in the AR/QR skill would catch it before the fix commit.

## Heutagogical Checkpoint

### 1. What did I learn?

The `window.CASH_DATA.powerOfOne = window.CASH_DATA.powerOfOne || {...}` guard pattern is architecturally load-bearing for all S14.1–S14.4 dashboards. Without it, the script's inline example data silently overwrites any real coaching output injected before the script runs — the dashboard would always show example data, never live data. This is the kind of bug that passes all visual QA (it looks correct) but breaks the actual integration. The pattern must be treated as a correctness requirement, not a style preference.

### 2. What would I change about the process?

The design doc for a calculation dashboard should include a "formula verification" table where expected values are computed by running the formula on the example inputs — not entered by hand. Hand-entering expected values introduces transcription errors (like the $100 COGS discrepancy in the S14.2 design doc). If the formula is implemented as a spreadsheet cell, the expected value table is free.

### 3. Framework improvements?

- Add to `rai-architecture-review` skill: "For HTML dashboards using `window.*` data injection, verify that every assignment uses the `||` guard: `window.X.key = window.X.key || defaultValue`. A missing guard will silently overwrite live injected data."
- Add to `rai-quality-review` skill: same check as AR above — make it explicit in the dashboard-specific QR checklist.
- Add `||` guard check to the implementation checklist in `s14.x` story templates.

### 4. What am I more capable of now?

The Power of One calculation engine establishes the Category A (P&L) / Category B (working capital) pattern that will be reused in any future cash analysis story. Category A: ΔCF = ΔValue × Volume (and ΔEBIT = same). Category B: ΔCF = Δdays × dailyRevenue, ΔEBIT = 0. This is a reusable computation primitive for cash coaching dashboards across E14–E17.
