# Diseño S67.6 — Compatibilidad Agent Plugins v1

## Problema y valor

ESCALA ya tiene una puerta pública (`escala`), un contrato MVP aprobado y
adaptadores privados para Codex y Claude. Falta un paquete mínimo del estándar
abierto Agent Plugins que permita a un cliente compatible descubrir esa misma
puerta sin instalar configuración de usuario, agentes privados, MCP o datos de
empresa.

## Decisión

Crear un builder y un validador offline en `adapters/agent_plugins/`. El
builder recibe un directorio de salida absoluto y vacío bajo una raíz permitida,
proyecta sólo el skill canónico y el catálogo de capacidades, y escribe:

| Ruta de salida | Propósito |
|---|---|
| `plugin.json` | manifiesto Agent Plugins v1 cerrado |
| `skills/escala/SKILL.md` | única puerta pública, con referencia reubicada |
| `skills/escala/references/capability-catalog.json` | contrato requerido por el skill, sin estado mutable |

El manifiesto declara el schema canónico, el nombre `escala` y metadatos
descriptivos; no declara extensiones ni MCP. El validador comprueba el
manifiesto, el conjunto exacto de archivos, descubrimiento a un nivel,
contención de rutas, ausencia de symlinks y ausencia de contenidos privados.
El builder usa directorio temporal hermano y renombre atómico: ante cualquier
fallo no deja un paquete parcial.

## Componentes y dependencias

| Componente | Cambio |
|---|---|
| `adapters/agent_plugins/build_plugin.py` | builder determinista y CLI local |
| `validators/agent_plugin.py` | contrato estricto y validación offline |
| `tests/test_s67_6_agent_plugins.py` | RED/GREEN de manifest, superficie, contención y fixture para E68 |
| `work/.../s67.6-*.md` | trazabilidad de diseño, plan y retrospectiva |

Se reutilizan `capabilities/mvp/catalog.json` y `escala-skills/escala/SKILL.md`
como fuentes de verdad. No se altera `install.sh`, ni los adaptadores Codex o
Claude: éstos ya cubren sus integraciones específicas.

## Límites y riesgos

- Un paquete válido prueba estructura y descubrimiento; no declara equivalencia
  semántica entre modelos ni compatibilidad plena de cada cliente. Esa prueba
  corresponde a E68.
- Los subagentes de cuatro áreas permanecen internos: exponerlos convertiría
  la puerta única en un catálogo técnico.
- No se empaqueta transcript, curso, memoria, SQLite, conectores o secretos.
- La referencia del catálogo se reescribe una sola vez durante la proyección;
  si el skill canónico cambia esa forma, el build falla para evitar deriva.

## Gemba, legado y deriva

`adapters/codex/build_adapter.py` ya muestra el patrón seguro de salida
absoluta, directorio temporal y superficie exacta; se reutiliza el patrón, no
su manifiesto específico de Codex. `validators/capability_map.py` conserva el
catálogo canónico, por lo que esta historia no crea una segunda taxonomía.
`validators/public_export.py` protege la exportación integral pero no modela el
formato Agent Plugins; el validador nuevo es net-new y complementario.

No hay V1 huérfano: esta es una capacidad net-new y los adaptadores existentes
coexisten porque cubren plataformas distintas. No se identificó hotspot de
deriva; se mitigan AG2 evitando duplicar contrato y AG4 manteniendo el cambio
en builder, validador y prueba con límites explícitos.

## Criterios de aceptación verificables

1. El paquete válido contiene exactamente las tres rutas declaradas y un solo
   skill hijo directo, `escala`.
2. Schema, nombre, campos desconocidos, symlinks, referencias que escapen y
   archivos privados fallan con razones estables y sin destino parcial.
3. Un fixture sintético puede ser usado por E68 para descubrir el skill y leer
   su contrato, sin afirmar que el modelo haya cumplido la metodología.
