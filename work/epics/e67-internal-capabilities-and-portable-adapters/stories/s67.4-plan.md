# Plan S67.4 — Paridad y migración de adaptadores

## Tareas ordenadas

1. **RED — contrato y matriz**
   - Especificar la matriz de seis capacidades y las pruebas de que Codex y
     Claude llegan al mismo catálogo y a una sola puerta pública.
   - Especificar la prueba negativa de aliases con lógica propia.

2. **GREEN — generador verificable**
   - Implementar un validador local y un script con `--check` para mantener el
     reporte JSON versionado.
   - Añadir un reporte Markdown que deje explícita la responsabilidad limitada
     del router YAML histórico.

3. **REFactor y verificación**
   - Ejecutar las pruebas de S67.2, S67.3, aliases y paridad; además de
     formato, lint y tipos aplicables.
   - Ejecutar el chequeo de reporte desde un checkout limpio de la historia.

## Riesgo y control

El riesgo principal es llamar equivalentes a dos catálogos distintos. La
matriz sólo toma como autoridad el JSON MVP; el YAML se identifica por nombre,
conteo y frontera de compatibilidad. Si el router necesita adoptar el JSON,
eso se registrará como historia posterior con su propio diseño y migración.
