## Revisión de arquitectura

1. **Deriva estructural:** el adaptador vive fuera del core y no crea APIs ni
   comandos adicionales.
2. **Complejidad:** tres archivos estáticos y una prueba de contrato; no hay
   abstracciones, almacenamiento ni red especulativos.
3. **Convención:** usa el core y el instalador existentes; el checkout de la
   prueba evita configuración personal.

No fue posible escribir la atestación `gate-ar-story`: RaiSE no expuso un
identificador de sesión resoluble en este worktree. La revisión queda
documentada; el cierre debe registrar este límite de infraestructura sin
presentarlo como una aprobación automática.

## Aprendizajes

1. Un adaptador multiplataforma debe declarar sus límites como datos y no
   repetir el orquestador; así la revisión puede probar la frontera.
2. El instalador actual requiere un checkout o artefacto materializado, pues un
   worktree tiene `.git` como archivo. Las pruebas de instalación deben simular
   el empaquetado que verá el empresario.
3. Los gates del CLI crean un `.venv` temporal en el worktree; se retiró tras
   cada ejecución para respetar la higiene del repositorio.
4. Ahora podemos validar una instalación Claude y separar claramente un límite
   de cliente de una diferencia de modelo, que S67.4/E68 medirán.
