# Retrospective: S36.6 — Master Acceptance Ledger

**Dates:** 2026-07-21 → 2026-07-21
**Estimated implementation:** 75m | **Recorded implementation and review repair:** 28m

## Summary

S36.6 established one strict, versioned acceptance control plane for the full
E37-E42 master plan: 6 epics, 42 requirements, deterministic YAML/Markdown
parity, evidence declarations, source-bound receipts, platform and gate scope,
and local-only architecture invariants. The current baseline is contract-valid
and deliberately mission-unproved: `0/42` requirements are proved. Baseline
mode exits 0 because the inventory is structurally complete; readiness exits 2
because future product work is still missing evidence.

Review found four material contract defects before close: multiple unproved
blockers could be represented while only one was rendered; valid reviewable
`unresolved/review-required` and `deferred/backlog` dispositions were rejected;
the human ledger omitted source, receipt, and blocker facts; and a broken
symlink could bypass the explicit non-overwrite guard. Commit `e275943` repaired
all four through focused RED-GREEN tests. The real qualification sequence was
then rerun from that immutable repair commit and recorded in `dc2fe09`; the old
receipt remains historical evidence and was not relabeled.

  discriminated proof states are covered by `tests/test_master_acceptance.py`.
- The canonical ledger contains each approved E37-E42 requirement exactly once

- Every requirement preserves its sources, observable acceptance statement,
  evidence artifact, receipt path, verification declaration, required gates,
  platforms, state, and blocker in both machine and human views.
- No plan, checkbox, code-presence claim, historical label, incomplete gate,
  stale receipt, or reviewable non-complete disposition can produce `proved`.
- Installer-machine authority, local data, filesystem-only Drive/OneDrive
  exchange, no hosted runtime, and no synchronized/shared authoritative SQLite
  are validated against canonical governance and export authorities.
- Two isolated real baseline runs are byte-identical; corrupt input fails with
  a fixed safe error; HEAD, tree, worktree status, remotes, public candidate,
  runtime, and external systems are not mutated.
- The current receipt is bound to source `e27594395cdba0087f6d7f42e8f36ce2ed3dd4bf`
  and tree `2748bfcf6aa994ec80e96587079fc05aa40334a0`.
- Scoped master-acceptance, governance, export, lint, format, types, and schema

## What went well

- The ledger makes product truth executable without confusing a valid plan
  inventory with delivered functionality.
- Authority hashes reuse canonical identity, closure, local-only, legal, and
  publication contracts instead of introducing competing vocabularies.
- The evaluator never executes declared verification commands. It validates
  content-addressed evidence and remains deterministic and offline.
- Review did substantive work: it compared the human artifact with the machine
  contract and exposed decision facts that tests had not previously required.
- Requalification preserved evidence lineage. Historical receipts remain
  auditable at their source commit, while current qualification comes only from
  the repaired source.

## What to improve

- Human/machine parity should be tested from the first renderer RED by asserting
  every decision-bearing field, not merely headings and selected values.
- Disposition tests should enumerate every canonical reviewable non-complete
  state at contract design time. The original test set covered active and
  completed paths but missed unresolved and deferred paths.
- Explicit output writers should treat any directory entry, including broken
  symlinks, as occupied. This guard now exists, but it should become a standard
  writer checklist item.
- RaiSE emitted the repaired implement-complete signal correctly, but querying
  with a non-exported fallback session ID returned an older signal. The CLI
  should expose the active session ID or warn when the filter is not the current
  emit context.
- The design, plan, and implement learning-record writers were silent for this
  story. That prevents formal lifecycle acceptance/gap metrics and should be
  repaired in the framework rather than imputed in retrospectives.

## Heutagogical Checkpoint

1. **What did I learn?** A machine-valid acceptance ledger can still be unsafe
   for human decisions. Before `e275943`, the Markdown looked complete but hid
   each requirement's receipt and blocker, so a reviewer could not independently
   distinguish absent proof from a concrete blocking condition.
2. **What would I change about the process?** I would define a field-by-field
   parity matrix during renderer design and use it as the first failing test.
   That would have moved the Markdown defect from review into T2 without reducing
   the value of the independent review.
3. **Framework improvements?** RaiSE needs reliable lifecycle learning records
   and less ambiguous session-filtered signal queries. It would also benefit
   from a reusable acceptance-ledger review checklist covering reviewable
   dispositions, symlinks, human parity, immutable source binding, and
   requalification after contract changes.
4. **What am I more capable of now?** I can operate a fail-closed master plan
   where contract validity, mission readiness, legal review, publication
   authorization, platform qualification, and human acceptance remain separate
   evidence-backed states across dozens of requirements.

## Improvements applied

- Limited unproved requirements to one explicit blocker so no blocker can be
  silently hidden by the human renderer.
- Accepted all canonical reviewable non-complete dispositions while preserving
  their unproved state.
- Expanded the Markdown ledger to include all decision-bearing evidence fields.
- Rejected existing files, directories, valid symlinks, and broken symlinks at
  explicit output targets.
- Validated historical receipt bytes against their exact Git source and reran
  the full deterministic baseline after the review repair.
- Re-emitted implementation completion on the final implementation HEAD and
  reran the focused master-acceptance gate when a session-filtered query appeared
  stale.

## Patterns added / reinforced

- Added `PAT-L-1300`: contract validity and mission readiness are separate;
  `0/N` can be a truthful valid baseline but never readiness.
- Added `PAT-L-1301`: each human acceptance row must preserve all
  decision-bearing machine facts.
- Reinforced `PAT-L-14` (+1) and `PAT-L-6` (+1): writer output is validated
  through the actual typed validator, not a parallel approximation.
- Reinforced `PAT-L-1298` (+1): technical, legal, and publication states remain
  separate authorities.
- Reinforced `PAT-L-1299` (+1): a qualification-contract repair requires a new
  immutable commit and complete rerun, never evidence relabeling.

## Learning chain summary

The expected lifecycle records for `rai-story-design/S36.6`,
`rai-story-plan/S36.6`, and `rai-story-implement/S36.6` were all missing. Formal
lifecycle acceptance rate, gap rate, and pattern utility are therefore `N/A`,
not zero. Review PRIME had two mandatory queries and returned no patterns.
Review JIT used its maximum three topic queries; none returned an existing
pattern covering the complete requested topic, so review-local topic gap rate is
`3/3 = 100%`. Two missing concepts became `PAT-L-1300` and `PAT-L-1301`; the
immutable-rerun and technical/legal/publication lessons were already present as
`PAT-L-1299` and `PAT-L-1298` but were not retrieved by these queries. Four
consciously evaluated existing patterns received +1 and none received -1, so
review-local pattern utility is `4/(4+0) = 100%`.
