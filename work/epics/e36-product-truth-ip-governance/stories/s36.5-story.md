# Story: Clean Export, License & Third-Party Contract

## User Story

As the ESCALA product owner and release operator,
I want a deterministic local clean-export builder and an independent staged-
artifact verifier,
so that a distribution candidate contains only explicitly approved portable
product files, carries truthful license and third-party metadata, and cannot
publish private, reference, credential, governance, or company material.

## Acceptance Criteria

### Scenario: A clean artifact is assembled from an allowlist

```gherkin
Given the private canonical repository is at a named clean commit
And a strict versioned product-boundary manifest declares exact public files
and roots
When the local builder targets a new empty temporary staging directory
Then it enumerates only allowlisted Git-tracked regular files
And every non-allowlisted source path remains absent
And it emits a sorted file manifest with a SHA-256 for every staged file
And it does not mutate the private repository or any public candidate
```

### Scenario: The staged artifact is independently verified

```gherkin
Given an artifact was produced by the clean-export builder
When an independent verifier scans the staging directory
Then it validates the staged files rather than trusting the source scan
And it proves the file set and hashes match the export manifest
And it returns a passing technical-artifact receipt only when every required
check passes
```

### Scenario: Unexpected or unsafe staged content fails closed

```gherkin
Given a passing staged artifact
When a file is added, removed, changed, replaced by a symlink, or given a
traversal path
Then independent verification fails
And the receipt identifies only a safe rule and relative locator
And no matched secret, private content, absolute root, remote URL, or raw
subprocess output is serialized
```

### Scenario: License and third-party posture is truthful

```gherkin
Given the current educational notice is not a formal software license and
conflicts with commercial product use
When clean-export policy is evaluated
Then the artifact contains explicit license-status and third-party inventory
metadata
And missing, contradictory, or unreviewed metadata cannot be inferred as legal
approval
And publication authorization remains false until the named human legal gate
is completed
```

### Scenario: Public-boundary rules apply to the exact artifact

```gherkin
Given the S36.3 public-boundary policy and the S36.2 immutable baseline
When the staged artifact is independently scanned
Then prohibited source, author, execution-method, private-path, credential,
company-data, and provenance rules have zero blocking findings
And the raw source remains absent from the staged current tree
And historical private presence is not misreported as an artifact finding
```

### Scenario: Repeated local builds are deterministic

```gherkin
Given the same clean source commit, policy, and approved metadata
When two builds run in separate empty local staging directories
Then their sorted path-and-hash manifests are byte-identical
And their sanitized verification receipts are byte-identical
And no timestamp, temporary root, or machine-specific path changes the result
```

### Scenario: Local-only and sharing boundaries survive export

```gherkin
Given ESCALA runs only on the installer's machine
When the export manifest is validated
Then it includes no hosted ESCALA service, cloud database, telemetry, OAuth,
Drive API, or OneDrive API requirement
And it never includes an authoritative SQLite database
And Drive or OneDrive remains only an optional user-controlled folder for
ordinary inbox and report files
```

## Examples (Specification by Example)

| Input state | Action | Expected output |
|---|---|---|
| Allowlisted tracked regular file with neutral content | Build and verify | File copied once; exact SHA-256 appears in sorted manifest |
| Candidate-public path not present in the explicit export allowlist | Build | Path excluded; candidate classification is not treated as permission |
| New unclassified tracked file | Build | File excluded by default; no implicit expansion of the artifact |
| Required metadata file missing | Verify | Fail-closed metadata check; technical artifact does not pass |
| Current educational notice with no formal software license | Evaluate posture | Explicit legal-review requirement; publication remains unauthorized |
| Staged file contains a prohibited identity term | Verify | Blocking vocabulary rule with safe relative locator only |
| Staged file contains a secret-shaped sentinel | Verify | Blocking credential rule; sentinel value absent from every output surface |
| Extra staged file or changed hash | Verify | Manifest mismatch; artifact fails |
| Symlink points outside staging | Verify | Traversal/symlink failure; external target is never read into evidence |
| Same source and policy built twice | Compare | Byte-identical manifest and receipt |
| Existing dirty public candidate | Run E2E flow | Strong before/after fingerprint remains identical; no copy-over or push |

## Notes

- This story implements E36 milestone M3 from the accepted epic design and
  `E36-ADR-001`.
- The 285 S36.3 candidate-public paths are a canary set, not an allowlist.
  Every distributed path requires explicit admission by S36.5.
- Technical artifact verification and legal/publication authorization are
  separate states. A clean technical artifact does not claim counsel approval.
- The existing Action Plan exporter retains its current business responsibility;
  this story uses product-boundary terminology for package export.
- The real integration proof runs locally from a clean source commit into a
  temporary directory and independently verifies the resulting filesystem.
- No hosted runtime, database migration, Drive/OneDrive integration, public-
  candidate repair, Git history rewrite, push, or publication belongs here.
