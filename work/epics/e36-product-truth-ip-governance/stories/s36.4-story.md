# Story: Typed Governance Taxonomy & Unique Epic IDs

## User Story

As the ESCALA product owner and governance operator,
I want one typed, fail-closed closure taxonomy and one unambiguous canonical
identity for every legacy epic folder,
so that validators and graph builds cannot mistake an unknown status, prose
alias, or duplicate numeric folder for completed work.

## Acceptance Criteria

### Scenario: Closure dispositions have one executable source of truth

```gherkin
Given governance scopes currently express complete, active, deferred, absorbed,
superseded, deprecated, partial, and backlog postures
When a validator evaluates an epic closure
Then it loads the disposition from one versioned typed policy
And terminal, completed, reviewable, and activation-eligible semantics come from
that policy
And the validator does not maintain a competing hard-coded vocabulary
```

### Scenario: Unknown or incomplete disposition fails closed

```gherkin
Given a scope uses an unknown, malformed, missing, or legacy-only status
When closure eligibility is evaluated
Then the policy rejects it with a stable safe error
And the epic cannot be treated as complete or activation-eligible
And no permissive alias is inferred from partial text
```

### Scenario: Every colliding legacy folder receives a unique identity

```gherkin
Given the repository contains two folders for each bare numeric ID E18 through
E22
When the epic identity registry is validated
Then every in-scope folder has exactly one unique canonical ID
And every resolvable alias maps to exactly one canonical entry
And a colliding bare numeric reference fails as ambiguous instead of selecting
one folder silently
```

### Scenario: Legacy links remain traceable without preserving collisions

```gherkin
Given an existing document refers to a legacy folder name or a resolvable alias
When identity resolution runs
Then it returns the intended canonical epic deterministically
And terminal or deferred disposition remains attached to the correct folder
And an unresolved or ambiguous reference blocks resolution with no guessed link
```

### Scenario: The real project graph is collision-free

```gherkin
Given the typed identity registry and its repository-owned resolution seam are
active
When the real RaiSE graph is rebuilt from the canonical worktree
Then no duplicate canonical epic node ID is reported for E18 through E22
And the receipt proves all ten legacy folders are accounted for
And no folder rename is claimed unless link impact and rollback were proved
```

## Examples (Specification by Example)

| Input | Expected result |
|---|---|
| Accepted `complete` disposition with required evidence | Typed completed posture; normal evidence gates still apply |
| `Deferred/Backlog` | Known non-complete posture; never activation-eligible |
| `Superseded/Discarded` | Known terminal non-complete posture with successor/action evidence |
| `Paused Somehow` | Reject as unknown; no substring inference |
| Missing disposition field | Reject policy/record as incomplete |
| Two entries share a canonical ID or alias | Reject the identity registry |
| Legacy folder alias uniquely identifies one entry | Resolve to its canonical ID deterministically |
| Bare `E20` refers to two historical folders | Report ambiguity; never keep the first filesystem match |
| Real graph build after migration | Zero E18–E22 duplicate-node diagnostics and ten-folder coverage |

## Notes

- The existing ESCALA-001 repair remains valid evidence but is not the final
  architecture: `validators/epic_closure.py` currently owns a second vocabulary
  and must consume the new canonical contract.
- The prose-only `work/epics/legacy-disposition-index.md` remains useful human
  context; it cannot be the executable identity or closure authority.
- S36.4 may add the smallest repository-owned graph normalization/resolution
  seam required by the installed graph builder. It must not patch an external
  installation or hide collisions by filtering diagnostics.
- ESCALA remains local-only. No hosted runtime, remote publication, cloud
  database, telemetry, or automatic Drive/OneDrive synchronization is added.
