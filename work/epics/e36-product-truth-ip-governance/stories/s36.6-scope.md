# S36.6 Scope: Master Acceptance Ledger

## In Scope

- Define one canonical, versioned YAML ledger under E36 and one deterministic
  Markdown rendering for human review.
- Inventory the approved master-plan requirements for E37-E42 without treating
  old roadmap labels, plans, code presence, unchecked boxes, or historical
  completion claims as proof.
- Give every requirement a stable unique ID, owning epic/story, observable
  acceptance statement, evidence artifact, verification command, required
  gates, supported platforms, architecture classifications, state, and blocking
  reason when unproved.
- Reuse S36.4 canonical identity and closure-disposition contracts rather than
  defining competing notions of epic identity or completion.
- Bind the ledger to S36.5 local-only, legal, publication, and exact-artifact
  authority so downstream work cannot silently broaden the product into a
  hosted service or publish an unqualified artifact.
- Model fail-closed transitions: unknown, planned, in-progress, blocked,
  missing-evidence, stale-evidence, and failed-evidence states cannot satisfy a
  proved requirement.
- Require named evidence and gate receipts for every proved state, including
  source binding and platform scope where applicable.
- Validate cross-field architecture rules: runtime and authoritative data stay
  on the installer machine; Drive/OneDrive remain optional filesystem exchange;
  authoritative SQLite is never synchronized or shared.
- Provide deterministic owner/epic filtering and a safe CLI exit contract for
  later story/epic close gates.
- Add positive, negative, completeness, determinism, safe-output, and renderer
  parity tests; produce a fresh baseline receipt for all E37-E42 entries.

## Out of Scope

- Implementing ingestion, spreadsheet interpretation, cash/strategy/people/
  execution coaching, meeting analysis, cockpit dashboards, folder automation,
  installers, updaters, release channels, or any E37-E42 runtime behavior.
- Marking a requirement proved solely because a source file, test, plan,
  retrospective, roadmap row, or prior `DONE` label exists.
- Creating hosted APIs, SaaS, telemetry, cloud databases, Drive/OneDrive API
  integrations, OAuth, remote workers, or multi-writer/shared SQLite.
- Synchronizing authoritative SQLite or private canonical company state through
  a shared folder.
- Final legal approval, Windows qualification, public release, remote push,
  repository migration, or modification of the dirty public candidate.
- Building a general-purpose project-management or policy platform beyond the
  exact E37-E42 acceptance contract.

## Done When

- [ ] One strict schema validates the complete E37-E42 ledger and rejects
      missing, null, unknown, duplicate, ambiguous, or unsupported fields.
- [ ] Every approved master-plan requirement appears exactly once with a stable
      ID and one accountable epic/story owner.
- [ ] Acceptance statements are observable and evidence declarations name an
      artifact, verification command, gates, source binding, and platform scope.
- [ ] Status semantics fail closed and no plan, checkbox, code-presence claim,
      or historical label can independently produce `proved`.
- [ ] Local-only, local-data, synced-folder, SQLite, hosted-runtime, legal, and
      publication invariants are validated across applicable requirements.
- [ ] Canonical YAML and rendered Markdown preserve identical semantic content
      and render byte-identically across repeated runs.
- [ ] The safe CLI can validate all requirements or filter by epic/owner and
      emits only sorted bounded identifiers/rules, never private values or
      absolute machine paths.
- [ ] The initial baseline is truthful: future E37-E42 work remains unproved
      unless S36.6 creates fresh qualifying evidence for the exact requirement.
- [ ] A real repository-level baseline run passes schema/completeness checks and
      records all unproved blockers without claiming the future epics complete.
- [ ] Focused tests, lint, format, types, schema compatibility, architecture
      review, retrospective, and all story-close gates pass before local merge.

## Acceptance Evidence

- Canonical YAML ledger plus deterministic Markdown rendering.
- Strict typed models, validator, renderer, and safe CLI.
- Positive and negative contract tests for every state and invariant.
- Completeness receipt covering every E37-E42 requirement and owner.
- Determinism and safe-output receipts from the real repository baseline.
- RaiSE architecture-review and full-gate results.

## Constraints

- Run locally and deterministically without network access.
- Use Pydantic models and complete type annotations.
- Reuse canonical governance and public-export authorities by semantic hash or
  typed API; do not copy their vocabularies into a competing policy source.
- Keep evidence relative, bounded, sorted, source-bound, and non-sensitive.
- Default to unproved whenever evidence, platform coverage, gate status,
  authority binding, or state transition is incomplete or stale.
