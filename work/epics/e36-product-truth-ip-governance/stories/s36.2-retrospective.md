## Summary

S36.2 created a strict typed exposure policy, a deterministic local-only scanner
over six bounded Git/filesystem surfaces, a sanitized CLI, and live private and
public-candidate receipts. The implementation keeps scan completeness separate
from risk presence and proves non-mutation with strong before/after repository
fingerprints.

The live run found 2,126 classified exposures and zero scan errors. It also
reported 7 unscanned worktree contents and 8 unscanned `HEAD` contents, so the
review correctly refuses to claim the repositories are secret-free. No
credential-risk finding was emitted. Distribution remains fail-closed.

## What went well

- The design separated observation completeness, risk presence, and export
  eligibility. This prevented a complete scan with findings from being treated
  as a failed scanner or a clean repository.
- Reusing the S36.1 fingerprint boundary avoided duplicating Git-state logic and
  gave direct non-mutation proof for a dirty external candidate.
- Exact staging preserved the intentional raw-reference deletion outside all
  five implementation commits.
- Sentinel tests covered models, `repr`, JSON, Markdown, written files, stdout,
  stderr, authenticated remotes, inherited `GIT_*`, and unsafe exceptions.
- The live task exposed an operator-UX defect that fixture correctness alone did
  not reveal, and Jidoka stopped the task until it was fixed.

## What to improve

- The plan required concise Markdown but did not define a measurable volume or
  grouping contract. The first live artifact was correct yet unusable at
  359,376 bytes. Future evidence plans should set separate contracts for a full
  machine ledger and a bounded human summary before implementation.
- Design, plan, and implementation did not persist their expected learning
  `record.yaml` files. The review can report this gap but cannot reconstruct
  denominator-based lifecycle metrics with audit-grade certainty.
- The implementation-time identifier `guardrail-must-code-types-002` was a graph
  guardrail, not a pattern accepted by `rai pattern reinforce`. The framework
  should expose a stable mapping or distinguish reinforcible pattern IDs in
  PRIME output.
- Gate execution repeatedly generated an untracked `uv.lock`. It was inspected
  and removed each time, but the gate runner should avoid creating repository
  artifacts when lockfile ownership is outside the story.

## Heutagogical checkpoint

1. **What did I learn?** Deterministic serialization is not enough for usable
   evidence. The first receipt was byte-stable and safe but repeated 2,126
   records; the live run proved that machine completeness and human operability
   require different renderers.
2. **What would I change about the process?** Add an explicit live-artifact
   usability assertion to T3: group the human output, omit locators, and enforce
   a measured size/row ceiling before T4 touches real repositories.
3. **Framework improvements?** Make learning-record creation observable and
   fail-loud, and make PRIME return IDs that the reinforcement command accepts.
   These are framework-level changes, not safe S36.2 scope additions.
4. **What am I more capable of now?** I can inventory a deliberately dirty Git
   estate without conflating worktree, canonical commit, history, configuration,
   candidate, and generated-export state, while keeping sensitive values behind
   a typed non-serializable boundary.
