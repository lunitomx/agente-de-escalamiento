# Story: Reference Removal & Public Vocabulary Boundary

## User Story

As the ESCALA product owner and release operator,
I want the prohibited raw source removed from the canonical current tree and an
executable public-vocabulary boundary,
so that a future clean export presents ESCALA as our own locally operated
product without publishing book, author, methodology-source, private-training,
or derived-reference material.

## Acceptance Criteria

### Scenario: The raw source leaves the canonical current tree

```gherkin
Given the raw reference asset is deliberately absent from the S36.3 worktree
And S36.2 proved that the same path was still tracked in canonical HEAD
When S36.3 commits the deletion
Then the path is absent from the new canonical tree
And Git records an auditable deletion
And the receipt states that historical presence remains
And no destructive history rewrite is claimed or performed
```

### Scenario: Public product vocabulary is source-neutral

```gherkin
Given a file is explicitly eligible for future public distribution
When the public-vocabulary validator scans its path and bounded text
Then prohibited book, author, methodology-source, and attribution terms fail
closed
And the finding identifies a safe relative path and stable rule ID
And generic business concepts owned by ESCALA remain usable
```

### Scenario: Private derived material is denied, not silently published

```gherkin
Given a private training or derived-reference path contains useful concepts
When distribution classification is evaluated
Then the path is explicitly denied from public export
And its content is not copied into a public staging area
And a term match alone does not trigger indiscriminate deletion of private
business knowledge
```

### Scenario: Unknown public paths fail closed

```gherkin
Given a tracked path is neither explicitly public-eligible nor explicitly
private or denied
When public-boundary validation runs
Then the path is not inferred to be public
And validation cannot report release readiness
And S36.5 must later admit it through the clean-export manifest
```

### Scenario: Existing public candidate remains evidence-only

```gherkin
Given the existing public candidate has unrelated dirty work and known legacy
vocabulary findings
When S36.3 verifies the boundary
Then its strong before and after fingerprints remain identical
And its unresolved findings remain reported as candidate risk
And no clean-export or public-remediation claim is made for that repository
```

## Examples (Specification by Example)

| Input | Classification | Expected result |
|---|---|---|
| Raw PDF deleted in the S36.3 worktree | `raw_reference` | Commit deletion; current tree absent; history still present |
| Public-eligible README names a prohibited source or author | `public_vocabulary` | Reject with stable rule and safe relative path |
| Public-eligible skill uses generic cash, people, execution, or strategy language | `product_vocabulary` | Allow when no prohibited attribution/source term exists |
| Parsed workbook, board-persona, or book-knowledge path | `derived_reference` | Explicit public deny; preserve private state unless separately approved |
| Governance, work evidence, or company profile | `private_or_internal` | Explicit public deny |
| Unclassified new path | `unknown` | Fail closed; never infer public eligibility |
| Dirty legacy public candidate | `candidate_only` | Observe without mutation; keep its findings unresolved |

## Notes

- S36.3 changes the current canonical tree and executable public boundary; it
  does not rewrite historical Git objects.
- S36.5 owns the real clean-export manifest, license, notices, staging, and
  independent artifact verification. S36.3 supplies enforceable vocabulary and
  deny rules that S36.5 must consume.
- The existing public candidate is read-only evidence. Updating or publishing a
  remote repository is not authorized by this story.
- ESCALA remains local-only. No hosted runtime, cloud database, telemetry, or
  automatic repository synchronization is introduced.
