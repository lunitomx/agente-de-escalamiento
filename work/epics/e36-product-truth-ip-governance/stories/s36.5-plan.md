# S36.5 Plan: Clean Export, License & Third-Party Contract

## Overview

S36.5 is the E36 M3 integration checkpoint. Six risk-ordered TDD tasks produce
one strict local export contract, one immutable-commit builder, one independent
staged-filesystem verifier, safe operator CLIs, and a real double-build/tamper
receipt. Every task ends in one focused green commit.

The plan preserves the design boundaries:

- the existing public canary is not the allowlist;
- `validators/export.py` remains the action-plan validator;
- source bytes come from an explicit full Git `HEAD` commit, never the arbitrary
  worktree;
- technical PASS, human legal review, and publication authorization are
  separate states;
- the product runs locally and Drive/OneDrive remain ordinary filesystem
  sharing only; and
- no push, publication, history rewrite, public-candidate write, hosted runtime,
  or SQLite synchronization occurs.

PRIME and both JIT planning queries returned zero results. E36 classifies S36.5
as L and “not calibrated,” so estimates below are first-pass planning values;
actual duration is recorded task by task instead of being inferred from earlier
stories.

## Gate Policy

| When | Command | Scope |
|------|---------|-------|
| Per task | `rai gate check gate-tests --scope <test_dir>/` | Only tests for the changed module (e.g. `packages/raise-cli/tests/storage/`) |
| Per task | `rai gate check gate-lint` | Full project (fast) |
| Per task | `rai gate check gate-format` | Full project (fast) |
| Per task | `rai gate check gate-types` | Full project |
| End of story | `rai gate check gate-tests --scope packages/<pkg>/` | Changed package only — NOT full suite |
| MR creation | `/rai-mr-create` | Full suite — the ONLY place where unscoped tests run |

No test runner, linter, formatter, or type checker is invoked directly. All
automated verification goes through `rai gate check`. S36.5 has no isolated
`packages/<pkg>/` subtree; implementation therefore uses the concrete affected
test files below. The later RaiSE story-close phase owns repository-wide close
gates and architecture confirmation.

### Manual integration sequence

## Dependency graph and execution order

```text
T1 reusable scanners ───────────────┐
                                    ▼
T2 strict contracts -> T3 builder -> T4 verifier/local repair -> T5 CLIs -> T6 real M3
```

- T1 and T2 are logically independent, but T1 executes first because accidental
  semantic duplication is the earliest architecture risk and the commits share
  later test context.
- T3 cannot create files until T2 makes selection and metadata executable.
- T4 depends on both the scanner seams and a real builder fixture.
- T5 exposes only already-green core behavior.
- T6 must run from a clean committed T1–T5 source because the builder accepts a
  full immutable `HEAD`; evidence is committed only after observation.
- The graph is acyclic. No task is delegated or parallelized because the six
  tasks converge on one typed module and one owning test file.

## Risks and mitigations

| Risk | Mitigation and stop condition |
|---|---|
| Broad root silently includes tests/internal data | Exact files for mixed roots; bounded roots only when every descendant is portable; policy overlap tests |
| Builder and verifier share assumptions | Separate process entry points; verifier starts from `lstat` filesystem enumeration and never receives builder memory |
| Manifest self-reference breaks determinism | Manifest excludes itself; external receipt owns manifest hash |
| Existing public/exposure logic is copied | T1 public seams land first; no export commit may introduce competing term/regex tables |
| Worktree dirtiness changes artifact | Full current commit required; all source/policies read through Git objects; untracked/modified-file tests |
| “PASS” is mistaken for publication approval | Three typed states in policy, metadata, CLI, and M3; no publish command |
| Dependency inventory overclaims broad constraints | Store constraints and observed versions separately; legal review remains required |
| Runtime remote reference is misclassified | Artifact roles distinguish local runtime from docs/updater; explicit CDN/loopback/update tests |
| Real integration mutates dirty public candidate | Strong path-free fingerprint before/after; immediate failure on mismatch; no write-capable command targets it |
| Gate-generated files pollute commits | Inspect status after every gate; remove only known generated untracked `uv.lock`/`.coverage`; exact staging |

## Commit and staging discipline

- RED is observed before product GREEN for each task.
- Focused gates pass before each commit.
- Only files owned by the current task are staged exactly; ignored governance or
  work evidence uses `git add -f -- <exact paths>`.
- Existing unrelated dirty work is preserved. No reset, stash, clean, broad add,
  or destructive checkout is allowed.
- Generated `uv.lock`, `.coverage`, staging directories, and temporary receipts
  are never committed.
- One task equals one commit. If the real M3 exposes a product defect, repair it
  in a new explicit TDD task commit and rerun M3 from a new clean source commit.
