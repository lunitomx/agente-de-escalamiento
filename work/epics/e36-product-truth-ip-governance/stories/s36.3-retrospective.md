## What went well

- The deny-first model separated candidate-public, denied, and not-eligible
  paths. This allowed private training/reference material to remain useful
  without silently granting it distribution eligibility.
- T3 isolated the 91.6 MB raw-asset deletion in its own auditable commit, while
  reachable history stayed explicit instead of being described as clean.
- The T4 migration changed handler, routes, CLI, ontology IDs, relationships,
  dashboard/template paths, and callers atomically, with no prohibited public
  compatibility alias.
- T5 removed only the 78 root provenance blocks rather than thinning entire
  knowledge nodes. Formulas, relationships, questions, worksheets, and the
  four-area business behavior remained under regression coverage.
- The real worktree canary found seven tracked bytecode files that text searches
  would have missed. Jidoka stopped the task until every required candidate
  path was readable.
- Exact staging and public-repository fingerprints preserved unrelated dirty
  work and proved that no public-candidate repair or publication occurred.
- The failed close gate was treated as product-relevant evidence. A focused
  provenance test reproduced the hidden import selection before the repair,
  and the original full-suite surface proved the repair afterward.

## What to improve

- Binary/unreadable tracked artifacts should be inventoried before semantic
  text remediation. Discovering the seven bytecode files during the live
  canary was correct but later than necessary.
- T6 initially wrote its receipt inside the same whole-worktree fingerprint
  subject. The human output was stable, but the JSON worktree hash necessarily
  changed because the receipt became part of what it described. Future plans
  must prove determinism with outputs outside the subject root, then version
  one bounded receipt, or design an explicit evidence-path exclusion first.
- The original public-candidate baseline had 50 findings, while the completed
  stricter policy reports 209. The review confirms this is broader detection,
  not mutation, but future plans should anticipate that policy expansion makes
  raw finding counts non-comparable without a policy hash.
- Design, plan, and implementation again produced no lifecycle learning
  `record.yaml` files. Review can report the gap but cannot reconstruct
  denominator-based PRIME/JIT metrics with audit-grade certainty.
- Gate execution repeatedly creates an untracked `uv.lock`; it was inspected
  and removed before commits, but the gate runner should avoid generating an
  artifact whose ownership is outside the story.
- The initial review relied on individually passing importer gates and did not
  expose that a duplicate package name plus `sys.path` mutation made results
  order-dependent. Importer audits should assert `module.__file__` whenever a
  canonical and legacy tree expose the same package.

## Heutagogical checkpoint

1. **What did I learn?** A vocabulary search is not a public boundary. The
   seven tracked bytecode files and the 66 unclassified paths showed that
   readable content, path disposition, and semantic neutrality must all pass
   independently before a future export can even consider a file. T7 added a
   second lesson: a passing focused test does not prove implementation identity
   when duplicate package names and Python's module cache can change resolution.
2. **What would I change about the process?** Run the full candidate-path
   readability inventory immediately after the strict policy exists, before
   mass edits. For integration evidence, write first to a temporary path
   outside the fingerprint subject and only then version one source-bound
   receipt. Importer audits must also inspect path manipulation, assert module
   provenance, and retain one full-suite or import-order validation surface.
3. **Framework improvements?** Add an explicit receipt-output/fingerprint-root
   conflict check to review templates, make learning-record creation observable,
   stop the gate runner from producing unowned lockfiles, and make duplicate
   Python package provenance part of orphaned-importer review. These are
   framework improvements, not product changes to smuggle into S36.3 review.
4. **What am I more capable of now?** I can separate private knowledge
   retention, candidate-public vocabulary, unknown-path fail-closure, current
   tree truth, reachable history, and a dirty external candidate while keeping
   evidence deterministic and free of matched values, roots, URLs, and raw
   errors. I can also diagnose order-dependent module-cache contamination
   without reintroducing prohibited legacy vocabulary into product code.
