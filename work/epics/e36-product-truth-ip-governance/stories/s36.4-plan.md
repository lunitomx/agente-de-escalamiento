# S36.4 Plan: Typed Governance Taxonomy & Unique Epic IDs

## Overview

S36.4 replaces the duplicated in-code closure semantics with one strict typed
policy and migrates all ten colliding E18–E22 epic folders to unique canonical
IDs. The installed RaiSE parser derives IDs from folder prefixes, so the folder
migration and identity registry must land atomically. Five green task commits
keep the closure contract, consumer migration, filesystem identity, receipts,
and real graph integration independently recoverable.

The story remains M by epic estimate but is complex by component count and
integration risk. No reliable story-plan calibration record exists. Local E36
actuals range from 47m32s for S36.2 to 1h53m12s for S36.3; this plan records
actual duration per task instead of inventing a calendar promise.

| Per task | `rai gate check gate-tests --scope <test_dir>/` | Only tests for the changed module (e.g. `packages/raise-cli/tests/storage/`) |
| Per task | `rai gate check gate-lint` | Full project (fast) |

| MR creation | `/rai-mr-create` | Full suite — the ONLY place where unscoped tests run |

### Repository-specific concrete scopes

This repository is a root Python package rather than `packages/<pkg>/`. The
concrete changed-module gates are:

```bash
.venv/bin/rai gate check gate-tests --scope tests/test_governance_contract.py
.venv/bin/rai gate check gate-tests --scope tests/test_epic_closure_governance.py
```

Never run pytest, Ruff, or Pyright directly. All validation flows through RaiSE
gates. A RED observation is recorded but not committed; each task commit lands
only after GREEN plus lint, format, and type gates.

## Execution order and dependency graph

```text
T1 typed disposition policy
  └──► T2 closure consumer migration
         └──► T3 identity policy + atomic ten-folder migration
                └──► T4 safe CLI and deterministic receipts
                       └──► T5 real graph integration and final evidence
```

The order is strictly sequential. T1 removes semantic ambiguity before the
consumer changes. T2 proves the safe facade before paths move. T3 owns every
identity/path mutation in one rollback boundary. T4 binds evidence only after
the canonical tree exists. T5 validates the actual integration without mixing
source repair into evidence capture.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| YAML becomes a third semantic copy | Disposition IDs stay data-driven; Python validates structure/invariants only |
| Temporary tests stop being repository-real | Every temporary root installs the canonical policy; writer and actual validator run together |
| Half of the directories move | Preflight all sources/destinations; ten moves and current reference updates share one uncommitted T3 transaction |
| Bare E18–E22 silently select one epic | Both members receive new IDs; bare values exist only in declared ambiguity sets |
| Historical evidence is rewritten | S36.2/E29/E32/E33/E34/E35 and completed retrospectives retain old path observations |
| Current operational paths remain stale | Exact current consumers/indexes are listed in T3; residual grep matches require explicit classification |
| Graph unit tests pass but real tool still drops a node | Installed `rai graph build --strict --no-diff` is a required T3 and T5 integration gate |
| Graph build mutates the global RaiSE index | Run only from the canonical worktree once migration is green; verify current branch/repo before each build |
| Receipt fingerprints itself | Determinism is proved outside the subject root; evidence paths are excluded from the identity inventory |
| Gate creates `uv.lock` or `.coverage` | Inspect and remove/quarantine generated artifacts before exact staging |
| Public or hosted scope leaks in | No remote/public candidate command, network dependency, SaaS, cloud DB, or synced SQLite path exists in any task |
