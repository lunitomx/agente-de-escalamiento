## Summary

S36.4 replaced competing closure semantics with one strict versioned YAML
policy, migrated the existing closure validator to that policy without breaking
its two public list-returning facades, and gave all ten colliding E18–E22 epic
folders unique E1801–E2202 identities. Both members of every collision were
renumbered, so bare legacy numeric references cannot silently privilege one
folder.

The story also introduced a strict identity registry and resolver, migrated
current operational paths while preserving historical observations, and added
deterministic sanitized JSON/Markdown receipts. The real installed graph—not a
mock parser—proved the repository identity migration.

## What went well

- The installed parser's real folder-prefix behavior was discovered before the
  migration, preventing a frontmatter-only repair that would have left the
  graph broken.
- Renumbering both members of each collision made legacy ambiguity stable and
  fail-closed instead of choosing the first enumerated directory.
- T3 kept ten folder moves and their operational references in one auditable
  Git transaction while historical evidence stayed unchanged.
- The policy is the semantic authority: Python validates invariants but does
  not reproduce the eight disposition IDs as another enum or table.
- Public facades return one fixed safe error while strict loaders retain typed
  diagnostic behavior internally.
- The versioned receipt is bound to the preceding green source commit, and
  separate post-commit runs prove byte determinism without claiming an
  impossible self-hash.
- Exact staging and explicit boundaries avoided installed-package patches,
  external repository changes, database mutations, pushes, and publication.

## What to improve

- The design's Python example used `status` and `canonical_ids`, while the
  implemented result uses `code` and `candidates`. Review corrected it, but
  executable examples or doctest-style validation would expose this drift
  earlier.
- The design's regression row originally said “full tests” without stating that
  the full suite belongs to story close. The implementation plan was correct;
  the design wording is now aligned.
- Design, plan, and implementation again produced no lifecycle learning
  `record.yaml` files. Review cannot reconstruct denominator-based PRIME/JIT
  metrics with audit-grade certainty.
- The session-filtered implement-signal query returned empty because
  `RAISE_CC_SESSION_ID` is unset, although the latest unfiltered signal matched
  the current `HEAD`. The workflow should provide a documented authoritative
  fallback instead of making a valid implementation look absent.
- RaiSE commands continue to generate an untracked `uv.lock`; it was inspected
  and removed before review staging, but artifact ownership should be fixed in
  the runner.

## Heutagogical checkpoint

1. **What did I learn?** Repository identity is executable filesystem state
   when the installed parser derives IDs from folder prefixes. Frontmatter,
   aliases, and unit tests cannot compensate for a colliding real tree. I also
   learned that binding a receipt to its own commit is structurally impossible;
   source binding and post-commit determinism must be separate proofs.
2. **What would I change about the process?** Probe the actual installed parser
   before finalizing an identity design, then plan the entire collision set as
   one rollback boundary. Treat code examples in design artifacts as executable
   contracts and verify them during implementation or review.
3. **Framework improvements?** Persist lifecycle learning records reliably,
   document the implement-signal fallback when the session environment variable
   is absent, validate design API snippets, and stop gates from producing
   unowned lockfiles.
4. **What am I more capable of now?** I can migrate a collision-heavy governance
   graph without deleting legacy work, rewriting history, patching the installed
   tool, leaking private paths, or allowing ambiguous references to resolve by
   enumeration order.
