# S36.6: Master Acceptance Ledger

## User Story

As the product owner executing the ESCALA Local V2 master plan,
I want every requirement assigned to E37-E42 represented in one strict,
machine-readable acceptance ledger,
so that planned work cannot be mistaken for working product and every future
completion claim can be traced to real local evidence.

## Business Outcome

The ledger becomes the control plane for the rest of the mission. It answers,
for every requirement: who owns it, what observable behavior must exist, what
artifact proves it, which command verifies it, which gates apply, on which
operating systems it must work, and whether the current state is genuinely
proved. It preserves the architectural decision that ESCALA runs only on the
installer's machine and that Drive or OneDrive are optional filesystem folders,
never hosted ESCALA infrastructure or a location for authoritative SQLite.

## Acceptance Criteria

### AC1 — Complete, unique requirement inventory

Given the approved master-plan scope for E37-E42
When the ledger validator loads the canonical ledger
Then every requirement has one unique stable ID, one owning epic and story,
one observable acceptance statement, and one explicit current state
And missing, duplicate, unknown, or cross-epic ownership fails closed.

### AC2 — Evidence-backed state transitions

Given a requirement whose implementation is only planned or documented
When its state is evaluated
Then it cannot be reported as proved or complete
And a proved state requires the named evidence artifact, verification command,
required gate receipts, and a successful result bound to the expected source.

### AC3 — Local-only invariants are executable

Given any E37-E42 requirement that handles runtime, company data, ingestion,
team exchange, automation, installation, or distribution
When the ledger is validated
Then its no-host and local-data classifications are explicit
And no requirement may imply SaaS, hosted APIs, cloud databases, OAuth,
Drive/OneDrive APIs, shared SQLite, or synchronized authoritative SQLite.

### AC4 — Human and machine views agree

Given the canonical machine-readable ledger
When the deterministic renderer is executed twice
Then both rendered Markdown outputs are byte-identical
And the human view preserves every requirement ID, owner, state, evidence,
gate, platform, and blocking reason without private values or machine paths.

### AC5 — Truthful initial baseline

Given existing code, plans, tests, and historical completion claims
When E37-E42 are baselined
Then no requirement is promoted from unproved merely because code or a plan
exists
And any currently proved requirement is supported by fresh, named evidence
generated during S36.6 or remains explicitly unproved.

### AC6 — Usable downstream gate

Given a future E37-E42 story or epic close
When the acceptance verifier is run for that owner
Then it returns deterministic PASS only for fully evidenced requirements
And otherwise returns bounded, sorted, non-sensitive blocking findings with a
non-zero exit code.

## Examples

### Example: plan is not proof

Given `REQ-E39-004` names a planned meeting-analysis capability
And its design document exists but no behavioral receipt exists
When the validator evaluates it
Then the state remains `unproved`
And the result includes `evidence.missing` rather than `complete`.

### Example: synced team folder remains ordinary storage

Given a requirement allows team files in a local Google Drive or OneDrive mount
When its architecture classifications are validated
Then `runtime_authority` is `installer_machine`
And `exchange_mode` is `filesystem_folder`
And `sqlite_sync_allowed` is `false`.

### Example: future evidence qualifies a requirement

Given an E41 installer requirement names macOS and Windows
And both platform receipts exist and pass their declared verification commands
When the verifier evaluates the requirement
Then and only then may its state be `proved`.

## Non-Functional Requirements

- Strict Pydantic models and complete type annotations at every boundary.
- Supported schema version and stable lowercase serialized enums.
- Deterministic ordering, rendering, findings, and safe CLI output.
- Local execution with no network, cloud service, or external publication.
- No absolute paths, remote URLs, company data, credentials, or raw command
  payloads in versioned evidence.
- Focused positive and negative tests plus full RaiSE close gates.

## Dependencies

- S36.4 closure and canonical epic-identity contracts.
- S36.5 clean-export, local-only, legal, and publication contracts.
- E36 mission, brief, design, scope, and approved product-owner requirements.

## Exclusions

- Implementing any E37-E42 product capability.
- Claiming Windows support, legal approval, release readiness, or publication.
- Introducing hosted ESCALA infrastructure or cloud data authority.
- Automatically mutating backlog, remote repositories, or external systems.
