# S47.3 — Diseño: OPSP completo y coherente

## Problema y valor

El modelo actual sólo conserva ocho strings estratégicos. No representa las
celdas del OPSP, sus filas Actions/Goals/Targets, la accountability por persona
ni las Key Capabilities de 3–5 años. Además, las fuentes instaladas contradicen
el rango de columnas de ejecución y las skills prometen rutas y guardado que no
existen.

La corrección permite mostrar un plan estructurado y honesto: cada dato
faltante queda pendiente, con una pregunta concreta, sin suponer información de
la empresa.

## Gemba y complejidad

Complejidad moderada: un contrato Pydantic existente, su constructor, pruebas y
tres representaciones de conocimiento. No hay UI, almacenamiento ni dependencia
externa nueva.

- `StrategyPlan` y `build_strategy_plan` son el único modelo/contructor
  existente; se extienden en vez de crear una V2 paralela.
- `WorksheetDAO` ya ofrece persistencia versionada, pero queda fuera de esta
  historia y será consumidor de S47.4.
- No existe una plantilla OPSP materializada; las skills referencian rutas
  inexistentes.
- No hay `governance/drift-hotspots.json`. Riesgo AG2: deriva entre código,
  YAML y mirrors; riesgo AG4: nueve archivos, contenido acotado sin storage.

## Enfoque y decisiones

Se amplía `StrategyPlan` con un esquema anidado de siete columnas y tres
filas (`Actions`, `Goals`, `Targets`). Cada celda conserva estado y
pregunta, y las responsabilidades se identifican por persona. Los ocho campos
existentes siguen como una proyección compatible para E40.

- S47.3-D1: extender `StrategyPlan`, no introducir un modelo V2.
- S47.3-D2: faltantes explícitos; una celda vacía nunca autoriza inferencia.
- S47.3-D3: columnas 1–3 son estrategia y 4–7 ejecución; la misma regla vive
  en ambos YAML y las tres skills.
- S47.3-D4: no persistir ni exportar en esta historia; S47.4 toma esa frontera.

No se agregan dependencias. El V1 no queda huérfano: `StrategyPlan` se
amplía compatible porque E40 consume sus propiedades actuales.

## Ejemplos

```python
plan = build_strategy_plan((

assert plan.status == "needs_clarification"
assert "key_capabilities" in plan.unresolved
```

## Criterios de aceptación

- [ ] AC-1: el modelo expone exactamente siete columnas y las filas
  Actions/Goals/Targets.
- [ ] AC-2: incluye accountability por persona y Key Capabilities a 3–5 años
  con validación de límites.
- [ ] AC-3: input parcial produce pendientes y preguntas explícitas, sin
  valores inventados.
- [ ] AC-4: ambos YAML y los tres mirrors de la skill declaran la misma
  semántica de ejecución.
- [ ] AC-5: no se escribe estado local ni se agrega `raise-cli` como
  dependencia de producto.

## Estrategia de pruebas

Pruebas unitarias validan modelo completo, parcial e inválido; pruebas de
recursos evitan referencias inexistentes y contradicciones de columnas. La
aceptación humana de una página renderizada queda explícitamente para S47.4.
