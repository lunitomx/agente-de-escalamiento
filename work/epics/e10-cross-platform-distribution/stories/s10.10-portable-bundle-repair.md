# S10.10 — Reparación del bundle portable

## Problema verificado

Antes de esta reparación, el instalador público publicaba sólo un enlace al
checkout y el ZIP de `escala_server.lifecycle` no incluía catálogo, capacidades
ni conocimiento. S10.10 los separó: el ZIP sigue siendo lifecycle, mientras
`build_public_export` genera el bundle conversacional completo y verificable.

## Resultado de producto

Una persona puede extraer un bundle local, ejecutar su instalador y usar la
única puerta pública `escala` en Codex, Claude Code o Hermes aunque el checkout
fuente ya no exista. Las 62 capacidades internas permanecen instaladas como
recursos privados del orquestador: no aparecen como comandos para el
empresario.

## Alcance

- Crear un build determinista que incluya únicamente los componentes locales
  permitidos: orquestador, catálogo, capacidades internas, conocimiento
  permitido, motores Python necesarios y metadatos de versión/procedencia.
- Instalar el bundle bajo una raíz local de ESCALA, no mediante enlaces al
  checkout de desarrollo.
- Publicar sólo el enlace de la puerta `escala` hacia la copia instalada; el
  enlace debe resolver catálogo y capacidades relativas dentro de esa copia.
- Conservar adaptadores mínimos por plataforma sin mezclar sus instrucciones
  en el núcleo portable.
- Validar actualización idempotente, rollback/safe-stop y que el estado de la
  empresa no se sobrescribe.
- Añadir pruebas de instalación aislada: construir, instalar, retirar/renombrar
  el checkout fuente y verificar rutas, catálogo, una ruta por dominio y el
  rechazo seguro de bundle corrupto.
- Actualizar la guía de instalación para distinguir el runtime lifecycle del
  bundle conversacional completo.

## Fuera de alcance

- Publicación comercial, firma/notarización, OAuth, hosting o sincronización
  de SQLite.
- E67: adaptación semántica de los seis procedimientos MVP futuros y generación
  de especialistas desde su contrato común.
- E68: evaluación con modelos reales Codex/Claude y paridad semántica.
- Incluir fuentes protegidas, corpus privado o datos de empresas en el bundle.

## Diseño

```text
build portable bundle
  ├─ core/escala-skills/       catálogo + puerta + capacidades internas
  ├─ core/conocimiento/        sólo conocimiento permitido y relativo
  ├─ core/python/              paquetes locales necesarios para ejecución
  ├─ manifest.json             hashes, versión, procedencia y lista permitida
  └─ installers/               adaptadores Codex / Claude / Hermes

install
  ├─ staging bajo raíz local del usuario
  ├─ validar manifest, hashes y catálogo antes de activar
  ├─ swap atómico de recursos instalados
  ├─ enlazar sólo <platform>/skills/escala → bundle/escala-skills/escala
  └─ conservar data/ y SQLite fuera del bundle y de carpetas sincronizadas
```

La copia instalada se convierte en la raíz de recursos. Ninguna ruta de una
capacidad puede resolver al checkout de construcción. Si una dependencia no
puede empaquetarse de forma lícita o portable, el build falla antes de generar
el artefacto.

## Criterios de aceptación

1. El bundle no contiene `.git`, `work/`, pruebas, fuentes privadas ni datos de
   empresa, y su manifest cubre cada archivo incluido.
2. Tras instalar y retirar el checkout fuente, `escala/SKILL.md` resuelve
   `catalog.yaml` y cada capacidad declarada sin path absoluto ni symlink roto.
3. La instalación muestra exactamente una puerta pública y no publica las
   capacidades internas como comandos.
4. Una actualización inválida no cambia la versión activa ni los datos locales;
   una actualización válida es idempotente y deja recibo redactado.
5. Las pruebas cubren caso positivo y negativo en cada adaptador de plataforma;
   el resultado de hardware limpio sigue siendo gate de E42/E68, no se finge.
6. La documentación para empresario describe pasos, requisitos, límites y
   desinstalación sin pedirle editar rutas internas.

## Evidencia de cierre local

- `tests/test_public_skill_installation.py` construye el artefacto desde Git,
  instala la única puerta en Claude, Hermes y Codex, conserva la versión activa
  ante un candidato corrupto y verifica una actualización idempotente.
- El mismo caso importa los módulos `coaching.*` desde una carpeta limpia
  mediante `scripts/escala-python`, sin checkout ni directorios de pruebas.
- `scripts/verify_portable_bundle.py` sigue fail-closed: cualquier archivo que
  no esté en el manifiesto bloquea la activación.
- E42/E68 conservan exclusivamente la evaluación externa de hardware/modelos.

## Reparación posterior — CLI documentado

La auditoría de E75 detectó que el constructor mantenía la validación interna
correcta de repositorio absoluto, pero el CLI pasaba `--repo .` sin normalizarlo,
aunque ésa es la forma documentada. El commit `5f03708` normaliza sólo el
argumento del CLI antes de entrar al validador estricto y añade una prueba
e2e. Un export aislado del commit actual construyó 347 archivos, verificó el
manifest independientemente y ejecutó el diagnóstico narrativo sin checkout.
Esta reparación no sustituye E42/E68 ni la revisión legal/humana.

## Evidencia y handoff

- El recibo reproducible de build/instalación aislada y la prueba de fuente
  retirada viven en `tests/test_public_skill_installation.py`.
- E42 consume la instalación real para REQ-E42-001..005.
- E67 amplía este envoltorio para los procedimientos generados desde E65; no lo
  reemplaza ni vuelve a introducir enlaces al checkout.
- E68 y E70 consumen el mismo artefacto, no una variante de desarrollo.
