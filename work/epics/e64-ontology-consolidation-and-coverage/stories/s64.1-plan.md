# S64.1 — Normalización y aliases: plan TDD

## Objetivo y frontera

Entregar un `CanonicalRelease` S64.1 estricto y determinista, generado
**unidireccionalmente** desde una proyección saneada de las colas privadas y
recibos ya autorizados de E59–E63. La proyección sólo puede llevar metadata
permitida: `candidate_id`, `source_ids`, `kind`, `canonical_name`, `origin`,
aliases, outcome de revisión independiente y referencias/digests opacos de
candidato, revisión y recibos aplicables. No puede copiar `working_text`,
texto fuente, unidades/locators, URLs, rutas absolutas, corpus ni claves no
conocidas.

`ReviewQueue` sigue siendo privado y no promueve conocimiento por sí mismo.
La entrada `approve-candidate` sólo es admisible tras validarse la independencia
extractor/reviewer ya impuesta por el contrato existente y tras validar la
proyección autorizada. Los candidatos E63 Cash con `needs-revision`, dependencia
externa o estado `blocked`/`source-bounded` se registran una única vez como
exclusión/revisión requerida; no se convierten en nodo. La story no produce
vistas YAML/SQLite, no modifica `OntologyDocument`, schema/vocabulary/cola
v2, ni declara cobertura, integridad, fidelidad, S64.4 o readiness de E65.

El worktree distribuible no contiene las colas ni recibos privados. Por tanto,
la construcción debe rechazar la ausencia de una proyección autorizada y no
emitir una release vacía. El conteo real se fija sólo después de obtener la
proyección autorizada: las pruebas del artefacto versionado deberán fijar los
conteos literales de `nodes` y `exclusions`, y verificar que cada candidate ID
de la proyección aparece exactamente en uno de ambos conjuntos. No se inventa
ningún conteo a partir de scopes, tests ni fuentes ignoradas.

## Tareas ordenadas (riesgo primero)

### 1. Frontera de proyección saneada y admisión independiente

**Tamaño:** S. **Dependencias:** ninguna. **Commit previsto:**
`test(s64.1): specify sanitized authorized candidate projection`.

**Archivos:** modificar `validators/ontology_v2.py` y
`tests/test_ontology_v2.py`.

**RED:** añadir fixtures de una proyección autorizada mínima y tests que
fallen si faltan `candidate_id`, `source_ids`, digest/recibo opaco o decisión;
si la decisión no es `approve-candidate`; si el reviewer no es independiente;
o si llegan `working_text`, `locators`, `source_url`, texto fuente, rutas
absolutas o una clave desconocida. Añadir casos que preserven IDs de candidato,
IDs de fuente y digests sin exponer unidades privadas.

**GREEN:** incorporar un modelo/adaptador estricto de entrada (`extra=forbid`)
que acepte únicamente el subconjunto permitido de una proyección autorizada,
valide IDs y referencias opacas, y compruebe el outcome independiente contra
los contratos existentes de `ReviewQueue`/`ReviewDecision`. Debe fallar cerrado
si falta la proyección autorizada; no debe leer rutas E6/E56 ni fuentes crudas.

**REFACTOR:** centralizar el allowlist y las validaciones de identificadores
opacos para que el constructor posterior no pueda reconstruir campos privados.

**AC:** escenarios “Registrar un candidato admisible” y guardrails de
procedencia/privacidad.

**Verificación:**

```bash

rai gate check gate-lint
rai gate check gate-format
rai gate check gate-types
```

### 2. Contrato `CanonicalRelease` y serialización determinista

**Tamaño:** M. **Dependencias:** tarea 1. **Commit previsto:**
`feat(s64.1): add strict canonical release contract`.

**Archivos:** modificar `validators/ontology_v2.py` y
`tests/test_ontology_v2.py`.

**RED:** especificar nodos y exclusiones válidos; rechazar IDs de nodo o
candidato duplicados, alias duplicados (dentro o entre nodos), alias que no
pertenece a un nodo, `source_ids` vacíos, digest/recibo faltante, una exclusión

unicidad y exclusividad nodo/exclusión; normalizar sólo orden determinista, no
contenido ni conflictos de evidencia.

**REFACTOR:** compartir las primitivas de validación/orden con la entrada de la
tarea 1 sin cambiar `OntologyDocument`, `ontology_views.py`,
`schema.json`, `vocabulary.yaml` ni `review-queue.json`.

**AC:** escenarios “Registrar un candidato admisible” y “Conservar diferencias

### 3. Constructor de una sola dirección y política explícita de exclusiones

**Tamaño:** M. **Dependencias:** tareas 1–2. **Commit previsto:**
`feat(s64.1): build release from authorized projection`.

**Archivos:** modificar `validators/ontology_v2.py` y
`tests/test_ontology_v2.py`.

**RED:** desde fixtures de proyección permitida, probar que un candidato con
`approve-candidate` independiente y precondiciones de recibo válidas genera un
único nodo estable con aliases, `source_ids` y referencias opacas distintas;
que dos recibos distintos no se fusionan; y que genérico, `needs-revision`,
`reject-candidate`, recibo ausente/inválido y E63 Cash
`external-content-source-bounded`/`blocked` salen exactamente una vez a
`exclusions` con `disposition` y `reason_code`, sin `canonical_id`. Probar que
no hay entrada de cola privada autorizada o que una proyección faltante aborta,
en vez de producir un JSON vacío o afirmar cobertura.

**GREEN:** implementar un único builder que consuma el adaptador saneado y
emita sólo `CanonicalRelease`. La elegibilidad debe ser una política explícita
sobre outcome, independencia y flags/recibos ya reducidos en la proyección;
no una heurística sobre nombres ni una lectura de `working_text`. Preservar
candidate IDs, source IDs y digests; no copiar ni dereferenciar corpus,
locators o paths. Todo input llega a nodo o exclusión, nunca ambos ni ninguno.

**REFACTOR:** exponer un recibo de construcción limitado a conteos y
reason-codes, con errores que mencionen IDs/reason-codes seguros y no
contenido privado.

**AC:** escenarios “Excluir candidatos no promocionables” y “Proteger
conocimiento externo de Cash bloqueado”.

**Verificación:**


## Orden y dependencias

`T1 -> T2 -> T3 -> T4 -> T5`. El orden es acíclico y deliberadamente
riesgo-primero: primero se bloquea la fuga desde la cola privada, después se
blinda el contrato/bytes, luego se aplica la política de promoción/exclusión y
sólo entonces se materializa el artefacto autorizado. T4 no puede iniciarse
sin la proyección autorizada; esa falta es un bloqueo de entrada, no permiso
para fabricar una release de conteo cero.

## Riesgos y mitigaciones

| Riesgo | Mitigación verificable |
|---|---|
| Fuga de corpus, `working_text`, locator o path | Allowlist estricto, `extra=forbid`, payloads adversariales y comprobación de bytes del JSON. |
| `approve-candidate` confundido con promoción directa | Adaptador que exige decisión independiente y builder explícito; tests de outcomes no promovibles. |
| Cash E63 se publica accidentalmente | Política de exclusión para `needs-revision`, externo, `blocked` y `source-bounded`; pruebas sin nodo Cash. |
| Release no reproducible | Orden canónico, renderer/cargador y comparación byte a byte. |
| Se pierde o migra legado E6/E56 | Prueba de coexistencia de mapa E6 y prohibición de lectura/promoción de legacy. |
| No existe insumo autorizado en el worktree | Fallo cerrado; T4/T5 se bloquean sin generar release ni cambiar estados. |
