# S64.2 — plan TDD

## Frontera

Sólo se validan `CanonicalRelease` y un manifiesto S64.2 seguro y opcional.
No se leen proyecciones/colas privadas, corpus, locators, archivos E6/E56 ni
se modifica S64.1. Sin manifiesto, el resultado es disponibilidad explícita
de relaciones, no una inferencia ni un green semántico.

## Tareas

### T1 — Especificar contratos adversariales

**RED.** Crear `tests/test_canonical_release_integrity.py` con un release
mínimo y manifest seguro. Cubrir relación con nodo desconocido, arista
duplicada, tipo inseguro, contrato duplicado, herramienta sin decisión,
decisión inexistente/no `decision-area`, regla sin evidencia, métrica sin
definición o unidad, y campos privados extras.

### T2 — Modelos y validador fail-closed

**GREEN.** Añadir contratos estrictos y
`validate_canonical_release_integrity` en `validators/ontology_v2.py`. Usar
únicamente IDs y referencias opacas. Devolver un receipt con conteos y
`relations_state`; no imprimir labels o fuente.

### T3 — CLI y release actual

**GREEN.** Añadir `scripts/check_canonical_release_integrity.py`, probar
salida segura y comprobar el release real S64.1 sin manifest:
`status=not-assessed`, `relations_state=no-relations-published` y salida
no-cero, sin afirmación de completitud de grafo. El script debe rechazar
cualquier manifest corrupto.

### T4 — Revisión y gates

Ejecutar pruebas focales con el Python compartido, Ruff, formato y Pyright
focal. Revisar diff para confirmar que no se tocó S64.1 ni se agregó material
privado. Documentar cualquier limitación: no hay relaciones publicadas, por
lo que la semántica tool→decision no puede certificarse hasta que exista un
manifiesto autorizado.
