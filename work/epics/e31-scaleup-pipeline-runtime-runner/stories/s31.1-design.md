# S31.1 Design: Guided ScaleUp Pipeline Runner

## Complexity
Moderate. The story touches a new runtime module, tests, and project dependencies, but it reuses the existing registry contract and avoids a generic engine.

## Gemba Findings
- `.raise/pipelines/scaleup.yaml` is the canonical pipeline registry.
- `validators/pipelines.py` already validates required pipeline, phase, gate, and skill-reference structure.
- `tests/test_pipeline_registry.py` imports validator modules by file path, which is the current local test pattern for root-level validators.
- There is no existing runner, evidence serializer, or CLI for pipeline execution.

## Problem
The ScaleUp pipeline registry is valid but passive. Operators can see that pipelines exist only by reading YAML or tests; there is no guided way to list, inspect, or record execution evidence.

## Value
The first runner makes the registry operational while preserving human review gates. It gives session close and later audits a deterministic evidence file instead of chat-only execution memory.

## Approach
Create `validators/pipeline_runner.py` as a small typed runtime companion to the existing registry validator. It will load YAML into Pydantic models, expose list/detail helpers, and provide a guided run function that records phase review, gate decisions, stop conditions, and final state.

This is not a full execution engine. It does not invoke skills automatically; it records the guided workflow state and leaves substantive work to existing `scaleup-*` skills.

## Components
| Component | Change | Purpose |
|-----------|--------|---------|
| `validators/pipeline_runner.py` | create | Typed loader, list/inspect helpers, guided evidence writer, minimal CLI |
| `tests/test_pipeline_runner.py` | create | TDD coverage for list, inspect, unknown pipeline, stopped run, evidence output |
| `pyproject.toml` | modify | Declare `pydantic` because runtime models import it |

## Decisions
- **D1: New runner module, existing validator untouched.** Validation and runtime evidence are different responsibilities; extending `validators/pipelines.py` would blur concerns.
- **D2: Pydantic models for registry/runtime state.** Project guardrails require typed structures with boundary validation; Pydantic gives clear errors for malformed registry data.
- **D3: Evidence as YAML.** YAML matches existing project artifacts and is readable during session close or audit.
- **D4: Guided run only.** The runner records decisions and stop/completion state; automatic skill execution is deferred until real usage proves the need.

## Legacy Sweep
Nothing becomes orphaned. This is net-new runtime capability over an existing declarative registry and validator.

## Drift Risk
- **AG2 clone amplification:** Low. YAML loading is new, but validation remains in `validators/pipelines.py`; tests guard against diverging from registry shape.
- **AG4 context-window planning:** Low to moderate. The first implementation touches three files only and avoids modifying ScaleUp skills.
- `governance/drift-hotspots.json` was not present in the gemba path, so no hotspot rank was applied.

## Storage and Error Contracts
This story does not replace a storage mechanism. New evidence writes are explicit: unknown pipeline requests raise a clear error and do not write success evidence; stopped runs write `state: stopped`.

## Supply Chain
`pydantic` is a well-known package and is already available in the local Python environments. It will be added to `pyproject.toml` so the dependency is explicit.

## Examples

### List Pipelines
```bash
python validators/pipeline_runner.py list --registry .raise/pipelines/scaleup.yaml
```

Expected output includes lines such as:
```text
scaleup-session-start | phases=4 | entrypoint=scaleup-start | Load company context and propose the best session focus.
```

### Inspect Pipeline
```bash
python validators/pipeline_runner.py inspect scaleup-cash-acceleration-system --registry .raise/pipelines/scaleup.yaml
```

Expected output includes phases, gates, stop conditions, outputs, and evidence fields in registry order.

### Guided Evidence
```bash
python validators/pipeline_runner.py run scaleup-execution-system --evidence-out work/runs/scaleup-execution.yaml --stop "User cannot assign accountability."
```

Expected evidence:
```yaml
pipeline_id: scaleup-execution-system
state: stopped
stopped_reason: User cannot assign accountability.
```

## Acceptance Criteria
- **MUST:** List all pipelines with id, intent, phase count, and entrypoint.
- **MUST:** Inspect one pipeline with phases, gates, stop conditions, outputs, and evidence fields.
- **MUST:** Write guided run evidence for completed and stopped states.
- **MUST:** Reject unknown pipeline ids without writing misleading success evidence.
- **MUST:** Cover list, inspect, unknown id, stopped run, and evidence serialization in tests.
- **MUST NOT:** Automatically execute `scaleup-*` skills in this story.
- **SHOULD:** Keep the module small enough that S31.2 can harden resume/evidence without undoing S31.1.

## Testing Strategy
| Layer | Test | Purpose |
|-------|------|---------|
| Unit | `tests/test_pipeline_runner.py::test_list_pipeline_summaries` | Registry listing behavior |
| Unit | `test_inspect_pipeline_includes_details` | Detail view includes phases/gates/stops |
| Unit | `test_unknown_pipeline_does_not_write_evidence` | Error path does not create false evidence |
| Unit | `test_guided_run_writes_stopped_evidence` | Stop condition evidence |
| Unit | `test_guided_run_writes_completed_evidence` | Completed evidence |

## Open Questions
- Whether S31.2 should add resume semantics or keep evidence append-only.
- Whether a future story should expose the runner as a first-class `scaleup-*` skill command.
