# S31.1 Plan: Guided ScaleUp Pipeline Runner

## Overview
Implement the first lightweight runner for `.raise/pipelines/scaleup.yaml`: list pipelines, inspect details, and write guided run evidence for completed/stopped states.

## Ordered Tasks

### Task 1 — RED: Runner behavior tests
- **Size:** S
- **Files:** create `tests/test_pipeline_runner.py`
- **TDD:** Write failing tests for list summaries, inspect details, unknown pipeline, stopped evidence, completed evidence.
- **AC:** List, inspect, unknown pipeline, stopped run, evidence serialization.
- **Verification:**
  - `rai gate check gate-tests --scope tests/test_pipeline_runner.py`
  - `rai gate check gate-lint`
  - `rai gate check gate-format`
  - `rai gate check gate-types`
- **Dependencies:** None.

### Task 2 — GREEN: Typed runner module
- **Size:** M
- **Files:** create `validators/pipeline_runner.py`, modify `pyproject.toml`
- **TDD:** Implement Pydantic models, registry loader, summary/detail helpers, guided evidence writer, and minimal CLI until Task 1 tests pass.
- **AC:** All MUST criteria except final manual integration.
- **Verification:**
  - `rai gate check gate-tests --scope tests/test_pipeline_runner.py`
  - `rai gate check gate-lint`
  - `rai gate check gate-format`
  - `rai gate check gate-types`
- **Dependencies:** Task 1.

### Task 3 — REFACTOR: CLI output and evidence shape

## Gate Policy
| When | Command | Scope |
|------|---------|-------|
| Per task | `rai gate check gate-tests --scope <test_dir>/` | Only tests for the changed module (e.g. `packages/raise-cli/tests/storage/`) |
| Per task | rai gate check gate-lint | Full project (fast) |
| Per task | rai gate check gate-format | Full project (fast) |
| Per task | rai gate check gate-types | Full project |
| End of story | `rai gate check gate-tests --scope packages/<pkg>/` | Changed package only — NOT full suite |
| MR creation | `/rai-mr-create` | Full suite — the ONLY place where unscoped tests run |

Concrete task scope for this story: use `tests/test_pipeline_runner.py` and `tests/test_pipeline_registry.py` because the changed package is the root validator/test surface rather than a `packages/<pkg>/` subtree.

## Execution Order
1. Write tests first to lock the runtime contract.
2. Implement the minimal typed module and dependency declaration.
3. Refine deterministic output/evidence only after behavior passes.
4. Run real-registry integration commands.

## Risks and Mitigations
- **Risk:** Runner grows into a generic engine. **Mitigation:** no automatic skill invocation in S31.1.
- **Risk:** Runtime model diverges from validator contract. **Mitigation:** tests use the real registry and registry test remains in final checks.
- **Risk:** `uv run` build issue blocks gates. **Mitigation:** record the tooling failure and use available gate output; do not mix a build-system repair into this story unless gates require it.
