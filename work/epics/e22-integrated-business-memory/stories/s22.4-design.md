# Diseño S22.4 — Inicio y recuperación contextual

## PRIME y complejidad

Las consultas RaiSE recuperaron cuatro decisiones que aplican directamente:
validar la DB mediante el contrato DDL antes de usarla (PAT-D-14), devolver
fallback local explícito en vez de elevar fallos de almacenamiento (PAT-D-15),
usar el ledger como autoridad de un snapshot aplicado (PAT-D-16) y conservar
el aislamiento/allowlist de las rutas de migración (PAT-D-19). El contexto de
código no devolvió símbolos para la rama; `rai schema sum check` está verde.

**Complejidad: moderada.** Consume tres componentes existentes (runtime,
schema/migrador y contrato de conversación), define una política de relevancia
determinista y tiene una frontera de privacidad. No cambia interacción humana,
no integra HTTP y no añade dependencias, por lo que no requiere investigación
UX ni infraestructura real adicional en esta historia.

## Problema y valor

Después de S22.3 la empresa ya tiene datos explícitos y migrados en SQLite,
pero una sesión nueva no dispone de una lectura local, pequeña y verificable
para retomar el contexto. El `SessionStartOrchestrator` heredado selecciona la
primera empresa, consulta un servidor y toma facts genéricos, por lo que no es
seguro para una empresa aislada por proyecto.

El bridge de S22.4 permitirá a S22.6 iniciar una conversación con contexto
confiable sin obligar a un empresario a repetir su perfil o volver a leer una
conversación. El resultado será estable, acotado a cinco ítems y degradable:
si no hay memoria válida, el recorrido actual continúa sin afirmar contexto
inventado.

## Gemba: estado y límites reales

### Dependencias, legacy y drift

- Depende de la DB por proyecto y health contract de S22.2, y del ledger/
  envolturas de S22.3. No se debe implementar hasta que ambos estén en `main`.
- **Legacy sweep:** nada queda huérfano: `SessionStartOrchestrator` y los
  `scaleup-start-*` coexisten porque su flujo actual no se sustituye hasta
  S22.6. Esta historia no los importa, modifica ni declara retirados.
- No existen `governance/drift-hotspots.json` ni `drift-catalog.md`. Riesgo
  AG2: duplicar ranking de `MemoryEngine`; mitigación: no se copia su búsqueda
  de facts, se define una única consulta SQL de contrato sobre las claves
  migradas. Riesgo AG4: tocar runtime, router, front door e instalador a la
  vez; mitigación: S22.4 toca sólo el bridge de lectura y sus pruebas.
- Supply chain: N/A. Se usa sólo `sqlite3`, `json`, `dataclasses` y `pathlib`
  de la biblioteca estándar; no se introduce dependencia.

## Enfoque y contrato

Se añadirá `ProjectMemorySessionContext(project_root)`, una frontera de lectura
con una única operación pública `load()`. Devuelve un dataclass inmutable:

```python
@dataclass(frozen=True)
class ContextItem:
    key: str
    value: str
    source: str
    observed_at: str
    kind: Literal["fact", "change"]
    confirmed: bool = True


@dataclass(frozen=True)
class SessionRecoveryResult:
    ready: bool
    items: tuple[ContextItem, ...] = ()
    reason: str | None = None
    user_message: None = None
```

`reason` se reserva para logs, diagnóstico y pruebas; el adaptador público no
lo representa. `user_message` es siempre `None`: la historia no introduce
texto, pregunta ni comando y por tanto no cambia UX antes de S22.6.

La operación seguirá esta secuencia, siempre con la raíz explícita:

1. Construir `ProjectMemoryRuntime(project_root)` y llamar `health()`. Si no
   está listo, devolver `SessionRecoveryResult(False, reason=...)` sin abrir
   otra fuente ni crear directorios.
2. Abrir la DB validada en modo de solo lectura. Identificar el snapshot actual
   exitoso de `.scaleup/agent/memory/company-profile.yaml` en
   `migration_applications`; si no existe, no hay facts recuperables para esta
   historia, aunque haya filas libres en `memory_facts`.
3. Consultar sólo las keys allowlisted `profile.focus.%`, `diagnosis.%` y
   `profile.%`. Parsear cada `value` como JSON; valores no serializables,
   vacíos, objetos/listas sin una representación breve o filas inválidas se
   omiten, nunca se convierten en texto improvisado.
4. Asociar cada fact a la ruta constante de perfil y a la fecha de aplicación
   del ledger. Su confirmación es `True` sólo porque proviene de un campo
   explícito que S22.3 importó desde el perfil empresarial; ningún fact de
   `MemoryEngine` libre, entidad, relación, conversación o inference entra.
5. Consultar las versiones más recientes de worksheets. Aceptar únicamente una
   envoltura de S22.3 con `relative_path`, `content_sha256`, `source_kind` y
   una aplicación de ledger correspondiente. Transformarla en un item `change`
   de metadatos (`source_kind`, categoría/herramienta y fecha), sin retornar el
   `payload` ni inferir qué cambió. Esto cubre “últimos cambios” comprobables
   sin filtrar datos de negocio innecesarios.
6. Ordenar en la DB/puente de forma determinista: facts de
   `profile.focus.` (prioridad 0), `diagnosis.` (1), `profile.` (2), cambios
   válidos (3); luego fecha observada descendente y key ascendente. Tomar los
   primeros cinco globales. No se usa similitud, embeddings ni criterio del
   modelo.
7. Cualquier `sqlite3.Error`, JSON malformado o fallo de lectura se reduce a
   fallback seguro. Una fila dañada se omite y conserva otras filas válidas;
   un fallo de consulta/conexión completa deja `ready=False` y `items=()`.

La base sana sin compañía/proveniencia/facts devuelve `ready=True, items=()`:
es “memoria vacía”, no un error. La ausencia/corrupción/contrato inválido es
`ready=False`: el consumidor S22.6 conserva literalmente el flujo YAML actual
y no informa internals a la persona.

### Preservación de valor y límites de almacenamiento

No se reemplaza un lector público existente: se añade una lectura explícita de
SQLite preparada por S22.2/S22.3. Antes, `conversation.run()` leía perfil y
estado efímero YAML; después de esta historia sigue igual. Por tanto no hay
cambio de contrato para callers. El dominio que agrega este bridge es la
verificación de procedencia/confirmación sobre la fuente única, que un mero
passthrough de `memory_facts` no puede aportar.

El hallazgo AR confirmó que la proveniencia por archivo no basta para verificar
cada fact. Ésta es la excepción mínima y necesaria al límite inicial de no
evolucionar el schema: S22.4 eleva el esquema a v4 con
`migration_fact_applications`. Cada fact guarda hash de valor, referencia a la
aplicación y `applied_at`, insertados en la misma transacción. El upgrade v3→v4
reconstruye esos vínculos atómicamente; no añade fuentes, API pública ni cambia
el comportamiento del migrador. Las actualizaciones v2/v3 se conservan y el
historial A→B→A sigue siendo una aplicación nueva verificable.

## Ejemplos concretos

### Contexto confirmado, orden y límite

```python
result = ProjectMemorySessionContext(root).load()

assert result.ready is True
assert [(item.kind, item.key) for item in result.items] == [
    ("fact", "profile.focus.current_decision"),
    ("fact", "diagnosis.cash"),
    ("fact", "profile.name"),
    ("change", "worksheet:strategy/opsp"),
]
assert all(item.confirmed for item in result.items)
assert all(item.source.startswith((".scaleup/", "work/")) for item in result.items)
assert len(result.items) <= 5
```

### Hechos libres y contenido sensible quedan fuera

```python
insert_fact(db, key="fact:free", value={"content": "el CEO cree que..."})
insert_fact(db, key="profile.secret", value="contraseña")
insert_worksheet_payload(db, {"payload": {"private_notes": "no mostrar"}})

result = ProjectMemorySessionContext(root).load()

assert all(item.key != "fact:free" for item in result.items)
assert all(item.key != "profile.secret" for item in result.items)
assert all("private_notes" not in item.value for item in result.items)
assert all("apikey" not in item.key.lower() for item in result.items)
assert all("clientsecret" not in item.key.lower() for item in result.items)
```

### Fallback y ausencia de escritura

```python
before = database_digest(root / ".scaleup/memory/escala.db")
result = ProjectMemorySessionContext(root).load()
after = database_digest(root / ".scaleup/memory/escala.db")

assert result.ready is True
assert before == after

bad = ProjectMemorySessionContext(root_with_corrupt_db).load()
assert bad.ready is False
assert bad.items == ()
assert bad.user_message is None
```

## Estrategia de pruebas

| Capa | Caso | Propósito |
|---|---|---|
| Unit | constructor/resultado | La raíz es explícita; resultado inmutable, sin texto público ni paths absolutos. |
| Unit | allowlist + JSON | Sólo namespaces S22.3 y envolturas válidas entran; JSON/filas inválidas se omiten sin lanzar. |
| Unit | ranking | Foco > diagnóstico > perfil > cambios; fecha/key resuelven empate; límite global cinco. |
| Integration | fixture S22.3 migrada | Proveniencia de perfil y worksheet se verifica contra ledger; no se incluye payload ni conversación. |
| Integration | vacía/corrupta/schema inválido | Vacía sana entrega `ready=True`; runtime no sano entrega fallback sin crear, migrar ni escribir. |
| Regression | aislamiento y digest | Dos raíces no comparten datos y `load()` no cambia el digest/filas de la DB. |

Los fixtures se crearán de forma sintética mediante el runtime/migrador de
S22.3 y tendrán fechas controladas. No se usa `.scaleup/agent/memory/
conversation.yaml` real ni datos del workspace. Para corrupción se usarán DBs
temporales con bytes/DDL inválidos, nunca la DB de desarrollo.

## Criterios de aceptación

### MUST

1. Con una DB S22.3 saludable, `load()` devuelve máximo cinco facts/cambios
   verificables, ordenados de forma determinista, y cada item expone key, valor
   seguro, tipo, ruta relativa de fuente y fecha observada.
2. Sólo se recuperan facts de los namespaces S22.3 allowlisted que tienen una
   aplicación de ledger de perfil válida, y cambios con envoltura/ledger S22.3
   válido; facts libres, entidades, relaciones, inferencias y payloads completos
   de worksheet no aparecen.
3. DB sana sin datos verificables devuelve `ready=True, items=()`; DB ausente,
   corrupta, de schema inválido o inaccesible devuelve `ready=False, items=()`
   sin excepción hacia el coach, creación, migración ni fallback YAML.
4. `load()` no muta la DB ni abre/lee/escribe conversación, conocimiento,
   home, rutas externas, logs, red o HTTP; dos project roots siguen aisladas.
5. El contrato no genera texto de UX, comandos, rutas absolutas, SQLite ni
   errores técnicos para la persona y es directamente integrable por S22.6.
6. Claves sensibles se excluyen tanto de facts como de categoría/herramienta de
   worksheet, incluidas formas compactas de credenciales como `apikey`,
   `dbpassword` y `clientsecret`.

### SHOULD

1. Una fila malformada queda aislada y no impide recuperar otras filas válidas.
2. Los cambios recientes válidos muestran tipo/herramienta/fecha, no contenido,
   respetando el límite y la prioridad global.

### MUST NOT

1. No persistir sesiones, hechos, candidatos, decisiones, aprendizajes ni
   métricas; S22.5 es la única historia de captura/confirmación.
2. No cambiar front door, conversation router, onboarding, diagnóstico, plan,
   progreso, installer ni skills públicos. La única excepción es schema/migrador
   v4 para proveniencia por fact, descrita arriba y limitada a ese contrato.
3. No seleccionar “la primera compañía”, consultar un puerto, usar una ruta
   global, HTTP, vector store, embeddings, plugin, cloud o LLM.
