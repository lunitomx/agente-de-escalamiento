# Retrospectiva: S22.4 — Inicio y recuperación contextual

**Fechas:** 2026-08-26 → 2026-08-26
**Estimado:** no registrado
**Real:** una iteración de implementación y tres correcciones de arquitectura.

## Resumen

S22.4 añadió una proyección local, acotada y de sólo lectura para que una sesión
futura pueda recuperar hasta cinco hechos o cambios empresariales verificables.
La proyección no cambia UX ni abre `conversation.yaml`: valida primero el
runtime local, usa únicamente facts migrados con procedencia demostrable y se
degrada a un resultado estructurado vacío cuando la memoria no es confiable.

La revisión arquitectónica convirtió una procedencia inicialmente por archivo
en una procedencia por fact. El schema v4 y el migrador vinculan cada fact a la
aplicación de migración concreta; el bridge acepta el vínculo sólo si el hash y
el timestamp del snapshot actual también coinciden. El upgrade v3→v4 se
reconstruye atómicamente y no vuelve recuperables facts inyectados.

## Qué salió bien

- El límite de historia se respetó: no se modificaron router, front door,
  instalador ni skills públicos; la integración natural queda para S22.6.
- La recuperación tiene frontera explícita de privacidad: excluye datos libres,
  payloads de worksheet y credenciales incluso en `APIKey`, `DBPassword`,
  `apikey`, `dbpassword` y `clientsecret`.
- Los fixtures de upgrade y de reversiones detectaron el problema real de
  versionar esquema sin demostrar la identidad del fact recuperado.
- El gate acotado `rai gate check gate-tests --scope
  tests/test_project_memory_context.py` pasó durante esta revisión. Los gates
  de migración/runtime, lint y formato ya estaban verdes en el progreso.

## Qué mejorar

- El diseño debe exigir desde el inicio la granularidad de procedencia que
  necesita el consumidor. “El perfil fue migrado” no demuestra que cada fact
  aún corresponde al snapshot vigente.
- El modelado de claves sensibles debe compartirse como utilidad de política
  antes de añadir nuevos adaptadores; detectar sólo nombres con guiones bajos
  dejó huecos de camelCase y formas compactas.
- RAISE no produjo records de aprendizaje para design, plan ni implement y el
  backlog no está configurado (`.raise/backlog.yaml` ausente). La historia se
  revisó y señalizó, pero esas fuentes deben habilitarse para métricas completas.

## Checkpoint heutagógico

1. **¿Qué aprendí?** Que una vista de recuperación segura no puede inferir
   confirmación de `memory_facts`: debe probar, por fact, su vínculo a una
   aplicación cuyo hash y `applied_at` son los del snapshot vigente.
2. **¿Qué cambiaría del proceso?** Añadiría la matriz de procedencia y la
   normalización de secretos a los ejemplos de diseño antes de implementar la
   consulta de ranking; habría evitado tres ciclos de corrección posteriores.
3. **¿Mejoras para el framework?** El template de story para proyecciones
   read-only debería pedir explícitamente identidad de fuente, semántica de
   upgrade y pruebas con claves sensibles camelCase/compactas.
4. **¿De qué soy más capaz ahora?** De diseñar recuperación local verificable
   que conserva aislamiento de proyecto, no muta almacenamiento y entrega un
   fallback usable sin revelar detalles internos.

## Mejoras aplicadas

- Se incorporó la tabla `migration_fact_applications` y su backfill v3→v4
  atómico para hacer verificable la procedencia de cada fact.
- Se añadió validación conjunta de hash de valor, snapshot y timestamp antes
  de publicar el fact, con pruebas que rechazan registros inyectados.
- Se normalizaron claves sensibles de facts y metadatos de worksheets antes de
  permitirlas en la vista.

## Patrones añadidos y reforzados

- Reforzados con voto `+1`: PAT-D-14 (validación DDL antes de leer una base
  local), PAT-D-18 (fixtures de upgrade y reversión) y PAT-D-19 (contención,
  allowlist y exclusión de memoria de sesión).
- Añadido PAT-D-20: una proyección read-only basada en migraciones debe guardar
  el enlace por fact a la aplicación exacta y comprobar hash y timestamp del
  snapshot vigente antes de exponerlo.
- Añadido PAT-D-21: normalizar nombres sensibles antes del ranking/allowlist,
  incluidas formas camelCase, compactas y etiquetas de metadatos anidados.
