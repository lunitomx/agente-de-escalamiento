# Plan S22.6 — Front door y continuidad natural

**Story:** S22.6  
**Tamaño:** M (7 puntos)  
**Fecha:** 2026-08-26  
**Estado de entrada:** S22.2–S22.5 están integradas en `main`; el diseño de
S22.6 está aprobado para implementación.

## Objetivo de implementación

Conectar los contratos ya aislados de recuperación S22.4 y consentimiento
S22.5 a `coaching.router.conversation.run()` sin cambiar la firma pública de
`scaleup-frontdoor conversation MENSAJE`. El empresario seguirá enviando una
frase natural y recibiendo un único mensaje humano. La integración debe ser
silenciosamente compatible: si no hay memoria sana o recuperable, onboarding,
diagnóstico, plan en una hoja y progreso conservan exactamente su recorrido
actual y no generan ninguna escritura.

La nueva frontera será un adaptador/protocolo interno, inyectable y testeable.
Sólo traduce resultados estructurados ya saneados por S22.4/S22.5; no vuelve a
leer SQLite desde el router, no interpreta transcripciones ni inventa
candidatos. La captura comienza únicamente tras una intención inequívoca de
pausar/cerrar y una pregunta explícita; sólo una respuesta completa `sí`
confirma mediante S22.5. `no` rechaza y cualquier otra respuesta conserva la
propuesta pendiente sin cerrar.

## Tareas atómicas (TDD)

### 1. Fijar el protocolo interno y el renderizador público seguro

**Tamaño:** M  
**Depende de:** S22.4 y S22.5 en `main`  
**Criterios:** MUST 1 y 4; SHOULD 1; MUST NOT 1–3.

Definir pruebas RED para `NaturalTurn` y un `MemoryContinuity` inyectable, y
crear `ProjectMemoryContinuity(project_root)`. `resume()` consume sólo la
proyección confirmada de `ProjectMemorySessionContext`; con items válidos
devuelve un prefijo breve y seguro, y con vacío, memoria ausente, corrupta o
fallback devuelve una señal interna sin texto público. El renderizador debe
aceptar únicamente campos públicos permitidos, limitar el resumen y rechazar
tokens/rutas/vocabulario de infraestructura antes de que lleguen al router.

Preparar también el esqueleto de `begin_pause()`, `capture_statement()` y
`answer_confirmation()` que delegará al bridge S22.5. No cambia schema ni
reimplementa reglas de consentimiento; el candidato será siempre `fact` o
`decision`, con origen fijo `explicit_user_statement` y observación opaca
generada para la sesión abierta.

- **RED:** DB confirmada retorna prefijo con hecho permitido; DB vacía,
  ausente/corrupta y un resultado con secreto, ruta, `sqlite`, `DB`, skill o
  ID no producen texto público ni escritura.
- **GREEN:** dataclasses/protocolo mínimos, puente read-only y renderizador
  determinista de español claro.
- **REFACTOR:** concentrar sanitización, límites y fallback; no duplicar SQL,
  política de secretos S22.4 ni transacciones S22.5.

**Archivos:** crear `escala_server/project_memory_continuity.py` y
`tests/test_project_memory_continuity.py`; modificar `escala_server/__init__.py`
sólo si el import instalado lo requiere.

### 2. Integrar retomar y pausa explícita sin bifurcar el router

**Tamaño:** M  
**Depende de:** tarea 1  
**Criterios:** MUST 1–4; SHOULD 1.

Modificar `conversation.run(message, base_path=...)` para inyectar o construir
el adaptador con la raíz explícita. Detectar las intenciones naturales limitadas
de retomar y pausar/cerrar sin alterar el protocolo del front door ni las
etapas existentes. Para retomar, componer como máximo el prefijo seguro seguido
de la única pregunta que ya correspondía al coach. Si el adaptador no tiene
contexto o devuelve fallback, retornar exactamente la respuesta previa del
router para el mismo estado.

Para pausar, abrir captura sólo si el bridge está listo y pedir una sola
pregunta humana sobre una decisión o dato concreto. La siguiente frase se toma
como declaración explícita exclusivamente dentro de esa etapa; después se
renderiza la propuesta de confirmación. Un `sí` llama S22.5; `no` la rechaza;
ambigüedad deja `proposed` y ofrece aclarar o continuar. La ruta normal no
convierte mensajes ordinarios en memoria.

- **RED:** secuencia pública retomar→contexto→pregunta; pausar→declaración→
  propuesta→sí/no/ambigua; exactamente una entrada en `sí`, cero en `no` y
  ambigua; la propuesta sigue pendiente y no cierra.
- **GREEN:** estado efímero mínimo del router y delegación al protocolo, sin
  acceso directo a base de datos.
- **REFACTOR:** helpers de intención/composición sin cambiar preguntas,
  persistencia o contenido estratégico preexistente.

**Archivos:** modificar `coaching/router/conversation.py`,
`escala_server/project_memory_continuity.py` y
`tests/test_scaleup_conversation.py`; ampliar
`tests/test_project_memory_continuity.py` sólo para el contrato del bridge.

| Per task | `rai gate check gate-tests --scope <test_dir>/` | Only tests for the changed module (e.g. `packages/raise-cli/tests/storage/`) |
| Per task | `rai gate check gate-lint` | Full project (fast) |

| End of story | `rai gate check gate-tests --scope packages/<pkg>/` | Changed package only — NOT full suite |
| MR creation | `/rai-mr-create` | Full suite — the ONLY place where unscoped tests run |

El cierre de historia ejecuta los scopes concretos
`tests/test_project_memory_continuity.py`,
`tests/test_scaleup_conversation.py`, `tests/test_scaleup_installer.py`,
`tests/test_project_memory_context.py` y
`tests/test_project_memory_session_close.py`. No se ejecuta una suite sin
scope.

## Orden y dependencias

`protocolo/renderizado seguro → router de retomar/pausar → regresiones y
fallback → runtime instalado → integración local`.

El orden es riesgo-primero: el adaptador limita qué puede alcanzar el front
door antes de introducir intenciones y escritura; los recorridos heredados se
congelan antes de modificar el instalador; el smoke llega cuando la ruta
instalada es importable. Las tareas 2–4 son secuenciales porque comparten el
protocolo y el router. No hay ciclo ni paralelismo seguro en los archivos de la
historia.

## Riesgos, mitigaciones y rollback

| Riesgo | Mitigación | Rollback |
|---|---|---|
| Router convierte conversación normal en memoria | Captura sólo tras pregunta explícita y pruebas de no-mutación | Revertir adaptador/router; S22.5 conserva sus datos aislados. |
| Fallback altera onboarding, diagnóstico, plan o progreso | Oráculos de respuesta previa, digest y conteos por etapa | Revertir integración; el coach previo sigue operativo. |
| Se filtra infraestructura o secreto al empresario | Renderer allowlist, limpieza centralizada y barrido de vocabulario prohibido | Retirar prefijo; ningún dato técnico queda expuesto por contrato. |
| `sí` deja escritura parcial o ambigüedad cierra | Delegar máquina transaccional a S22.5 y probar estados | Revertir caller; propuesta/entrada siguen auditables en S22.5. |
| Runtime instalado omite dependencia o arrastra servidor | Lista mínima en `copy_memory_runtime()` y smoke temporal | Revertir sólo lista de copias; datos locales se preservan. |
