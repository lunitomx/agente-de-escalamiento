# Diseño S22.5 — Cierre, hechos y patrones confirmados

## PRIME y complejidad

RaiSE recuperó los patrones PAT-D-14/15/16/18/19/20/21: validar el DDL antes
de operar, degradar sin elevar errores al coach, conservar ledger/operaciones
en la misma transacción, no seguir rutas externas y normalizar secretos. El
contexto estructural no devolvió símbolos; `rai schema sum check` está verde.

**Complejidad: compleja.** Define una frontera de consentimiento, tres estados
de datos, transacciones, conflicto y evolución de schema. No es una historia
de UX: no requiere investigación ni infraestructura externa porque no presenta
la pregunta al empresario todavía.

## Problema y valor

S22.4 sólo recupera snapshots que el empresario ya había guardado en archivos.
El cierre heredado (`SessionCloseOrchestrator`) captura decisiones y aprendizajes
automáticamente mediante `MemoryEngine`, el esquema DAO legado y rutas bajo
`Path.home()/.escala`; por ello no puede preservar el consentimiento ni el
aislamiento del proyecto.

El nuevo bridge permitirá a S22.6 pedir una confirmación natural sin que una
inferencia del modelo quede registrada como hecho. El resultado medible es que
cada entrada de conversación persistida tiene un `yes` inequívoco, fuente
auditable y ninguna alternativa ambigua produce una entrada confirmada.

## Enfoque y contrato

Se añadirá `ProjectMemorySessionClose(project_root)` con cuatro operaciones
explícitas: `open_session()`, `propose()`, `confirm()` y `close()`. Ninguna
acepta una ruta de DB, empresa implícita, transcript o callback de modelo.

### Estados y persistencia

```
candidate input -> proposed -- exact yes --> confirmed entry (active)
                         |                    |
                         +-- exact no --------> rejected
                         +-- otro texto ------> proposed (no-op)
session close: permitted sólo cuando no hay proposed
```

La migración v6 añade tres tablas locales, con claves/índices definidos en el
DDL y sin cambiar tablas de migración:

| Tabla | Datos mínimos | Invariante |
|---|---|---|
| `session_memory_proposals` | id, session_id, kind, statement, origin, observation_ids JSON, response_state, created/responded_at | propuesta es mutable sólo para cambiar `proposed` a `confirmed`/`rejected`; nunca es un fact. |
| `confirmed_memory_entries` | id, proposal_id UNIQUE, session_id, kind, statement, source JSON, confirmation_confidence, confidence_reason, status, replaces_entry_id, confirmed_at | se crea una vez por `yes`; fuente/consentimiento inmutables. |
| `project_memory_sessions` | id, status, opened_at, closed_at, close_reason | no cierra con propuestas pendientes; audita ciclo sin usar el DAO global. |

`CandidateSource` admite exclusivamente `origin="explicit_user_statement"`,
el mismo `session_id` y observaciones opacas (IDs, no texto). Para `fact` y
`decision` exige >=1; para `pattern`, >=2 distintos. `statement` es un texto
ya propuesto por un adaptador futuro, limitado y validado; una etiqueta,
statement o metadato que parezca credencial se rechaza entero, no se redacta.
`origin=model_inference`, falta de observaciones, IDs duplicados, ID de sesión
incongruente o cualquier contenido no estructurado devuelve candidato inválido.

`confirm(proposal_id, answer)` normaliza Unicode/case/espacios y acepta sólo
las palabras completas `sí`, `si`, `yes`; acepta `no` como rechazo. Cualquier
otro valor devuelve estado pendiente sin escribir. Repetir una decisión ya
terminal devuelve su estado existente. El `yes` inserta la entrada confirmada,
marca la propuesta y actualiza la sesión dentro de una transacción; si falla,
no queda transición parcial.

La confianza es fija `1.0` y razón `explicit_confirmation`: prueba que la
persona autorizó conservar el texto, no que el texto sea una predicción cierta.
No se calcula trust de modelo. Para un posible conflicto, el caller debe pasar
un `replaces_entry_id` de la misma clase y una nueva propuesta confirmada; sólo
entonces se marca la anterior `superseded`. Sin referencia explícita, dos
afirmaciones se conservan como entradas separadas: no se infiere contradicción.

`close(session_id)` consulta propuestas pendientes en la misma DB: devuelve
`closed=False, reason="confirmation_pending"` si existen, y sólo marca cierre
cuando todas están confirmadas/rechazadas o no hay propuestas. Una DB vacía,
ausente/corrupta/URI especial/schema inválido devuelve resultado no listo y no
crea datos mediante una fuente alternativa. No hay sesión pública ni texto UX;
los resultados técnicos permanecen internos.

### Compatibilidad de snapshots S22.4

Las entradas S22.5 viven únicamente en sus nuevas tablas. No actualizan
`memory_facts`, `migration_sources`, `migration_applications`,
`migration_fact_applications`, `companies` ni worksheets. Por ello la consulta
de S22.4 sigue viendo sólo el snapshot migrado actual y su digest permanece
estable respecto de esas tablas. S22.6 podrá componer ambas proyecciones con
una decisión explícita de presentación, sin reinterpretar una entrada S22.5
como perfil migrado.

## Ejemplos y fixtures adversariales

### Confirmación, rechazo y ambigüedad

```python
decision = close.propose("s-1", decision_candidate("Contratar líder de ventas", ["o-1"]))
assert decision.status == "proposed"
assert close.confirm(decision.id, " Sí ").status == "confirmed"

pattern = close.propose("s-1", pattern_candidate("Cobranza se retrasa", ["o-2", "o-3"]))
assert close.confirm(pattern.id, "no").status == "rejected"

fact = close.propose("s-1", fact_candidate("Caja disponible: 320000", ["o-4"]))
assert close.confirm(fact.id, "quizá").status == "proposed"
assert close.close("s-1").closed is False
```

### Falsificación, secreto y conflicto no inferido

```python
assert close.propose("s-1", fact_candidate("APIKey=abc", ["o-5"])).accepted is False
assert close.propose("s-1", fact_candidate("El modelo cree que quebrará", [], origin="model_inference")).accepted is False
assert close.propose("s-1", pattern_candidate("Ventas bajan", ["o-6"])).accepted is False

# Dos decisions parecidas no se sobrescriben sin replaces_entry_id explícito.
first = confirm(close.propose("s-2", decision_candidate("Abrir Monterrey", ["o-7"])))
second = confirm(close.propose("s-2", decision_candidate("No abrir Monterrey", ["o-8"])))
assert active_entry_count(close, kind="decision") == 2
assert first.status == second.status == "active"
```

before = ProjectMemorySessionContext(root).load()

## Estrategia de pruebas

| Capa | Caso | Propósito |
|---|---|---|
| Unit | validación de candidato/answer | Sólo yes exacto confirma; no rechaza; ambigüedad no-op; observaciones y secretos se rechazan. |
| Unit | state machine/idempotencia | Terminales no cambian ni duplican; cierre bloqueado por pendientes. |
| Integration | DB v4 → v6 | Upgrade conserva S22.3/S22.4, crea contrato v6 y health valida DDL/índices. |
| Integration | transacción/conflicto | Error revierte propuesta/entrada/sesión; reemplazo explícito supersede y conflicto implícito coexiste. |
| Regression | snapshot/privacidad | `ProjectMemorySessionContext.load()` no cambia resultados; no home, conversation, YAML, red o rutas externas. |
| Regression | dos raíces | candidatos, sesiones y entradas de A nunca son visibles en B. |

## Criterios de aceptación

### MUST

1. Proponer no persiste un hecho; únicamente `sí`/`si`/`yes` completos y
   normalizados crea una entrada confirmada, y cada entrada guarda tipo,
   statement aprobado, sesión/origen/observaciones, fecha y confianza explícita.
2. `no` deja rechazo auditable sin entrada; cualquier otra respuesta, candidato
   sin evidencia suficiente, secreto, ruta externa o inferencia queda pendiente
   o inválido sin transformar datos en memoria.
3. Patrón exige dos observaciones distintas; decisión/fact una; conflictos no
   sobrescriben y sólo un reemplazo identificado+confirmado supersede.
4. Confirmación y cierre son transaccionales/idempotentes; pendiente bloquea
   cierre y ningún fallo SQLite deja transición o entrada parcial.
5. V6 conserva salud/aislamiento local y S22.4 continúa devolviendo sólo su
   snapshot migrado, sin cambios a `migration_*` ni facts de perfil.

### SHOULD

1. Resultados técnicos diferencian ready, invalid, pending, rejected,
   confirmed, duplicate y fallback sin incluir statement sensible.
2. La procedencia se exporta como estructura auditable local sin transcript.

### MUST NOT

1. No auto-confirmar, inferir facts/patrones, usar trust del modelo ni guardar
   transcripciones, credenciales, conversation.yaml, home, cloud o red.
2. No modificar UX/front door/router/instalador/skills ni el cierre heredado.
3. No hacer la entrada confirmada visible automáticamente a S22.4.
