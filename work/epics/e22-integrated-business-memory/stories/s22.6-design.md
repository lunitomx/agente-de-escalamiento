# Diseño S22.6 — Front door y continuidad natural

## PRIME y complejidad

La consulta de grafo RaiSE no devolvió conceptos y el contexto estructural no
devolvió símbolos; se continuó con gemba del front door, router, instalador y
contratos S22.4/S22.5. `rai schema sum check` está verde.

**Complejidad: moderada.** Conecta cuatro fronteras existentes (front door,

historia son la especificación verificable mínima.

## Problema y valor

Hoy `scaleup-frontdoor` pasa una frase a `coaching.router.conversation.run()`
y éste responde la siguiente pregunta del recorrido. S22.4 y S22.5 ya pueden
recuperar contexto y confirmar memoria local, pero permanecen aislados: una
persona no recibe continuidad al volver ni puede cerrar naturalmente sin
conocer implementación.

S22.6 hará que ScaleUp diga sólo lo útil para el empresario: un contexto breve
al retomar y una pregunta clara antes de recordar una declaración explícita.
El valor observable es que una segunda sesión retoma información confirmada,
las negativas/ambigüedades no se guardan y los recorridos existentes siguen
funcionando igual cuando no hay memoria.

## Enfoque: protocolo de continuidad natural

Se añadirá una frontera interna de conversación (por ejemplo
`ProjectMemoryContinuity`) inyectable al router. Su contrato es de intención y
resultado, no de rutas, SQL ni texto de error:

```python
@dataclass(frozen=True)
class NaturalTurn:
    prefix: str | None = None
    next_question: str | None = None
    stage: Literal["normal", "capture", "confirm"] = "normal"

class MemoryContinuity(Protocol):
    def resume(self, project_root: Path) -> NaturalTurn: ...
    def begin_pause(self, project_root: Path) -> NaturalTurn: ...
    def capture_statement(self, project_root: Path, text: str) -> NaturalTurn: ...
    def answer_confirmation(self, project_root: Path, text: str) -> NaturalTurn: ...
```

El router conserva su respuesta actual para `normal` y compone, como máximo,
un prefijo seguro de continuidad seguido de la pregunta que ya correspondía.
La raíz es siempre `base_path`; ningún caller acepta una ruta de DB, ID de
empresa o payload técnico.

### Secuencia pública

1. Al detectar una intención natural de retomar (por ejemplo, “retomemos” o
   “¿dónde nos quedamos?”), el router pide al adaptador `resume(base)`. Si hay
   items confirmados, presenta un máximo de contexto ya saneado por S22.4 y
   continúa con una única pregunta útil. Vacío/fallback es exactamente la
   respuesta previa del router, sin mención a memoria o error.
2. Al detectar una intención inequívoca de pausar/terminar, el router abre una
   sesión local. Si está lista, pregunta: “Antes de pausar, ¿qué decisión o
   dato concreto quieres que recuerde para la próxima vez?” Si no está lista,
   ofrece la despedida/continuación existente sin bloquear.
3. Sólo la respuesta a esa pregunta explícita se trata como declaración de la
   persona. El adaptador la conserva como candidato estructurado con origen
   `explicit_user_statement` y una observación local opaca; no analiza ni
   infiere otros turnos. Para mantener el contrato S22.5, el MVP propone un
   hecho/decisión explícito; patrones requieren las dos observaciones que ya
   exige el bridge y no se inventan desde conversación libre.
4. El adaptador repite el contenido para confirmación clara: “Entendí: …
   ¿quieres que lo recuerde? (sí/no)”. `sí` llama confirmación, `no` la rechaza;
   otro texto conserva `proposed`, explica que no dará nada por hecho y ofrece
   aclarar o seguir. Sólo se intenta `close()` cuando no queda propuesta.
5. Todos los resultados `ready=False`, inválidos o fallback se convierten en
   continuidad silenciosa y segura. Nunca se exponen razones, rutas, SQLite,
   IDs, comandos, skills, DB, logs, stack traces ni términos de arquitectura.

La clasificación del candidato no usa LLM ni heurística que convierta una
inferencia en hecho: la pantalla natural invita a una “decisión o dato” y el
adaptador usa un tipo determinista de captura limitado. El texto se valida y
la persistencia sigue siendo exclusivamente el bridge S22.5; el router no
escribe SQLite directamente.

## Ejemplos ejecutables de contrato

### Recuperación confirmada y conversación normal

```python
reply = router.run("quiero retomar lo que veníamos trabajando", base_path=root)

assert "puntualidad de entrega" in reply
assert "¿" in reply
assert ".scaleup" not in reply
assert "sqlite" not in reply.lower()
```

### Captura explícita, confirmación y siguiente sesión

```python
assert "qué decisión o dato" in router.run("quiero pausar", base_path=root).lower()
proposal = router.run("Contrataremos una líder de ventas en septiembre", base_path=root)
assert "¿quieres que lo recuerde?" in proposal.lower()
confirmed = router.run("sí", base_path=root)
assert "la próxima vez" in confirmed.lower()

next_reply = router.run("retomemos", base_path=root)
assert "líder de ventas" in next_reply.lower()
```


## Estrategia de pruebas y fixtures

| Capa | Fixture/caso | Evidencia |
|---|---|---|
| Adaptador unitario | `confirmed_db` con facts/decisión confirmados | Prefijo máximo, sólo valores saneados y ninguna palabra interna. |
| Adaptador unitario | `rejected_db` y `ambiguous_db` | `no` no crea entry; ambigüedad permanece propuesta y no permite cerrar. |
| Integración router | `absent_db`, `corrupt_db`, `empty_db` | La misma frase de onboarding/diagnóstico/plan/progreso devuelve el flujo previo y no crea DB, sesión, proposal ni entry. |
| Integración router | `confirmed_db` | Retomar → contexto → una pregunta; pausar → captura explícita → sí → nueva sesión recupera. |
| Privacidad | Todos los fixtures y mensajes | Ningún output incluye rutas, SQLite/DB, comando, skill, ID, origen técnico o texto de `conversation.yaml`. |
| Instalador | Runtime temporal Codex/Claude/Hermes | El front door instalado importa el adaptador y reproduce el caso confirmado; S22.7 amplía la matriz/release. |

Los fixtures se construyen en `tmp_path` mediante los APIs S22.2–S22.5; no se
usa la conversación real del workspace. Cada caso registra digest y conteos
antes/después para demostrar ausencia de mutación cuando no hay `sí` inequívoco.

## Criterios de aceptación

### MUST

1. La puerta pública conserva una sola frase de entrada y una respuesta humana;
   retomar muestra sólo contexto confirmado y seguro cuando existe, seguido de
   una pregunta útil.
2. Onboarding, diagnóstico, one-page plan y progreso mantienen sus respuestas
   y persistencia actuales con DB vacía, ausente, corrupta o fallback.
3. Pausar/cerrar sólo propone una declaración que la persona escribió después
   de una pregunta explícita; `sí` confirma mediante S22.5, `no` rechaza y una
   respuesta ambigua no escribe ni cierra.
4. Ni salida pública ni error/fallback expone infraestructura, rutas, comandos,
   skills, SQLite/DB, IDs, fuentes internas, logs o transcripción.
5. Tests E2E cubren `confirmed`, `rejected`, `ambiguous` y `absent/corrupt`
   con conteos/digests que prueban no escritura accidental.

### SHOULD

1. El resumen de recuperación es conciso y usa el mismo español claro del
   coach; vacío/fallback no agrega texto.
2. El runtime instalado recibe el adaptador mínimo sin reintroducir un servicio
   HTTP, home global o dependencia externa.

### MUST NOT

1. No inferir, resumir ni persistir automáticamente contenido de conversación.
2. No cambiar schema, migración, ranking, consentimiento, dashboards ni la
   semántica de los recorridos empresariales existentes.
3. No hacer red, HTTP, cloud, embeddings, plugins, LLMs o lectura de
   `conversation.yaml` como fuente de memoria.
