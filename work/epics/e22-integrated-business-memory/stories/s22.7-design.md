## Problema y valor

S22.6 conectó continuidad natural al front door, pero aún falta la evidencia
de release de que lo que vive en un bundle limpio funciona igual en los clientes
publicitados y no mezcla la información de una empresa con el runtime global.
Sin esa prueba, una demostración puede funcionar en el checkout y fallar tras
instalarse o declarar paridad Hermes sin haberla observado.

Esta historia convierte la promesa local-first en resultados auditables: una
persona instala ScaleUp, habla sin comandos, confirma una decisión y en una
nueva sesión la recupera sin perderla al actualizar o retirar el producto.
El resultado se mide con comandos ejecutables, artefactos dentro de `tmp_path`,
conteos/digests de SQLite y documentación que distingue evidencia de límite.

## Enfoque

Se añadirá una prueba de aceptación de release que instale a un directorio
temporal y use exclusivamente el `scaleup-frontdoor` copiado. Para Claude y
Codex se ejecutará el mismo recorrido determinista contra roots de empresa
distintas:

1. instalar el target en una raíz limpia y verificar que sólo existe la skill
   pública y todos los módulos requeridos por continuidad;
2. enviar frases humanas para abrir pausa, declarar una decisión, confirmarla
   con `sí`, y abrir una segunda sesión con `retomemos`;
3. comprobar la declaración recuperada, una sola siguiente pregunta útil y la
   ausencia de tokens técnicos/sensibles en todas las respuestas;
4. generar backup desde el runtime del bundle, alterar o retirar la DB en forma
   offline y restaurar; comprobar la entrada confirmada y su procedencia;
5. actualizar/reinstalar y desinstalar el target; verificar que la empresa y
   su memoria no se copian al runtime ni se borran salvo `--purge` acotado.

Hermes seguirá la misma prueba de bundle/front door. La equivalencia de runtime
queda acreditada si sus respuestas y estado son idénticos a Claude/Codex. La
paridad de *cliente Hermes real* requiere que el ejecutable real descubra la
skill y ejecute el front door en un entorno aislado; si no está presente o su
bootstrap depende de permisos/servicios externos no proporcionados, el release
debe registrar este límite, el comando de reproducción y la condición exacta
para cerrarlo. No se simula ni se sustituye por un test unitario.

El comportamiento con DB ausente/vacía/corrupta conserva el contrato ya
establecido: el front door devuelve el flujo previo y no crea base, sesión,
propuesta ni entrada. No hay reemplazo de storage en esta historia, por lo que
el storage migration gate no aplica. Backup/restore mantiene el contrato
administrativo offline: una restauración no lista deja la DB sana intacta y no
es invocada mientras conversa un usuario.

## Ejemplos ejecutables de contrato

### Claude y Codex: bundle instalado, confirmar y recuperar

```python
command = destination / ".codex" / "scaleup" / "bin" / "scaleup-frontdoor"
assert "qué decisión o dato" in _say(command, project, "quiero pausar").lower()
assert "quieres que lo recuerde" in _say(
    command, project, "Contrataremos una líder de ventas en septiembre"
).lower()
assert "próxima vez" in _say(command, project, "sí").lower()

resumed = _say(command, project, "retomemos")
assert "líder de ventas" in resumed.lower()
assert all(token not in resumed.lower() for token in (".scaleup", "sqlite", "skill"))
```

### No y fallo de memoria no escriben ni filtran

```python
before = _memory_state_digest(project)
assert "no lo voy a dar por hecho" in _say(command, project, "tal vez").lower()
assert _memory_state_digest(project) == before

corrupt.write_bytes(b"not a sqlite database")
reply = _say(command, corrupt_project, "retomemos")
assert reply == baseline_reply
assert not any(token in reply.lower() for token in ("sqlite", "db", ".scaleup"))
assert _memory_state_digest(corrupt_project) is None
```

### Backup/restore offline y uninstall conservador

```python
runtime = ProjectMemoryRuntime(project)
backup = runtime.backup()
assert backup.ready
runtime.db_path.unlink()
assert runtime.restore(backup.backup_path).ready
assert "líder de ventas" in _say(command, project, "retomemos").lower()

_installer(destination, "--target", "codex", "--uninstall")
assert (project / ".scaleup" / "memory" / "escala.db").is_file()
assert not (destination / ".codex" / "scaleup").exists()
```

## Estrategia de pruebas y evidencia

| Capa | Caso exacto | Evidencia exigida |
|---|---|---|
| Instalador real | `--target claude`, `codex`, `hermes` en un mismo `tmp_path` | Una skill pública, front door ejecutable y runtime completo por destino; nada empresarial bajo el destino instalado. |
| E2E Claude/Codex | instalar → pausar → declaración explícita → `sí` → `retomemos` | Respuesta contiene decisión; DB local tiene 1 entrada activa con proveniencia válida; roots de proyectos distintos no se cruzan. |
| Consentimiento y privacidad | `no`, ambiguo y texto ES/EN sensible o técnico | Cero entradas confirmadas indebidas; digest/conteos prueban ausencia de escritura; respuesta y recuperación no filtran contenido ni términos internos. |
| Fallback | DB ausente, vacía y corrupta desde el bundle instalado | Misma salida del flujo base por etapa; ningún archivo/estado de memoria nuevo. |
| Backup/restore | DB con decisión confirmada, backup, alteración offline, restore; backup inválido | La decisión sobrevive restauración; backup inválido no sustituye una DB sana. |
| Update/uninstall | reinstalar y `--uninstall`/`--purge` por target | Normal preserva datos empresariales; purge elimina sólo runtime seleccionado; nunca se rastrean o borran otros proyectos. |
| Release/docs | README, demo readiness y demo script | Comandos reproducibles, privacidad/local-first y limitación Hermes coinciden con las pruebas ejecutadas. |
| Gates | manifest | `gate-tests` focalizado y suite completa, `gate-lint`, `gate-format`; `gate-types` se registra como skipped si no tiene comando. |

## Criterios de aceptación

### MUST

1. Claude Code y Codex ejecutan desde instalaciones temporales limpias el
   recorrido completo de continuidad natural y recuperan en una segunda sesión
   sólo la declaración confirmada, sin consultar el checkout.
2. La matriz demuestra aislamiento: una empresa no puede recuperar una entrada,
   backup ni DB de otra; el runtime instalado no recibe datos empresariales.
3. Las respuestas públicas y la DB confirmada no contienen texto sensible o
   técnico prohibido; `no`, ambigüedad, DB ausente, vacía o corrupta no producen
   confirmación ni una escritura accidental observable.
4. Backup/restore offline sobre una entrada confirmada funciona, y un backup
   inválido no reemplaza una base sana; update/uninstall preserva empresa y
   memoria excepto por `--purge` del target explícito.
5. Hermes tiene evidencia del mismo bundle/runtime, y documentación expresa de
   forma verificable si no existe evidencia de conversación del cliente real.

### SHOULD

1. Los tres destinos producen las mismas respuestas deterministas para el
   recorrido de memoria cuando se ejecuta su front door instalado.
2. README y documentación de demo dan pasos de instalación, privacidad,
   contingencia y limpieza que una persona no técnica puede seguir.

### MUST NOT

1. No declarar paridad de cliente Hermes sin ejecutar ese cliente real o dejar
   su límite explícito en la evidencia de release.
2. No añadir estado global, HTTP, cloud, plugins, embeddings ni datos de empresa
   al home/runtime compartido.
3. No cambiar contratos de consentimiento, esquema o coach sólo para facilitar
   un test de release.

## Preguntas abiertas

- Si la suite completa revela deuda ajena a E22, se reportará separadamente: no
  se ocultará debilitando gates ni se ampliará S22.7 sin una regresión atribuible.
