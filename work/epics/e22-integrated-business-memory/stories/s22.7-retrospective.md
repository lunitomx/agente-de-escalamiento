# Retrospectiva: S22.7 — Validación E2E, privacidad y release

**Fecha:** 2026-08-26  
**Estimado:** M  
**Resultado:** completada localmente; lista para `/rai-story-close`.

## Resumen

S22.7 cerró la evidencia de release de la memoria empresarial local. La matriz
ejecuta el `scaleup-frontdoor` copiado por una instalación limpia para Claude,
Codex y el runtime Hermes: pausa natural, declaración, confirmación explícita,
y recuperación en un proceso posterior. Acredita aislamiento entre empresas,
backup/restore offline, degradación segura y update/uninstall conservadores.

Durante la revisión se detectó una fuga real: el instalador copiaba todo
`.scaleup/agent`, por lo que un checkout que contuviera perfiles,
`conversation.yaml`, `escala.db` o backups de una empresa podía distribuirlos
al bundle. El arreglo cambió esa copia por una allowlist de runtime
(`identity`, `sub-agents`, `validators`) y añadió una regresión que siembra
esos datos privados antes de instalar los tres destinos. La prueba verifica
que ninguno aparece en el runtime distribuido.

## Qué funcionó bien

- La matriz usó el ejecutable instalado, no imports del checkout; eso convirtió
  la promesa de release en evidencia de producto reproducible.
- La revisión adversarial no se limitó al contenido de una conversación: también
  probó que la propia fuente de instalación no distribuya datos empresariales.
- La documentación distingue con precisión la equivalencia del runtime Hermes
  del comportamiento no observado de su cliente real.

## Qué mejorar

- El smoke del cliente Hermes real requiere una instalación con permiso de
  lectura de su configuración. Hasta entonces es un límite explícito, no un
  criterio que se deba inferir de la copia de archivos.
- La señal `implement/complete` debe emitirse después de la última corrección
  de una historia; cuando falta o apunta a otro HEAD obliga a repetir el gate
  focal de manera correcta, aunque la suite ya esté acreditada.
- Los warnings históricos de drift deben conservarse separados de la historia:
  no justifican ampliar S22.7 ni ocultar la evidencia de release.

## Checkpoint heutagógico

1. **¿Qué aprendimos?** La privacidad de una memoria local tiene dos fronteras:
   captura/lectura pública y distribución. Filtrar texto no evita que un
   instalador copie una DB o conversación existente.
2. **¿Qué cambiaríamos del proceso?** Sembrar datos empresariales simulados en
   el checkout desde el primer smoke de instalador, antes de afirmar que el
   runtime es portable.
3. **¿Mejoras para el framework?** La checklist de release debería requerir una
   prueba de payload negativo: perfiles, conversaciones, DB y backups fuente no
   deben llegar a ningún destino instalable.
4. **¿Qué somos capaces de hacer ahora?** Auditar una instalación end-to-end
   contra datos reales de una empresa sin confundir prueba de bundle con prueba
   de cliente externo.

## Mejoras y patrones persistidos

- Se reforzaron `PAT-D-24` (política canónica de texto público) y `PAT-D-14`

  empresariales entren al bundle distribuible.
