# Plan S22.7 — Validación E2E, privacidad y release

**Story:** S22.7
**Tamaño:** L (8 puntos)
**Fecha:** 2026-08-26
**Estado de entrada:** S22.2–S22.6 están integradas en `main`; el diseño `4ada118` define la frontera.

## Objetivo de implementación

Demostrar desde bundles instalados en destinos temporales limpios que Claude Code y Codex pueden pausar, declarar una decisión, confirmarla con `sí` y recuperarla en una segunda sesión sin usar el checkout ni exponer detalles técnicos. La matriz acreditará el runtime Hermes; si no existe evidencia ejecutable de su cliente real, la evidencia de release declarará el límite preciso, sin afirmar paridad de cliente.

La evidencia comprobará que datos empresariales, DB y backups permanecen bajo la raíz explícita de cada empresa; que una DB ausente/vacía/corrupta conserva el flujo base sin escritura; y que backup/restore, update y uninstall cumplen el contrato local-first. Sólo se tocará producción ante un incumplimiento reproducible de este contrato.

## Política de gates (obligatoria)

| When | Command | Scope |
|------|---------|-------|
| Per task | `rai gate check gate-tests --scope <test_dir>/` | Only tests for the changed module (e.g. `packages/raise-cli/tests/storage/`) |
| Per task | `rai gate check gate-lint` | Full project (fast) |
| Per task | `rai gate check gate-format` | Full project (fast) |
| Per task | `rai gate check gate-types` | Full project |
| End of story | `rai gate check gate-tests --scope packages/<pkg>/` | Changed package only — NOT full suite |
| MR creation | `/rai-mr-create` | Full suite — the ONLY place where unscoped tests run |

Por ser evidencia explícita de release, la tarea final agrega una corrida unscoped de `gate-tests` después de los scopes; no sustituye ni debilita la política anterior. `gate-types` se registra como `skipped` si el manifiesto no define comando. No se invoca `pytest` directamente.

## Orden y dependencias

`matriz limpia → continuidad/aislamiento Claude-Codex → privacidad/fallback → backup/restore y retención → Hermes/docs → smoke manual y regresión`.

El orden es riesgo-primero: prueba binario instalado y aislamiento antes del valor visible, retención o documentación. Las tareas son secuenciales porque todas extienden helpers de instalador y docs dependen de resultado Hermes. No hay ciclo ni paralelismo seguro en estos archivos.

## Riesgos y mitigaciones

| Riesgo | Mitigación y criterio de salida |
|---|---|
| Smoke usa checkout accidentalmente. | Invocar ruta copiada por target y trabajar desde raíces temporales. |
| Hermes sin cliente real disponible. | Ejecutar bundle/runtime, registrar binario/comando/resultado y declarar límite explícito. |
| E2E oculta o duplica estados. | Reusar `_installer`, ejecutor y digest; conservar conteos/aserciones por paso. |
| Restore/purge afecta datos externos. | Preparar dos raíces, comprobar contención y usar sólo target explícito. |
| Deuda de suite ajena a E22. | Ejecutar gates, separar evidencia atribuible y no modificar gates. |
