## Límite de la historia

No se cambió runtime, instalador, router ni front door. El esquema se elevó a
v4 y el migrador ahora persiste proveniencia por fact transaccionalmente. La
integración natural del resultado queda para S22.6.

## Correcciones de arquitectura

- `migration_fact_applications` vincula cada fact importado con el `id`, hash y
  `applied_at` de su aplicación de migración; el contexto sólo publica el vínculo
  del snapshot actual cuyo hash y timestamp coinciden.
- Se normalizan claves sensibles en camelCase/snake_case, se limitan valores y
  metadatos, y los cambios de worksheet se validan con su propio ledger aunque
  no exista compañía ni aplicación de perfil.

- Signoff v3→v4: el upgrade reconstruye atómicamente vínculos sólo para facts
  que coinciden con el perfil persistido y la última aplicación que aún tiene
  snapshot en el ledger; un fact inyectado no recibe vínculo ni se recupera.
- Las claves sensibles se normalizan conservadoramente también cuando contienen
  acrónimos (`APIKey`, `DBPassword`) o formas compactas (`apikey`,
  `dbpassword`, `clientsecret`) tanto en facts como en metadatos de worksheet.
- La excepción de arquitectura se formalizó: schema/migrador v4 sólo añaden
  proveniencia verificable por fact y el upgrade v3→v4 es atómico; no se amplían
  fuentes, API pública ni el comportamiento de migración.
