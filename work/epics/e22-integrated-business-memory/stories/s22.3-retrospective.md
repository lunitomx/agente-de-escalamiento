# Retrospectiva: S22.3 — Migración YAML idempotente

**Fechas:** 2026-08-26 → 2026-08-26  
**Estimación:** L (5 h 15 min planificadas) | **Real:** sin telemetría de duración registrada

## Resumen

S22.3 incorporó las fuentes empresariales heredadas permitidas a la SQLite
local de cada proyecto mediante `ProjectMemoryMigrator`. La migración usa un
ledger de snapshots con hash, una transacción por artefacto y escritura
versionada para que una repetición no cree datos nuevos, mientras un cambio
real sí conserva una versión nueva. Perfil, diagnóstico, OPSP y worksheets se
procesan independientemente; una fuente ausente o YAML inválido se informa sin
alterar los otros artefactos ni sus archivos de origen.

## Qué salió bien

- El ledger de fuentes y la escritura de negocio se confirmaron en la misma
  transacción, por lo que la deduplicación se basa en una aplicación exitosa y
  no en mtime ni en un indicador separado y frágil.
- Los hashes distinguen correctamente la semántica de YAML (snapshot canónico)
  de la fidelidad documental de Markdown (bytes UTF-8 originales).
- La validación de contención y symlinks ocurre antes de leer fuentes: sólo
  rutas empresariales allowlisted entran al migrador; conversación y
  `knowledge/**` permanecen fuera.
- Los casos de prueba recorren upgrades y reversiones reales A→B→A, además de
  backup y restore offline después de una migración, no sólo mocks unitarios.
- Al no existir un signal `implement complete` verificable para el HEAD,
  `rai gate check gate-tests --scope tests/test_project_memory_migration.py`
  se repitió y pasó antes de esta revisión.

## Qué mejorar

- Emitir el signal de implementación después de cada fix posterior a revisión;
  su ausencia obliga a repetir el gate focal aunque la evidencia de código sea
  válida.
- Registrar learning records de diseño, plan e implementación. No existe
  ningún record bajo `.raise/rai/learnings/` para S22.3, por lo que el proceso
  no permite contrastar decisiones de fase con datos históricos.
- El grafo funcionó sólo con búsqueda por palabras porque el índice semántico
  no está disponible. Es suficiente como fallback, pero limita la calidad de
  PRIME para historias futuras.

## Checkpoint heutagógico

1. **¿Qué aprendí?** Que el ledger debe representar el snapshot que sí llegó a
   negocio y vivir en la misma transacción; de lo contrario un error parcial
   puede hacer que una fuente parezca migrada sin estarlo.
2. **¿Qué cambiaría del proceso?** Definiría desde el contrato de fixtures los
   ciclos upgrade/reversión y la recuperación post-migración, para no dejar la
   idempotencia reducida a dos llamadas idénticas.
3. **¿Mejoras para el framework?** RaiSE debería advertir, sin bloquear, cuando
   faltan records de aprendizaje y cuando `implement complete` no corresponde
   al HEAD que entra a review.
4. **¿De qué soy más capaz ahora?** De modelar migraciones locales que separan
   autoridad de fuente, aplicación de estado, proveniencia y privacidad, y de
   probarlas contra cambios reales de datos empresariales.

## Mejoras aplicadas

- Se añadió un ledger de fuente para aplicaciones idempotentes y verificables.
- Se preservó la semántica de hash: YAML canónico y Markdown en bytes sin
  reinterpretación.
- Se reforzó la lectura segura con contención/symlinks antes de parsear y con
  exclusión explícita de memoria conversacional.
- Se ampliaron pruebas con upgrade/reversión A→B→A y backup/restore offline
  sobre una base ya migrada.

## Patrones añadidos / reforzados

- Reforzado `PAT-D-14` (+1): la validación de salud derivada del DDL fue
  relevante para que el runtime acepte el ledger evolucionado de S22.3.
- Añadido `PAT-D-16` (architecture): el ledger de fuente es la autoridad de
  idempotencia y se confirma en la transacción de escrituras de negocio.
- Añadido `PAT-D-17` (technical): YAML se hashea canónicamente; Markdown se
  hashea como bytes UTF-8 para conservar fidelidad del documento.
- Añadido `PAT-D-19` (risk): validar contención y symlinks antes de toda lectura
  y excluir memoria de sesión de la allowlist empresarial.
- Añadido `PAT-D-18` (process): probar upgrades y reversiones A→B→A reales, y
  verificar backup/restore tras datos migrados.

## Riesgo operativo pendiente

La migración no sustituye aún las fuentes heredadas ni integra el front door;
esas decisiones pertenecen a historias posteriores de E22. El migrador debe
seguir operando con la raíz explícita de cada empresa y el runtime local
saludable de S22.2.
