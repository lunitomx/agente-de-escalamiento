# S22.3 — Migración YAML idempotente: plan

**Story:** S22.3  
**Tamaño:** L (8 puntos)  
**Fecha:** 2026-08-26  
**Estado de entrada:** diseño aprobado; depende del runtime local saludable de
S22.2.

## Objetivo de implementación

Entregar un migrador explícitamente local, `ProjectMemoryMigrator(project_root)`,
que incorpore snapshots empresariales YAML/Markdown a la SQLite de S22.2 de
forma transaccional e idempotente. El trabajo queda estrictamente limitado a
las fuentes y los destinos definidos por el diseño: no migra conversación,
`knowledge/**`, rutas globales ni cambia el front door.

## Propiedad de archivos

| Archivo o árbol | Propietario de S22.3 | Límite |
|---|---|---|
| `escala_server/project_memory_migration.py` | S22.3 | Nuevo migrador, contrato de resultado, descubrimiento, normalización y escritura transaccional. |
| `escala_server/schema.py` | S22.3 | Sólo la evolución compatible del DDL/versión para `migration_sources`; no tocar `escala_server/daos/schema.py`. |
| `escala_server/project_memory.py` | S22.3 | Adaptación mínima, sólo si resulta imprescindible para preservar la frontera de rutas del runtime. |
| `tests/test_project_memory_migration.py` | S22.3 | Contratos de migración y aislamiento. |
| `tests/fixtures/project_memory_migration/` | S22.3 | Empresas sintéticas completa y parcial/corrupta; nunca datos del workspace real. |

No son propietarios ni se modifican: `escala_server/migrate.py`,
`escala_server/daos/**`, `.scaleup/agent/memory/conversation.yaml`,
`.scaleup/knowledge/**`, el instalador y el front door.

## Tareas atómicas (TDD)

### 1. Definir el contrato de snapshot, resultado y fixtures de entrada

**Tamaño:** S  
**Depende de:** S22.2  
**Criterios:** MUST 1, 3 y 4; escenarios de primera migración y fuente inválida.

Crear los fixtures de dos proyectos aislados y el esqueleto público del
migrador. El contrato de resultado expone solamente `ready`, `db_path`,
`imported`, `skipped`, `errors` y `sources` relativos; no payloads sensibles.
El descubrimiento enumera una lista blanca de rutas, rechaza escapes de raíz y
excluye expresamente conversación y conocimiento distribuido.

- **RED:** pruebas para raíz completa/parcial, lista blanca, paths relativos,
  exclusión de conversación/knowledge y ausencia como `missing`.
- **GREEN:** dataclasses/resultados y descubrimiento/lectura inmutables mínimos;
  todavía sin escritura de negocio.
- **REFACTOR:** factorizar validación de path y normalización sin introducir un
  lector genérico que pueda incorporar archivos fuera del contrato.

**Archivos:** crear `escala_server/project_memory_migration.py`,
`tests/test_project_memory_migration.py`,

### 2. Añadir ledger local y validar la evolución del esquema

**Tamaño:** S  
**Depende de:** tarea 1  
**Criterios:** MUST 1, 2 y 5; escenario de repetición.

Evolucionar el DDL de S22.2 de forma compatible para registrar snapshots
exitosos por `relative_path`, `content_sha256` e `import_schema`, con
proveniencia/tipo/fecha suficientes. Subir `SCHEMA_VERSION` y extender el
contrato DDL-derivado para que `health()` acepte la DB actualizada y rechace un
ledger incompleto. La inicialización debe ser segura tanto para DB nueva como
para una DB válida de S22.2.

- **RED:** pruebas que inicializan una DB S22.2 y verifican upgrade, índice o
  unicidad del ledger y health posterior; prueba que un ledger defectuoso se
  rechaza.
- **GREEN:** DDL, migración de versión y helpers de esquema mínimos.
- **REFACTOR:** mantener la autoridad de estructura en `schema.py`; no
  duplicar SQL de validación en el migrador.

**Archivos:** modificar `escala_server/schema.py`; ampliar
`tests/test_project_memory_migration.py` únicamente en los contratos de

### 3. Persistir perfil y diagnóstico de manera determinista

**Tamaño:** M  
**Depende de:** tareas 1–2  
**Criterios:** MUST 1–4; escenarios de primera migración, repetición y error
parcial.

Implementar normalización canónica de YAML (claves estables) y SHA-256; en una
transacción por artefacto, hacer upsert de la compañía ID estable y facts
explícitos `profile.*`/`diagnosis.*`. Registrar ledger sólo junto con la
escritura exitosa. Igual fingerprint retorna `unchanged`; YAML inválido retorna
error por su ruta y deja avanzar las demás fuentes.

- **RED:** perfil completo crea compañía/facts/proveniencia; segunda ejecución
  no altera conteos; cambio de perfil actualiza sin duplicar; YAML corrupto no
  deja facts ni ledger de ese archivo.
- **GREEN:** serialización estable, upsert y unidad transaccional mínima.
- **REFACTOR:** centralizar el patrón `snapshot → dedupe → apply → ledger` para
  reutilizarlo con worksheets, sin extraer hechos de Markdown narrativo.

**Archivos:** modificar `escala_server/project_memory_migration.py` y
`tests/test_project_memory_migration.py`.

### 4. Migrar planes y worksheets con versionado exacto

**Tamaño:** M  
**Depende de:** tarea 3  
**Criterios:** MUST 1–4; SHOULD 2; escenarios de cambio real y plan ausente.

Incorporar pulse/context, OPSP válido y worksheets empresariales. OPSP tiene
precedencia; los Markdown heredados sólo aplican como fallback si no existe

- **REFACTOR:** conservar mapeo explícito de tipos/rutas y una sola primitiva
  transaccional; no reutilizar DAOs o migrador legado incompatibles.

## Orden y dependencias

`Contrato/fixtures → ledger compatible → perfil/diagnóstico →
planes/worksheets → integración/recuperación`.

El orden es deliberadamente riesgo-primero: primero se prueba el límite de
privacidad y la determinación del snapshot; después la evolución del DDL que
el runtime validará; por último se añaden escrituras de negocio. No hay tareas
paralelizables sin solapamiento de `schema.py`, el migrador o su suite de
contrato. La cadena es acíclica y cada paso termina en un commit reversible.

## Riesgos, mitigaciones y rollback

| Riesgo | Mitigación | Rollback |
|---|---|---|
| DDL nuevo deja inválida una DB local previa | Migración de versión y pruebas desde una DB S22.2; `health()` deriva su contrato del DDL | Restaurar backup local de S22.2 o revertir el commit de ledger; las fuentes siguen intactas. |
| Dedupe por mtime o JSON no estable duplica versiones | Hash SHA-256 de snapshot canónico y clave única de ledger; tests de repetición/cambio | Revertir la transacción del artefacto; no se registra ledger parcial. |
| YAML corrupto bloquea una empresa | Errores estructurados por ruta y transacción independiente | Reintentar tras corregir fuente; los artefactos válidos permanecen migrados. |
| Lectura fuera del proyecto o de conversación | Lista blanca, paths relativos contenidos, fixtures de exclusión | No hay escrituras en fuente; retirar el módulo revierte el comportamiento sin tocar datos de entrada. |
| Regresión de backup/restore | Prueba de recuperación offline sobre DB ya migrada | Usar backup local validado de S22.2; no hay servicios externos. |
