# S43.4 — Revisar antes de responder: diseño

## Problem

Una vez que S43.3 eligió la herramienta, ESCALA está a punto de generar una
recomendación. Sin una revisión intermedia, la respuesta puede contener:

- afirmaciones presentadas como hechos sin fuente,
- números de periodos distintos,
- fuentes que se contradicen,
- acciones que no responden al objetivo inicial,
- o preguntas críticas ausentes que cambiarían la decisión.

Esto erosiona la confianza del empresario y contradice el valor de E43.

## Value

El empresario recibe una respuesta que distingue claramente hechos, inferencias
y desconocidos; señala contradicciones y dudas; y solo avanza cuando la acción
propuesta responde al objetivo inicial.

## Complexity

**Moderate** — 4-5 componentes nuevos, lógica determinista de revisión sobre
estructuras ya existentes, tests que cubren tres escenarios críticos.

## Approach

Crear el módulo puro `coaching.reviewer` que, a partir de la ficha de decisión
de S43.1, el paquete de evidencia de S43.2 y el recibo de selección de S43.3,
genere un informe de revisión con `findings` clasificados y una acción final:
`reviewed` (pasa), `clarify` (falta información que altera la decisión) o
`blocked` (contradicción crítica detectada).

## Components Affected

| Component | Change | Purpose |
|-----------|--------|---------|
| `coaching/reviewer/__init__.py` | create | Punto de entrada `run(context)` que carga decisión, evidencia, recibo y devuelve informe de revisión. |
| `coaching/reviewer/engine.py` | create | Lógica pura de revisión: tipos de findings, detección de contradicciones, alineación de acción con objetivo. |
| `coaching/reviewer/models.py` | create | Modelos Pydantic para `ReviewFinding`, `ReviewReport` y `ReviewResult`. |
| `coaching/reviewer/formatter.py` | create | Renderiza el informe de revisión como markdown ejecutivo. |
| `coaching/reviewer/tests/test_reviewer.py` | create | Tests unitarios e integración. |
| `coaching/reviewer/__main__.py` | create | Entrada CLI `python -m coaching.reviewer`. |
| `escala-skills/escala-reviewer/SKILL.md` | create | Skill adapter delgado. |

## Design Decisions

| ID | Title | Rationale |
|----|-------|-----------|
| D1 | Nuevo módulo puro `coaching.reviewer` | Separa la lógica de revisión del adapter conversacional, siguiendo el patrón de `coaching.decision`, `coaching.evidence` y `coaching.selector`. |
| D2 | Revisión determinista sobre metadatos | Para una historia M, basta con revisar metadatos (periodo, confianza, status, área) y no requiere parsear el contenido de las fuentes. |
| D3 | Tres acciones posibles | `reviewed`, `clarify`, `blocked` cubren los casos: listo para responder, falta información, contradicción crítica. |
| D4 | Consumir `DecisionRef`, `EvidencePackage` y `SelectionReceipt` | Reutiliza los contratos de S43.1-S43.3 sin duplicar modelos. |
| D5 | Findings trazables | Cada finding tiene `kind`, `severity`, `source_ids`, `message` y `recommendation`. |

## Examples

### Entrada: recibo Cash con evidencia consistente

```json
{
  "base_path": ".",
  "decision": { "decision": "...", "area": "cash", "horizon": "inmediato", "outcome": "..." },
  "package": { "sources": [...], "missing": [], "not_trustworthy": [], "questions": [] },
  "selection": {
    "action": "tool_selected",
    "receipt": { "area": "cash", "tool": "cash_analysis", "evidence_used": ["worksheet-cash-ccc"], ... }
  }
}
```

### Salida: revisión aprobada

```json
{
  "output": "## Revisión de calidad\n\nLa recomendación puede avanzar...",
  "artifacts": {
    "action": "reviewed",
    "report": {
      "decision": "...",
      "area": "cash",
      "tool": "cash_analysis",
      "findings": [
        { "kind": "fact", "severity": "info", "source_ids": ["worksheet-cash-ccc"], "message": "Worksheet disponible y reciente.", "recommendation": "" }
      ],
      "critical_questions": [],
      "action_aligned": true,
      "can_proceed": true
    }
  },
  "errors": []
}
```

### Escenario: evidencia no confiable

Entrada con `not_trustworthy` no vacío:

Salida con acción `clarify` y findings de severidad `warning`.

### Escenario: contradicción crítica

Dos fuentes del mismo periodo con valores incompatibles (simulado por metadatos de confianza baja o estados contradictorios):

Salida con acción `blocked`.

## Acceptance Criteria

### MUST

- **AC1:** Dado un recibo y evidencia consistente, el módulo devuelve `action: reviewed` y `can_proceed: true`.
- **AC2:** Dado evidencia `not_trustworthy`, el módulo devuelve `action: clarify` con findings de advertencia.
- **AC3:** Dada una contradicción entre fuentes `available`, el módulo devuelve `action: blocked`.
- **AC4:** Cada finding incluye `kind`, `severity`, `source_ids`, `message` y `recommendation`.
- **AC5:** El módulo reutiliza `DecisionRef`, `EvidencePackage` y `SelectionReceipt` sin re-crear lógica de descubrimiento.
- **AC6:** Los tests de los tres escenarios pasan localmente.

### SHOULD

- **AC7:** La revisión detecta cuando la acción propuesta no alinea con el `outcome` de la decisión.

### MUST NOT

- **AC8:** El módulo no genera recomendaciones ejecutivas (eso es S43.5).
- **AC9:** El módulo no silencia findings críticos.

## Dependencies

- S43.1 debe haber confirmado una decisión.
- S43.2 debe producir un `EvidencePackage`.
- S43.3 debe producir un `SelectionReceipt`.

## Legacy Sweep

Nada queda huérfano. `coaching.selector` elige la herramienta; `coaching.reviewer`
revisa antes de responder. Son responsabilidades distintas.

## Drift Risks

- **AG4** (acoplamiento >3 módulos): bajo riesgo. `coaching.reviewer` consume
  únicamente los outputs de S43.1-S43.3 (solo lectura).

## Testing Strategy

| Layer | Name | Purpose |
|-------|------|---------|
| Unit | `test_reviewer.py` | Validar findings, contradicciones, alineación y acciones. |
| Integration | `run()` con `tmp_path` | Verificar flujo completo con decisión, package y selection. |
| Adapter smoke | skill `escala-reviewer` | Confirmar contrato de `run()`. |

## Open Questions

1. ¿La acción `blocked` debe incluir una pregunta específica para desbloquear?
   Se propone: sí, en `artifacts.questions`.
2. ¿La detección de contradicciones requiere parsear contenido de worksheets?
   Se propone: no, para esta historia basta con metadatos (status, confianza).
