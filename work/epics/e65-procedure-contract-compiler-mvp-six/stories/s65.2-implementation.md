# Implementación S65.2

- Se creó `validators/procedure_compiler.py`: un compilador fail-closed sin parámetros de fuente, release o ruta. Sólo carga el workspace validado y E64.
- Se añadieron seis plantillas internas y seis YAMLs renderizados: diagnóstico, OPPP, Vision Summary, prioridad trimestral, ritmo de reuniones y revisión trimestral.
- Cada plantilla une sus inputs con nodos canónicos y deja salida, dueño, KPI, Who/What/When y cadencia como `unknown` con preguntas abiertas explícitas.
- `procedures/mvp/release.json` conserva la traza nodo→procedimiento y los digests opacos derivados de E64, sin IDs de candidato ni `source_ids`.
- `scripts/build_mvp_procedures.py --check` verifica bytes exactos de todos los artefactos renderizados.
- `tests/test_procedure_compiler.py` cubre el camino válido y bloquea candidato Cash, nodo externo, evidencia inyectada, input no aprobado y release sin las exclusiones Cash obligatorias.


## Remediación de auditoría

Se endureció la compilación tras dos hallazgos altos: ahora recorre recursivamente toda plantilla antes de validarla y rechaza `candidate.*` o las tres exclusiones Cash incluso dentro de pasos, reglas, estado, handoff u objetos anidados. Además, una superficie MVP estática valida inputs, preguntas, pasos, outputs, reglas, warnings, criterios, actualizaciones de estado y handoff. Sólo un handoff dentro de los seis procedimientos MVP y el destino aprobado para ese flujo puede compilar.


## Remediación de bypass textual

La segunda re-auditoría detectó que la comprobación anterior sólo revisaba el inicio de cada string. `_reject_unapproved_references` ahora usa límites de token técnico: localiza cualquier `candidate.<id>` y las tres exclusiones Cash dentro de acción, prompt, statement, lista o diccionario anidado. No bloquea lenguaje ordinario como “A candidate may clarify the plan.” porque no contiene un identificador técnico con punto. Las pruebas adversariales cubren las cinco ubicaciones.
