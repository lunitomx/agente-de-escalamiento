# S35.1 Design: Golden Case Fixture Contract

## Complexity

Moderate. The story creates one validator module, one focused test file, and
YAML fixtures. It does not run LLM calls and does not compare full prose
snapshots.

## Problem

E35 needs behavior fixtures before it can detect skill drift. Without a typed
fixture contract, later drift checks would rely on ad hoc YAML and brittle
snapshot expectations.

## Value

Golden cases become stable, reviewable inputs for future drift gates. S35.1
defines what a valid behavior case is before S35.2 expands coverage and S35.3
checks outputs.

## Gemba Findings

- `validators/voice_of_customer.py` uses Pydantic + YAML and is the closest new
  contract-validator pattern.
- `validators/pipelines.py` validates skill references by checking
  `.agents/skills/<skill>/SKILL.md`.
- `.agents/skills/scaleup-*` contains the local skill catalog.
- `rai schema sum check` reports `schema.sum not found`; no storage schema is
  changed by this story.

## Legacy Sweep

Nothing becomes orphaned. This is a net-new contract for E35 golden cases.

## Approach

Create `validators/skill_golden_cases.py` with:

- `SkillGoldenCase`: typed fixture model.
- `load_golden_cases(path)`: YAML list loader.
- `validate_golden_case_file(path, skills_root)`: readable validation errors.

Required properties:

- `case_id`
- `skill`
- `input_context`
- `expected_sections`
- `required_methodology_terms`
- `forbidden_claim_patterns`
- `evidence_required`
- `notes`

Validation should fail when:

- the referenced skill does not exist;
- expected sections are empty;
- required methodology terms are empty;
- forbidden claim patterns are empty;
- `input_context` is empty.

## Components

| Component | Change | Purpose |
|---|---|---|
| `validators/skill_golden_cases.py` | create | Typed golden case fixture contract and validation helper. |
| `tests/test_skill_golden_cases.py` | create | Positive and negative fixture contract tests. |
| `tests/fixtures/skill_golden_cases/*.yaml` | create | Valid, missing skill, and missing expected properties examples. |

## Acceptance Criteria

### MUST

- Complete fixtures for existing skills pass validation.
- Fixtures referencing missing skills fail validation.
- Fixtures without expected properties fail validation.
- Validation errors are readable and actionable.

### MUST NOT

- Do not execute skills or call models.
- Do not validate generated outputs yet.
- Do not integrate release gates yet.

## Testing Strategy

| Layer | Test | Purpose |
|---|---|---|
| Unit | valid fixture loads and validates | Proves contract shape. |
| Unit | missing skill fails | Proves catalog reference check. |
| Unit | missing expected properties fail | Proves cases cannot be empty shells. |
| Unit | non-list fixture root fails | Proves YAML root contract. |
