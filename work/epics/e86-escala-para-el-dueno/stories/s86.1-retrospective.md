# Retrospectiva S86.1 — Cero comandos visibles

## Qué se entregó

- **Q2.** 31 `SKILL.md` internos (más el espejo `escala-agent/skills/escala-bugreport`)
  sin `/escala-`. Los siguientes pasos al dueño ahora son preguntas en español llano
  ("¿Vemos cuánto dinero liberas si cobras 10 días antes?"); las referencias del
  agente quedan como "procedimiento interno `escala-x`", igual que la puerta.
- **Q4.** `install.sh` quita cualquier symlink `escala*` que no sea la puerta (de
  cualquier repo, incluso rotos), nunca archivos/carpetas reales ni `scaleup-*`, y
  dice "Quité N atajos viejos; ahora sólo hablas con ESCALA." (singular con N=1).
- Tests: `tests/test_s86_1_no_visible_commands.py` (6), todo en HOME temporal y
  repo git sintético.

## Sorpresas

- `update.sh` llamaba `bash install.sh` sin plataforma; desde que el instalador exige
  `--platform`, salía con error 2 y nunca reinstalaba. Por eso Q4 no se cumplía con
  sólo cambiar el instalador. Ahora reinstala donde ya había un enlace `escala*`.
  El procedimiento `escala-update` tenía el mismo defecto y también se corrigió.
- `escala-health` contaba `escala-*`: tras la puerta única habría dicho 0. Ahora
  cuenta `escala*` (lo esperado es 1).
- El selector Python (`coaching/selector/engine.py` + `formatter.py`) todavía
  imprime "Próximo paso: ejecutar `/escala-cash`…". Está fuera de los `SKILL.md`; queda
  como pregunta abierta para S86.2/S86.4.

## Decisiones conservadoras

- Ejemplos JSON del selector/revisor: se reemplazó la lista `skills` por un marcador
  en lugar de cambiar el formato que emite el motor.
- No se tocó `~/.agents/skills`: el instalador nunca escribió ahí.
- La tabla de Strategy conserva sus dos columnas para no mover las filas de
  `escala-strategy-research`/`journey` que otras historias prueban.

## Aprendizaje

Un criterio de aceptación sobre un script envoltorio (`update.sh`) hay que probarlo
ejecutando el envoltorio, no sólo el script que llama: el defecto estaba en la llamada.
