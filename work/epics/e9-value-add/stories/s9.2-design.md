# S9.2: Quarterly Pulse — Design

**Story:** S9.2 — Quarterly Pulse  
**Epic:** E9 — Value-Add Features  
**Date:** 2026-05-06  
**Branch:** story/s9.2/quarterly-pulse

## Problem & Value

**Problem:** Users need a lightweight way to check progress between full diagnoses without repeating the full 26-question process. The current loop is: full diagnose → weeks of work → full diagnose again. There is no quick signal to surface whether an area is improving, stalling, or regressing between cycles.

**Value:** A 5-question pulse (~2 minutes) gives each Scaling Up decision a directional signal (-1/0/+1) on a weekly or monthly cadence. The comparison against prior pulse makes the trend visible, enabling timely course corrections before problems compound — rather than waiting for the next full diagnosis to surface them.

## Gemba Walk Findings

### Module pattern (from `coaching/export/__init__.py`)

All coaching modules follow the same contract:

```python
def run(context: dict) -> dict:
    """Returns dict with keys: output (str), artifacts (dict), errors (list[str])"""
```

Invoked via stdin JSON:
```bash
echo '{"answers": {...}}' | python3 -m coaching.pulse
```

- Read with `coaching/core.read_yaml()`, write with `coaching/core.write_yaml()`
- No external deps (stdlib + yaml already present)
- `__main__.py` is a 2-line entrypoint via `coaching.core.run_and_print`

### Decision keys and ROUTING_RULES duplication (PAT-L-1 flag)

`ROUTING_RULES`, `DECISION_LABELS`, and `PRIORITY_ORDER` are already duplicated between `coaching/diagnose/__init__.py` and `coaching/export/__init__.py`. The S9.1 retro lesson (PAT-L-1) identified this. Pulse needs a decision→skill map for course corrections. **Design decision: extract to `coaching/core` as part of this story.** This is additive-only — no existing module behavior changes. Both S9.1 modules can optionally import from core in future; S9.2 will import from core.

### Validators pattern (from `.scaleup/agent/validators/export.py`)

The export validator reads a markdown **file on disk**. Pulse has no markdown artifact — its output is a JSON dict and an appended YAML history. The S9.1 validator pattern does not map cleanly.

**Design decision:** The pulse validator validates the `pulse-history.yaml` file — specifically that the last entry has the required keys and correct structure. The SKILL.md adapter invokes `python3 .scaleup/agent/validators/pulse.py` after each pulse run; the validator reads the history file directly (no JSON file intermediary needed). This avoids inventing a new artifact and keeps the validator grounded in the durable output.

### Interactive prompting (new pattern)

No existing coaching module uses `input()`. Pulse introduces it when `answers` is absent from context. **Design decision:** interactive prompting is isolated in `coaching/pulse/__init__.py` behind a single guard: `if "answers" not in context: answers = _prompt_interactive()`. Tests and CLI piping always pass `answers` in context → never hit the prompt. This keeps the module testable and the interactive path auditable.

### pulse-history.yaml does not exist

`.scaleup/my-company/pulse-history.yaml` does not exist yet. First-run must create it gracefully.

### coaching/pulse/ does not exist

`coaching/pulse/` is net-new. No legacy code to preserve or migrate.

## Approach

Follow the identical cross-platform architecture established in S9.1 (coaching/export/):

```
coaching/pulse/
    __init__.py          ← run(context) -> dict, core pulse logic
    __main__.py          ← 2-line entrypoint via coaching.core.run_and_print
    tests/
        test_pulse.py    ← unit tests (non-interactive, answers always in context)

coaching/core/__init__.py  ← ADD: ROUTING_RULES, DECISION_LABELS, PRIORITY_ORDER (extraction)

.scaleup/my-company/
    pulse-history.yaml   ← created on first run, appended on subsequent runs

.scaleup/agent/validators/
    pulse.py             ← validates last entry in pulse-history.yaml

.claude/skills/scaleup-pulse/
    SKILL.md             ← thin adapter, invokes core Python
```

### Core logic (`coaching/pulse/__init__.py`)

**Input context keys:**
- `answers` (dict, optional): `{"people": -1, "strategy": 0, "execution": 1, "cash": 0, "overall": 0}`
- `base_path` (str, default `"."`)

**Execution flow:**
1. If `answers` not in context → call `_prompt_interactive()` to gather -1/0/+1 per decision
2. Validate answers: each value must be in `{-1, 0, 1}`, all 5 keys required
3. Load `pulse-history.yaml` (empty list if file doesn't exist)
4. For each decision, detect trend from current answer: `1→improving`, `0→stalling`, `-1→regressing`
5. Load prior pulse entry (if any) for context display
6. Build course_corrections list: for each regressing decision, append `f"{label} regressing → run {command}"`
7. Assemble markdown output table
8. Append new entry to pulse-history.yaml with timestamp
9. Return `{output, artifacts, errors}` per module contract

**Trend detection (resolved):** Trend is a direct mapping of the single answer value:
- `answer > 0` → `"improving"`
- `answer == 0` → `"stalling"`
- `answer < 0` → `"regressing"`

This is one question per decision per pulse. Multi-pulse trend lines (e.g., 3-run moving average) are explicitly S9.3 scope. The `sum` language in the task instructions was an artifact of an earlier multi-question design. Direct mapping is KISS.

### pulse-history.yaml schema

```yaml
pulses:
  - date: "2026-05-06"
    answers:
      people: 1
      strategy: 0
      execution: -1
      cash: 0
      overall: 0
    trends:
      people: improving
      strategy: stalling
      execution: regressing
      cash: stalling
      overall: stalling
    course_corrections:
      - "Execution regressing → run /scaleup-execution"
```

A list under `pulses:` key — insertion-ordered, new entries appended. The comparison logic reads `history["pulses"][-1]` for the prior entry. First-run creates the file with an empty `pulses: []` list, then appends.

### ROUTING_RULES extraction to `coaching/core`

Add three constants to `coaching/core/__init__.py` (no behavior changes, no existing imports modified):

```python
PRIORITY_ORDER = ["people", "strategy", "execution", "cash"]

DECISION_LABELS = {
    "people": "People",
    "strategy": "Strategy",
    "execution": "Execution",
    "cash": "Cash",
}

ROUTING_RULES = {
    "people": "/scaleup-people",
    "strategy": "/scaleup-strategy",
    "execution": "/scaleup-execution",
    "cash": "/scaleup-cash",
}
```

`coaching/pulse/__init__.py` imports from core. S9.1 modules (`diagnose`, `export`) keep their local copies for now — they can be refactored in a future cleanup story (no breaking changes in S9.2).

### Validator (`pulse.py`)

Validates the **pulse-history.yaml** file — specifically the last entry structure:

```python
REQUIRED_ENTRY_KEYS = ["date", "answers", "trends", "course_corrections"]
REQUIRED_DECISION_KEYS = ["people", "strategy", "execution", "cash", "overall"]
VALID_ANSWER_VALUES = {-1, 0, 1}
VALID_TREND_VALUES = {"improving", "stalling", "regressing"}
```

Usage:
```bash
python3 .scaleup/agent/validators/pulse.py .scaleup/my-company/pulse-history.yaml
```

Exit 0 = VALIDATION PASSED. Exit 1 = errors to stderr.

### SKILL.md adapter (thin wrapper)

Steps:
1. Check if profile exists (prerequisite guard)
2. Invoke `python3 -m coaching.pulse` with or without piped answers
3. Quality gate: `python3 .scaleup/agent/validators/pulse.py .scaleup/my-company/pulse-history.yaml`
4. Present `result["output"]` and `result["artifacts"]["course_corrections"]`

No business logic in the adapter.

## Acceptance Criteria

### MUST

1. `echo '{"answers": {"people": 1, "strategy": 0, "execution": -1, "cash": 0, "overall": 0}}' | python3 -m coaching.pulse` produces valid pulse JSON output with `output`, `artifacts`, `errors` keys
2. Trend correctly mapped: `answer > 0 → improving`, `answer == 0 → stalling`, `answer < 0 → regressing` per decision
3. Pulse entry appended to `.scaleup/my-company/pulse-history.yaml` with date, answers, trends, course_corrections
4. Course correction suggested for each regressing decision, pointing to correct `/scaleup-*` command
5. Quality gate validates last entry in pulse-history.yaml (exit 0 success, exit 1 with error messages to stderr)
6. `ROUTING_RULES`, `DECISION_LABELS`, `PRIORITY_ORDER` extracted to `coaching/core/__init__.py` and imported by pulse module

### SHOULD

- Handle first-run gracefully: create `pulse-history.yaml` with `pulses: []` then append; `prior_pulse_date` is `null`
- Interactive prompting when `answers` not provided in context (uses `input()` per decision)
- Prior pulse date surfaced in artifacts when history exists

### MUST NOT

- Modify existing `coaching/` module behavior (diagnose, welcome, progress, worksheet, level, router, export)
- Use external Python dependencies beyond stdlib + yaml
- Write to any path other than `.scaleup/my-company/pulse-history.yaml`
- Place business logic in SKILL.md adapter

## Key Design Decisions

1. **Trend = direct mapping of single answer, not sum.** One question per decision per pulse. `answer > 0 → improving`, `answer == 0 → stalling`, `answer < 0 → regressing`. Multi-pulse trend lines (moving average, regression slope) are S9.3 scope. The "sum" language in the task instructions was an artifact of an earlier multi-question design; direct mapping is KISS.

2. **Validator validates pulse-history.yaml, not a JSON file.** Pulse has no markdown artifact (unlike S9.1). The durable output of a pulse run is the appended YAML history. The validator reads the history file directly — no JSON intermediary needed — and checks the last entry's structure. This is the simplest approach that provides an end-to-end quality check.

3. **ROUTING_RULES extracted to coaching/core.** Pulse requires a decision→skill map for course corrections. Rather than duplicate a third time (already in diagnose and export), this story extracts the three constants (`ROUTING_RULES`, `DECISION_LABELS`, `PRIORITY_ORDER`) to `coaching/core/__init__.py` as an additive-only change. S9.1 modules keep their local copies for now — no behavior changes, no risk.

4. **Interactive prompting isolated behind single guard.** `if "answers" not in context: answers = _prompt_interactive()`. All unit tests and CLI piping pass answers in context — never touch the `input()` path. Interactive mode is a convenience for direct human use; it's not the primary execution path.

5. **pulse-history.yaml as list-under-key, not flat list.** Schema is `{pulses: [...]}` rather than a bare YAML list. This is more extensible (can add top-level metadata later, e.g., `version`) and follows the same pattern as other YAML files in `.scaleup/agent/memory/`.

6. **First-run creates file, no error.** If `pulse-history.yaml` doesn't exist, `run()` creates it with `pulses: []` then appends. `prior_pulse_date` is `null` in artifacts. The validator must handle this gracefully too (if pulses list is empty, validate as valid — no entries to check).
