## Conflict Resolution

### Conflict 1: File naming — append vs new file per same-day session

- **Existing scaleup-close Step 2** creates `YYYY-MM-DD-2.md`, `YYYY-MM-DD-3.md` for multiple same-day sessions.
- **s9.4-scope** says "append with separator" to the same `YYYY-MM-DD.md`.

**Resolution: Keep the existing per-file behavior.** S9.4 does NOT change the file naming logic. Each session gets its own file. The summary module appends to whatever file was written by close Step 2 — i.e., it writes the summary section into that same file after the YAML frontmatter + notes. The "append with separator" language in scope refers to same-file coexistence of the summary block alongside the notes block, not multi-session merging.

Scope is clarified: the session log file written by close Step 2 is the target. The summary module adds a `## Session Summary` section to it.

### Conflict 2: Data source — file-read vs context-passed

- **E9 design.md Risks** states: "El core recibe los datos como contexto; no deduce nada."
- A file-read approach would require re-parsing the just-written log, which is redundant and error-prone.

**Resolution: Core receives session data as context (stdin JSON).** The SKILL.md adapter passes the structured data it already collected in Step 1 directly to `coaching/summary` via stdin JSON. The module does NOT re-read the session log file.

### Conflict 3: "No user action required" vs user-prompted close

- Close Step 1 already asks the user 4 questions. That data collection happens regardless.
- "No user action required" means the summary is auto-generated from that already-collected data — no additional questions, no explicit "generate summary" command.

**Resolution: Summary runs automatically after Step 3 (quality gate passes).** It becomes Step 3.5 in the pipeline. User is not asked anything new. The adapter simply passes the collected data to `coaching/summary` and appends the output to the log file.

### Conflict 4: Score changes — no baseline snapshot exists

- `scaleup-start` reads current scores from YAML but does not persist a before-snapshot.
- There is no reliable "before" score to diff against at close time.

**Resolution: Score-change section is optional and omitted by default.** If `scores_before` is absent from context, the summary omits the score-change section entirely (graceful-omit). A future story can add baseline snapshotting to `scaleup-start`. The scope note "if diagnosis ran during session" captures this implicitly — for now, the condition is "if `scores_before` is provided in context," which will be rare until snapshotting is built.

### Conflict 5: User-prompted notes vs auto-summary coexistence

**Resolution: Both coexist in the same file.** The session log file retains its existing structure:
1. YAML frontmatter (written by close Step 2)
2. `## Session Notes` (written by close Step 2)
3. `## Session Summary` (appended by new Step 3.5)

The summary does not replace or modify the notes. It is additive.

---

## What and Why

**Problem:** After each coaching session, the user has no auto-generated record of what was accomplished. They must manually write notes or remember decisions later. Session records compound learning and accountability; auto-generation ensures consistency without adding user burden.

**What we're building:**

1. `coaching/summary/__init__.py` — public `run(context) -> dict` API, stdin JSON entry point
2. `coaching/summary/engine.py` — pure function: accepts session data dict, returns structured summary dict
3. `coaching/summary/formatter.py` — accepts structured summary dict, returns markdown string
4. `.scaleup/agent/validators/summary_validator.py` — validates summary section exists in a session log file
5. `.claude/skills/scaleup-close/SKILL.md` — updated to add Step 3.5 (invoke summary module)

**Why this architecture:**
- Matches the E8/E9 cross-platform pattern: core Python callable standalone, thin SKILL.md adapter
- Separates concerns: engine knows nothing about markdown, formatter knows nothing about business logic
- Validator follows the ADR-5 pattern: code-based quality gate, no LLM self-evaluation

### Example 3: Python module invocation (standalone)

```bash
echo '{
  "base_path": ".",
  "log_file_path": ".scaleup/my-company/sessions/2026-05-06.md",
  "date": "2026-05-06",
  "duration_minutes": 45,
  "decision_focus": "strategy",
  "worksheets_completed": ["7 Strata of Strategy"],
  "tasks_created": ["Define brand promise"],
  "tasks_completed": [],
  "notes": ["Clarified BHAG"],
  "scores_before": null
}' | python3 -m coaching.summary
```

Returns JSON:
```json
{
  "output": "Summary appended: .scaleup/my-company/sessions/2026-05-06.md",
  "artifacts": {
    "log_file_path": ".scaleup/my-company/sessions/2026-05-06.md",
    "summary_appended": true,
    "sections": ["decision_focus", "worksheets", "tasks", "notes"]
  },
  "errors": []
}
```

### Example 4: How `scaleup-close` SKILL.md invokes the summary module (Step 3.5)

After Step 3 (quality gate PASS), the adapter runs:

```bash
echo '{
  "base_path": ".",
  "log_file_path": "{log_file_path}",
  "date": "{YYYY-MM-DD}",
  "duration_minutes": {N},
  "decision_focus": "{decision}",
  "worksheets_completed": [{worksheets}],
  "tasks_created": [{tasks_created}],
  "tasks_completed": [{tasks_completed}],
  "notes": [{notes}],
  "scores_before": null
}' | python3 -m coaching.summary
```

The adapter checks the return value and continues to Step 4 if `errors` is empty.

## Acceptance Criteria

- **MUST**: Summary auto-generated when `/scaleup-close` runs — no additional user action
- **MUST**: Summary appended to the session log file written by close Step 2 (same file, after notes)
- **MUST**: Includes: duration, decision focus, worksheets completed, tasks created, tasks completed, session notes as key points
- **MUST**: Core Python module in `coaching/summary/` with `run(context) -> dict` interface
- **MUST**: Module callable standalone via `python3 -m coaching.summary` with stdin JSON
- **MUST**: Integrated into `scaleup-close` as new Step 3.5 (after quality gate, before confirmation)
- **MUST**: No regression — existing session validator (`validate_session_log`) still passes
- **SHOULD**: Quality gate validator (`summary_validator.py`) validates `## Session Summary` section present in log file
- **SHOULD**: Score-change section gracefully omitted when `scores_before` is null (not an error)
- **WONT**: Score delta computation (requires baseline snapshot — deferred to future story)

## Data Flow

```
scaleup-close Step 1 (user answers 4 questions)
    ↓ collected data dict
scaleup-close Step 2 (writes session log file with frontmatter + notes)
    ↓ log_file_path
scaleup-close Step 3 (quality gate — validate_session_log PASS)
    ↓
scaleup-close Step 3.5 [NEW] — invoke coaching.summary via stdin JSON
    → engine.py: build_summary(data) → summary dict
    → formatter.py: format_summary(summary) → markdown string
    → append to log_file_path
    → summary_validator.py: validate summary present (quality gate)
    ↓ (errors == [])
scaleup-close Step 4 (show confirmation to user — unchanged)
```

## LEAN Gates

- **KISS**: engine.py is a pure function with no I/O; formatter.py is a pure function. All I/O in `__init__.py`.
- **DRY**: reuses `coaching/core` utilities (`ensure_dir`, `read_yaml`); mirrors export module pattern.
- **YAGNI**: score-delta deferred; no email/external sending; no retroactive generation.
- **MVP**: one summary section appended to existing file — smallest possible complete feature.
