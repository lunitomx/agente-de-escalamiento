# S9.3: Progress Dashboard — Design

**Story:** S9.3 — Progress Dashboard  
**Epic:** E9 — Value-Add Features  
**Date:** 2026-05-06  
**Branch:** story/s9.3/progress-dashboard  

---

## Problem & Value

**Problem:** Users have diagnosis scores in `company-profile.yaml` and pulse history in `pulse-history.yaml`, but no single view to see both. After running `/scaleup-pulse` multiple times, there is no way to quickly answer: "Where do I stand now? What's trending up? What needs attention?"

**Value:** A one-command dashboard (`/scaleup-dashboard`) gives the full picture: current diagnosis scores, the historical pulse trajectory over time, which decisions are winning, and which need immediate attention — making progress tangible and removing the need to open multiple files.

## Gemba Walk Findings

### coaching/progress/ — V1 already exists (legacy sweep)

`coaching/progress/__init__.py` already exists and is a **worksheet-completion progress tracker**. It shows:
- Scores per decision (from `company-profile.yaml`)
- Worksheet completion counts per decision (e.g., "3/8 worksheets done")
- Suggested next worksheet based on lowest score

It does **NOT** read from `pulse-history.yaml`. It has no concept of pulse trajectory, wins, or attention areas. The existing skill adapter is `.claude/skills/scaleup-progress/SKILL.md`.

**Legacy sweep verdict:** `coaching/progress/` is V1 of a different capability — worksheet progress, not pulse trajectory. The S9.3 dashboard is a **net-new module** (`coaching/dashboard/`) that is independent of and does not modify `coaching/progress/`. The story AC says "extends coaching/progress/" — this is scope language meaning "builds on the progress concept," not a Python inheritance or import relationship. Dashboard will stand alone.

### Module pattern (from coaching/export/ and coaching/pulse/)

All coaching modules follow the contract:
```python
def run(context: dict) -> dict:
    """Returns dict with keys: output (str), artifacts (dict), errors (list[str])"""
```

Invoked via stdin JSON:
```bash
echo '{}' | python3 -m coaching.dashboard
```

`__main__.py` is always a 2-line entrypoint via `coaching.core.run_and_print`.

### Data source 1: Diagnosis scores

The scope document mentions `.scaleup/agent/memory/diagnosis.yaml`, but this file **does not exist**. Only `company-profile.yaml` exists in that directory. Diagnosis scores live under the `scores` key in `company-profile.yaml`:

```yaml
scores:
  people: 0
  strategy: 0
  execution: 0
  cash: 0
  last_diagnosis: ""
```

The export module (`coaching/export/__init__.py`) already uses this pattern via `_read_scores()`. Dashboard will follow the identical pattern.

### Data source 2: Pulse history (locked schema PAT-L-7)

`pulse-history.yaml` schema confirmed from real file:

```yaml
pulses:
  - date: "2026-05-06"
    answers:
      people: 1
      strategy: 0
      execution: -1
      cash: 0
      overall: 0
    trends:
      people: improving
      strategy: stalling
      execution: regressing
      cash: stalling
      overall: stalling
    course_corrections:
      - "Execution regressing → run /scaleup-execution"
```

### Validator pattern (from export.py and pulse.py)

Export validator checks a markdown file for `##` section headers (exit 0/1). Pulse validator checks the YAML history file structure. Dashboard validator follows the export pattern: validates the markdown output string for required `##` section headers.

Dashboard output is a **string** returned in `result["output"]` — it does not write to disk. The validator will accept the dashboard output as a string via stdin (or a temp file). This is the simplest pattern that provides the quality check without creating an unnecessary file artifact.

### Shared constants (coaching/core/)

`DECISION_LABELS`, `ROUTING_RULES`, and `PRIORITY_ORDER` are already in `coaching/core/__init__.py` (extracted during S9.2). Dashboard imports from core — no duplication.

### Sessions directory

`.scaleup/my-company/sessions/` exists but is empty. The scope document explicitly excludes reading session logs — pulse-history.yaml is the structured source. Confirmed out of scope.

## Approach

Follow the identical cross-platform pattern from S9.1/S9.2:

```
coaching/dashboard/
    __init__.py          ← run(context) -> dict, core dashboard logic
    __main__.py          ← 2-line entrypoint via coaching.core.run_and_print
    tests/
        test_dashboard.py

.scaleup/agent/validators/
    dashboard.py         ← validates 4 required ## sections in output string

.claude/skills/scaleup-dashboard/
    SKILL.md             ← thin adapter, invokes core Python
```

### Core logic (`coaching/dashboard/__init__.py`)

**Input context:**
- `base_path` (str, default `"."`)

**Execution flow:**
1. Read scores from `.scaleup/agent/memory/company-profile.yaml` → `profile["scores"]`
2. Read `pulse-history.yaml` → `{pulses: [...]}`
3. Build Section 1: Current Scores table (scores + level labels)
4. Build Section 2: Pulse History table (date × decision trends, most-recent first)
5. Build Section 3: Wins — decisions where most recent pulse trend == `"improving"`
6. Build Section 4: Attention Areas — decisions where trend == `"regressing"` in last pulse OR trend == `"stalling"` in both last 2 pulses
7. Return `{output: markdown_string, artifacts: {...}, errors: []}`

Dashboard is **read-only**: it reads two files and returns a string. It writes nothing to disk.

### Win/Attention derivation rules

```python
# Wins: improving in most recent pulse
wins = [d for d in DECISIONS if last_pulse["trends"].get(d) == "improving"]

# Attention: regressing in last pulse OR stalling in last 2+ consecutive pulses
attention = []
for d in DECISIONS:
    if last_pulse["trends"].get(d) == "regressing":
        attention.append((d, "regressing"))
    elif len(pulses) >= 2 and last_pulse["trends"].get(d) == "stalling" and pulses[-2]["trends"].get(d) == "stalling":
        attention.append((d, "stalling"))
```

### Graceful degradation

| Condition | Behavior |
|-----------|----------|
| `company-profile.yaml` missing or `scores` empty | Current Scores section shows placeholder: "No diagnosis yet. Run `/scaleup-diagnose` first." |
| `pulse-history.yaml` missing or `pulses` empty | Pulse History, Wins, Attention sections show: "No pulse data yet. Run `/scaleup-pulse` to start tracking." |
| Only 1 pulse entry | Attention "stalling 2+" check skipped (no prior to compare); regressing check still runs |

### Validator (`dashboard.py`)

Validates markdown **string from stdin** — four required `##` sections:

```python
REQUIRED_SECTIONS = [
    "## Current Scores",
    "## Pulse History",
    "## Wins",
    "## Attention Areas",
]
```

Usage:
```bash
echo '{}' | python3 -m coaching.dashboard | python3 -c "
import sys, json
result = json.loads(sys.stdin.read())
print(result['output'])
" | python3 .scaleup/agent/validators/dashboard.py
```

Or pass output string via file. Exit 0 = VALIDATION PASSED. Exit 1 = errors to stderr.

**Note:** The validator reads from a file path argument (consistent with export.py pattern) so the SKILL.md adapter can pipe the output to a temp file and validate it.

### SKILL.md adapter (thin wrapper)

Steps:
1. Prerequisite guard: check `company-profile.yaml` exists
2. Invoke `echo '{}' | python3 -m coaching.dashboard`
3. Extract `result["output"]` — write to temp file
4. Run quality gate: `python3 .scaleup/agent/validators/dashboard.py <temp_path>`
5. Present the dashboard markdown to the user
6. If `result["errors"]` non-empty, show errors and suggest remediation

No business logic in the adapter.

## Acceptance Criteria

### MUST

1. `echo '{}' | python3 -m coaching.dashboard` produces valid JSON with `output`, `artifacts`, `errors` keys
2. `result["output"]` is markdown containing exactly 4 `##` sections: `Current Scores`, `Pulse History`, `Wins`, `Attention Areas`
3. Current scores table reads from `company-profile.yaml` → `scores` key (same path as `coaching/export/_read_scores()`)
4. Pulse history table built from `pulse-history.yaml` — graceful "No pulse data yet" message when file missing or empty
5. Wins correctly identifies decisions with `trend == "improving"` in most recent pulse
6. Attention areas flags: regressing in last pulse OR stalling in last 2+ consecutive pulses
7. Quality gate validates 4 required sections (exit 0 = valid, exit 1 = errors to stderr)

### SHOULD

- Show most-recent pulse first in history table (reverse chronological)
- Gracefully handle missing `company-profile.yaml` with placeholder message
- Surface `pulse_count` in artifacts
- Include routing command in attention items (e.g., `→ run /scaleup-execution`)

### MUST NOT

- Write to any file (dashboard is read-only — no persistence)
- Modify `coaching/progress/` or any existing coaching module
- Import from `coaching/progress/` (independent module)
- Use external Python dependencies beyond stdlib + PyYAML (already present)
- Place business logic in SKILL.md adapter

## Key Design Decisions

1. **`coaching/dashboard/` is net-new, not an extension of `coaching/progress/`.** The AC phrase "extends coaching/progress/" refers to the product concept (building on the progress idea), not a Python import relationship. `coaching/progress/` is a worksheet-completion tracker. `coaching/dashboard/` is a pulse-trajectory dashboard. They serve different purposes, read different data, and must remain independent to avoid coupling two unrelated concerns.

2. **Data source for scores is `company-profile.yaml`, not `diagnosis.yaml`.** The scope document mentions `diagnosis.yaml`, but that file does not exist. Scores live in `company-profile.yaml` under the `scores` key — confirmed by reading the actual file and the existing `coaching/export/_read_scores()` implementation. Dashboard follows the identical read pattern.

3. **Dashboard is read-only — no file writes.** Unlike export (writes an action plan file) or pulse (appends to history), the dashboard only reads and returns a formatted string. This keeps the module side-effect-free and simplifies testing.

4. **Validator validates the markdown output string via a file argument.** Following the export.py pattern, the validator receives a file path. The SKILL.md adapter pipes the dashboard output to a temp file. This is consistent with existing validator conventions and avoids inventing a new stdin-based validator pattern.

5. **Attention "stalling 2+" requires at least 2 pulses.** When there is only 1 pulse, the stalling-persistence check is skipped (no prior entry to compare). Regressing is still flagged with 1 pulse. When 0 pulses, the entire Wins/Attention section shows "No pulse data yet."

6. **Pulse history table uses trend labels, not raw answers.** The `-1/0/+1` answers are implementation details. The table shows `improving/stalling/regressing` which is directly human-readable. The `answers` field is available in each entry but not surfaced in the dashboard table.

7. **KISS on statistics.** No trend lines, no moving averages, no percentages. Read the last 1-2 pulse entries and apply two simple rules. S9.3 scope explicitly excludes "ASCII charts" and "date filtering." YAGNI.
