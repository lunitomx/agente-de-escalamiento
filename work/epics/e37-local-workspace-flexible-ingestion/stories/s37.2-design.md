# S37.2: Flexible File Ingestion — Design

## Complexity and gemba

S37.2 es compleja (story L): toca contratos, registry, cuatro familias de
formato, perfilado estructural, preguntas, identidad y receipts. La caminata
de código encontró que `escala_server/workspace/authority.py` ya resuelve la
contención local y la redacción de autoridad; se reutilizará, no se duplicará.
`coaching/class_intake.py:20-59` es un flujo didáctico específico que persiste
YAML y serializa rutas absolutas, por lo que permanece como V1 coexistente y no
se convierte en parser empresarial. No existe un ingester genérico que deba
eliminarse. El grafo recuperó los guardrails de aprendizaje, boundary-first y
el diseño de E37; no había un componente existente para reutilizar.

No existe `governance/drift-hotspots.json` ni `governance/drift-catalog.md` en
el checkout. La revisión de drift del módulo de autoridad de S37.1 no encontró
clones; el único riesgo AG2 es duplicar guardas/receipts, mitigado por un único
seam compartido. AG4 se controla manteniendo el walking skeleton en un módulo
cerrado. El gate global de story-accretion contiene IDs futuros S37.2/S37.3 en
tests del ledger; se tratará como warning histórico, no como defecto funcional.

## Problem and value

El runtime ya puede saber dónde está su autoridad, pero todavía no puede
recibir el CSV, Excel o transcript que el empresario ya tiene y explicar con
seguridad qué estructura encontró. Un perfilador local hace visible lo
entendido, detiene los empates materiales y entrega una identidad repetible a
las siguientes historias sin imponer una plantilla ni enviar datos a la nube.

## Approach

Se crea `escala_server.workspace.ingestion` con modelos Pydantic estrictos,
una registry cerrada y adapters pequeños basados en la stdlib. CSV/TSV usan
`csv`; XLSX básico se inspecciona con `zipfile` + XML; texto/transcript se
perfila por encoding y estructura; PDF, cifrado, extensión desconocida o
provider faltante devuelven una disposición explícita. Cada entrada pasa por
`validate_workspace`, se comprueba que el archivo esté dentro de
`exchange_root`, se calcula SHA-256 y se deriva `source_id` de la ruta relativa
y los bytes. El perfil no escribe SQLite ni mueve el archivo.

El resultado distingue datos internos de un receipt redacted. El receipt solo
expone `status`, códigos, conteos, ordinales de tablas/filas/columnas,
`relative_path`, fingerprint y `source_id`; nunca nombres de máquina, URLs,
contenido de celdas, encabezados crudos o secretos. Si el mejor candidato de
encabezado/fecha/entidad empata, el estado es `needs_clarification` con
opciones como `row_0` y `row_1`; no se inventa una interpretación.

No se añade dependencia externa: Pydantic ya existe y la lectura tabular básica
se mantiene en la biblioteca estándar. Esto mantiene la instalación local y
el límite sin host, OAuth, API de Drive/OneDrive, OCR o telemetría.

## Concrete examples

```python
result = profile_source(config, exchange / "ventas.csv")
assert result.status == "ready"
assert result.identity.relative_path == "ventas.csv"
assert str(exchange) not in result.receipt_json
```

```python
result = profile_source(config, exchange / "cash.tsv")
assert result.status == "needs_clarification"
assert result.questions[0].code == "header_row_ambiguous"
assert result.questions[0].options == ("row_0", "row_1")
```

```python
result = profile_source(config, exchange / "estado.pdf")
assert result.status in {"provider_unavailable", "unsupported"}
assert str(exchange) not in result.receipt_json
```

## Acceptance criteria

### MUST

1. La registry reporta capability y outcome explícito para CSV, TSV, XLSX,
   texto/transcript, PDF y extensiones desconocidas sin red.
2. CSV/TSV y XLSX básico perfilan estructura, candidatos de encabezado y tipos
   date/entity/unit sin plantilla obligatoria.
3. Ambigüedad material produce preguntas ordinales y no cambia estado canónico.
4. Fingerprint, procedencia relativa, source identity y receipts son
   deterministas; cambiar bytes cambia identidad.
5. Unsupported/provider-unavailable/corrupt y redaction están probados.

### SHOULD

- Exponer el resultado en JSON y Markdown idénticos en información segura.
- Dejar un punto de extensión local para que S37.3 consuma el `source_id` sin
  mover ni persistir aquí.

### MUST NOT

- No API cloud, OAuth, hosted runtime, SQLite sync, OCR, universal parser,
  movimiento de archivos, escritura de estado canónico ni dependencia nueva.

## Testing strategy

Fixtures temporales cubren CSV y TSV válidos, dos headers empatados, workbook
XLSX básico, texto UTF-8, bytes corruptos, workbook cifrado/no interpretable,
PDF/unknown y cambio de un byte. Se verifican no mutación de origen/SQLite,
ausencia de paths absolutos y contenido en receipts, estabilidad byte-a-byte y
calidad completa de pytest, Ruff y Pyright.
