# S37.3: Synced-Folder Inbox & Failure Handling — Design

## Complexity and gemba

S37.3 es moderada: agrega un scanner, ledger local, outcomes de corrida,
atomic write y qualification E2E alrededor de los contratos ya probados. La
caminata encontró que `escala_server.workspace.authority` ya valida raíces y
que `escala_server.workspace.ingestion` ya posee `build_source_identity`,
`profile_source` y receipts. No se duplican. `coaching/class_intake.py` sigue
siendo V1 didáctico y no tiene relación con inbox empresarial; no hay V1 que
quede huérfano.

No existe `governance/drift-hotspots.json` ni `governance/drift-catalog.md` en
este checkout. AG2 se mitiga delegando identidad/perfilado a S37.2; AG4 se
mitiga con un scanner directo sin watcher, sin API y sin recursión. Los
warnings históricos del gate de story-accretion no pertenecen a este código.

## Problem and value

Una carpeta sincronizada es útil solo si las corridas diarias son repetibles y
los fallos no se convierten en corrupción o pérdida de documentos. El scanner
local hace visible qué fue aceptado, duplicado o reportado y conserva la
autoridad en la máquina del instalador.

## Approach

`escala_server.workspace.inbox` recibe `InboxConfig(workspace, max_bytes)` y
enumera únicamente archivos directos de `exchange_root`. El tamaño, symlink y
tipo se validan antes de leer; las demás entradas pasan por S37.2. Un
`InboxLedger` Pydantic se guarda en `data_root/.escala-inbox-ledger.json`,
fuera del intercambio y de SQLite. La primera disposición por `source_id` se
conserva. Una identidad vista vuelve como `duplicate`; un byte cambiado produce
otro hash y otra entrada. El ledger se escribe con archivo temporal y
`os.replace`; si está corrupto, la corrida falla cerrada sin mutación.

Los outcomes `accepted`, `duplicate`, `needs_clarification` y `quarantined`
usan códigos estables. Quarantine es report-only: el original nunca se borra,
mueve ni sobreescribe. Los reportes se escriben en
`data_root/.escala-inbox-reports/` y solo contienen procedencia relativa,
source IDs, dispositions y códigos. El `run_id` es un hash de esa salida
segura, no una marca de tiempo ni un path.

No se agrega dependencia, watcher, OAuth, SDK de Drive/OneDrive, red,
telemetría ni migración SQLite.

## Concrete examples

```python
first = scan_inbox(InboxConfig(workspace=config))
second = scan_inbox(InboxConfig(workspace=config))
assert first.items[0].disposition == "accepted"
assert second.items[0].disposition == "duplicate"
```

```python
source.write_text("fecha,cliente,importe\\n2026-07-22,Acme,11\\n")
run = scan_inbox(InboxConfig(workspace=config))
assert run.items[0].disposition == "accepted"
assert len(run.ledger.source_ids) == 2
```

```python
run = scan_inbox(InboxConfig(workspace=config, max_bytes=10))
assert run.items[0].disposition == "quarantined"
assert run.items[0].code == "source_too_large"
```

## Acceptance criteria

### MUST

1. Repeated scan: accepted → duplicate and unchanged ledger.
2. Changed bytes: new source identity while old identity remains.
3. Symlink/directory/oversized/corrupt/unsupported/ambiguous failures are
   explicit, report-only and non-destructive.
4. Ledger/reports/receipts are local, deterministic and redacted.
5. Temporary real-folder qualification proves all invariants without cloud.

### SHOULD

- Keep the ledger small and sorted so diffs and receipts are reviewable.
- Provide both JSON and Markdown run receipts for later E38/E42 consumption.

### MUST NOT

- No SQLite schema or exchange database, no cloud API/OAuth, no watcher,
  destructive move, OCR, universal parser or new dependency.

## Testing strategy

Temporary folders cover valid CSV/XLSX, second scan, changed bytes, ambiguous
TSV, corrupt/unknown/oversized/symlink/directory inputs, corrupt ledger, JSON
and Markdown redaction, and filesystem/SQLite non-mutation. A qualification
receipt records only safe booleans, dispositions and commit hashes.
