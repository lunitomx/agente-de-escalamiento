# Retrospective: S37.3 — Synced-Folder Inbox & Failure Handling

**Dates:** 2026-07-22 10:01 -06:00 → 10:13 -06:00  
**Estimated:** 35m hypothesis | **Actual implementation span:** ~9m53s

## Summary

S37.3 completa el límite E37: una corrida directa de filesystem sobre una
carpeta ordinaria, incluso si la carpeta está sincronizada por Drive/OneDrive,
acepta fuentes una vez, devuelve `duplicate` en reruns, conserva identidades
anteriores cuando cambian bytes y reporta symlinks, directorios, oversize,
corruptos y formatos no soportados sin mover documentos ni crear SQLite.

El ledger JSON es local al `data_root` del instalador, sus escrituras son
atómicas y los reportes JSON/Markdown son deterministas y redacted. El ledger
maestro de E37 sigue `unproved`; esta story deja listos REQ-E37-006 y
REQ-E37-007, pero no los promueve por sí sola.

## What went well

- La separación ledger/data_root vs exchange evitó el riesgo principal de
  sincronizar autoridad por accidente.
- `first disposition wins` hizo visible la idempotencia: el segundo scan fue
  read-only para el ledger y un byte cambiado produjo un nuevo ID.
- El scanner rechazó symlink/directorio/oversize antes de llamar a S37.2, sin
  seguir aliases ni leer contenido innecesario.
- El caso real representó Drive/OneDrive con una carpeta ordinaria y no
  necesitó connector, OAuth o servicio remoto.
- El reporte de fallos fue report-only; el archivo original, el nombre y el
  contenido permanecieron intactos.

## What to improve

- La qualification inicial usó un límite demasiado bajo y convirtió el CSV
  válido en oversize; se detectó antes de registrar evidencia y se repitió con
  `max_bytes=100`, dejando el resultado correcto y trazable.
- El scanner aún enumera solo entradas directas; si E38 necesita subcarpetas,
  habrá que diseñar una política explícita, no activar recursión implícita.
- El ledger JSON es adecuado para un writer local; cualquier futura escritura
  concurrente debe diseñarse como una story separada, no asumirse segura.

## Heutagogical checkpoint

1. **¿Qué aprendí?** La idempotencia no requiere mover documentos: una
   identidad por bytes, un ledger fuera del exchange y una primera disposición
   estable son suficientes para una corrida diaria segura.
2. **¿Qué cambiaría del proceso?** Probaría el límite de tamaño como primer
   fixture de qualification, porque es una configuración operacional que puede
   invalidar un caso feliz aunque el parser funcione.
3. **¿Mejoras para el framework?** RaiSE debería tener un gate nativo para
   writer/validator local y para la ausencia de `gate-code`; hoy hay que
   registrar el fallback manualmente aunque los gates disponibles pasen.
4. **¿En qué soy más capaz ahora?** Puedo integrar un parser local en un inbox
   repetible con límites de seguridad, ledger auditable y receipts útiles para
   las siguientes épicas sin convertirlo en SaaS.

## Improvements applied

- El ledger se validó antes de escanear y se escribe con temp + `os.replace`.
- Se añadió qualification con booleans seguros para rerun, bytes cambiados,
  symlink, directorio, oversize, corrupto, reportes y SQLite.
- La API pública `escala_server.workspace` expone el scanner y receipts, sin
  duplicar los seams de S37.1/S37.2.
- La ausencia de `gate-code` instalada queda documentada; no se presenta como
  un PASS ficticio.

## Patterns added / reinforced

- Añadido `PAT-L-1306`: ledger de idempotencia fuera del exchange, primera
  disposición, duplicate read-only y nueva identidad por bytes.
- Reforzado `PAT-L-6` con +1: writer/validator contract para el ledger y
  receipts.
- Reforzados `PAT-L-1304` y `PAT-L-1305` con +1: identidad/redaction y
  outcomes explícitos de adapters.
