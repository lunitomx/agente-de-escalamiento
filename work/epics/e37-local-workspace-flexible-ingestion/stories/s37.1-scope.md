# S37.1 Scope: Local Workspace & Data Authority

## Objective

Crear el contrato ejecutable que separa la autoridad local de datos de la
carpeta ordinaria de intercambio. Antes de que cualquier DAO o runtime abra
SQLite, ESCALA debe demostrar que la base y el estado autoritativo viven fuera
del exchange y que la configuración no contiene una integración cloud oculta.

## In Scope

- Modelo Pydantic estricto `WorkspaceConfig` con versión, plataforma y roles de
  `data_root`, `database_path` y `exchange_root`.
- Resolución segura de rutas absolutas/relativas, symlinks y containment sin
  depender de prefijos de texto ni nombres como Drive/OneDrive.
- Guard fail-closed para SQLite, WAL/journal y raíces canónicas dentro del
  exchange, ejecutada antes de crear directorios o conexiones.
- Resultado/receipt acotado con roles, códigos estables, hashes opcionales y
  locators lógicos; nunca rutas absolutas, secretos ni contenido.
- Seam local para que CLI/server/DAO puedan validar la configuración antes de
  `init_db` sin añadir red, OAuth, telemetría o servicio remoto.
- Fixtures y gates positivos/negativos para macOS y formas Windows de path.

## Out of Scope

- Perfilado o extracción de CSV/XLSX/DOCX/PDF/transcripts; S37.2.
- Enum, fingerprint de fuentes, idempotencia, duplicados o cuarentena del
  inbox; S37.3.
- Consolidación de `escala_server/schema.py` y `escala_server/daos/schema.py`.
- Instalador empaquetado para macOS/Windows, migración, rollback o release; E41.
- Escritura de datos de empresa, hechos contables, dashboards o coaching.
- APIs cloud, OAuth, sincronización de SQLite o colaboración multi-writer.

## Done When

- [ ] `WorkspaceConfig` rechaza campos desconocidos, raíces ausentes,
      containment ambiguo y database/exchange overlap.
- [ ] La validación resuelve symlinks y evita que un path aparente fuera del
      exchange oculte una ubicación dentro.
- [ ] El fallo de autoridad ocurre antes de crear DB, WAL, journal o directorio
      autoritativo, con prueba de no mutación.
- [ ] El resultado positivo y los errores son deterministas, tipados y
      redacted; no contienen rutas absolutas, valores de configuración cloud ni
      contenido de archivos.
- [ ] El seam puede ser invocado desde el runtime local sin llamadas de red ni
      API de Drive/OneDrive.
- [ ] Tests focalizados, lint, formato y pyright pasan antes del cierre de la
      story; la suite completa se revalida en el merge local.
- [ ] El artefacto de evidencia para REQ-E37-001 y REQ-E37-002 está listo para
      que S37.1 lo conecte al ledger maestro sin marcarlo como probado antes de
      los receipts finales.

## Acceptance Evidence

- Contrato y schema Pydantic versionado.
- Matriz de paths válidos, overlap, symlink y Windows-style fixtures.
- Receipt positivo redacted y receipts negativos con códigos estables.
- Before/after fingerprint del workspace temporal probando que una negativa no
  crea SQLite, WAL, journal ni directorios.
- Gate command reproducible para `REQ-E37-001` y `REQ-E37-002`.

## Constraints

- Fail closed sobre errores de resolución, filesystem no legible, campos
  desconocidos, schema mayor o containment no determinable.
- No se imprime ni serializa una ruta absoluta de la máquina, URL, token,
  credential, contenido o stdout crudo de subprocess.
- Los modelos nuevos deben ser Pydantic strict y totalmente tipados.
- No se hace push, publicación, modificación del public candidate ni cambio
  destructivo de archivos existentes.
