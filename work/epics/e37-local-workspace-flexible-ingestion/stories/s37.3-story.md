# Story: Synced-Folder Inbox & Failure Handling

## User Story

As an entrepreneur who exchanges files through a normal local, Google Drive or
OneDrive-synced folder,
I want ESCALA to scan that folder repeatedly, accept each source once and
report or isolate unsafe inputs,
so that a daily run cannot duplicate sources, corrupt local authority or expose
which files failed.

## Acceptance Criteria

### Scenario: valid inbox entries are accepted idempotently

```gherkin
Given a local exchange folder with a ready CSV and XLSX
When the inbox is scanned twice
Then the first scan records accepted source identities
And the second scan reports duplicate for the same identities
And the local source ledger is unchanged by the second scan
```

### Scenario: changed bytes create a new source disposition

```gherkin
Given a source already accepted by its fingerprint
When its bytes change and the inbox is scanned again
Then the new fingerprint/source identity is processed as a new source
And the prior identity remains auditable in the installer-local ledger
```

### Scenario: unsafe or unsupported entries are isolated by report

```gherkin
Given corrupt, encrypted, oversized, ambiguous, unsupported or symlink inputs
When the inbox is scanned
Then each input receives a stable quarantine/report disposition
And the original exchange file is not deleted or overwritten
And no authoritative SQLite state is written for the failed input
```

### Scenario: ordinary synced folders remain filesystem-only

```gherkin
Given the exchange root is a folder already synchronized by Google Drive or OneDrive
When the inbox runs
Then it uses ordinary filesystem reads only
And it never calls cloud APIs, OAuth, telemetry or hosted services
```

## Examples (Specification by Example)

| Input | Action | Expected Output |
|-------|--------|-----------------|
| `ventas.csv` ready | Scan twice | `accepted` then `duplicate`, one ledger identity |
| Same filename with changed bytes | Scan | New `accepted` identity, old identity retained |
| Ambiguous `cash.tsv` | Scan | `needs_clarification`, safe report, source untouched |
| Corrupt/large/unknown/symlink entry | Scan | Explicit `quarantined` disposition, no destructive move |

## Notes

This story consumes S37.1 authority and S37.2 profiling. The authoritative
SQLite and company state stay on the installer machine; the exchange folder is
ordinary documents only. The local source ledger/report is installer-local
runtime metadata, never a synced SQLite database and never a cloud API.
